### Allocation

- Swift는 자동으로 메모리를 할당하고 해제한다.

**Stack**

- 스택 포인터 연산을 통해 메모리를 할당하고 해제하므로 매우 빠르다.

**Heap**

- 힙 메모리 내에 사용되지 않는 부분을 찾아 할당하고, 해제하려는 경우 메모리를 어디에 반납할지 결정하는 과정이 필요하다.
- 힙은 멀티 스레드 환경에서 공유되기 때문에, 스레드 안정성을 보장하기 위한 비용이 크다.
- 참고) 힙에 메모리가 할당되는 모습
    
    <img width="879" height="407" alt="image" src="https://github.com/user-attachments/assets/d91efcbc-f2b2-46eb-a31f-3557d8cffd02" />

    
- 힙에 할당되는 공간이 4워드인 이유
→ 변수를 저장하기 위한 2워드 외에도 참조 카운팅을 위한 공간(1워드), 객체의 타입을 저장하는 공간(1워드)의 추가적인 공간이 필요하다.

**주요 차이점**

- Value semantics vs Reference semantics (값 의미론 vs 참조 의미론)
    - 둘은 단순히 메모리 위치를 넘어 데이터를 어떻게 취급하고 전달하느냐에 대한 철학적 차이를 다룬다.
    - Value semantics: 복사된 데이터는 원본과 독립적이다.
    - Reference semantics: 복사된 데이터는 원본과 동일한 인스턴스를 가리킨다.
- **스택 - 값 타입**
    - **할당:** 스택 포인터를 이동시키는 단순 산술 연산 (O(1)).
    - **해제:** 함수 종료 시 포인터가 돌아오며 즉시 해제.
    - **비용:** 매우 저렴하며 CPU 캐시 효율이 높음.
- **힙 - 참조 타입**
    - **할당:** 사용 가능한 빈 공간을 찾는 검색(Search) 과정과 스레드 간 동기화(Lock) 비용 발생
    - **관리:** 참조 카운트(ARC)를 실시간으로 증감시키는 원자적(Atomic) 연산 비용 추가.
    - **비용:** 스택에 비해 상대적으로 비싸며 메모리 파편화 관리 필요.
- 구조체와 클래스
    - 구조체는 기본적으로 상태 공유를 의도하지 않는다. (고로 멀티스레드 환경에서도 안전)
    - 클래스는 힙에 할당되므로 더 큰 비용을 가진다.
    - 따라서 특별하게 필요하지 않다면 구조체를 사용하는 것이 더 효율적일 수 있다.

### Reference Counting

- Swift에서 참조가 추가되거나 제거될 때, 참조 카운트를 내부적으로 같이 저장해 관리한다.
따라서 해당 작업은 매우 빈번히 일어난다.
- 간접 참조로 인한 카운트를 증가하거나 감소 연산도 고려해야 한다.
- 여러 스레드의 모든 힙 할당 인스턴스에서 해당 값에 접근하기 때문에 thread-safety 해야 한다.

**RC 기본 동작**

- retain: 참조를 얻었을 경우, 참조 카운트를 원자적으로 증가시키는 호출
- release: 참조가 제거되었을 경우, 참조 카운트를 원자적으로 감소시키는 호출
- 카운트 값이 0이되면 더 이상 필요 없는 객체라 판단하고, 힙을 lock한 후 메모리를 해제한다.

**값 타입인 구조체라면?**

- 순수한 값 기반의 구조체는 참조가 없기 때문에 참조 카운팅 오버헤드가 없다. → 클래스보다 오버헤드가 적다.

<img width="1280" height="782" alt="image" src="https://github.com/user-attachments/assets/ada51dee-b87c-4cd2-8ba3-8634b0cc7a33" />


- 그러나 내부에 힙을 사용하는 프로퍼티 (Class, String 등)가 있으면, 참조 카운팅이 필요하다.
    - 해당 타입에 대한 복사가 일어날 경우, 내부적으로 각각 힙 할당 프로퍼티에 대한 retain, release 연산이 수행된다.
    - 따라서 이 경우 클래스에 비해 두 배의 참조 오버헤드가 발생한다.

### Method Dispatch

**Static Dispatch**

- 컴파일러가 코드를 빌드할 때, **어떤 함수가 실행될지 100% 알고 있는 상태**.
- 따라서 컴파일 타임에 구현이 결정되며, `@inline`같은 것을 사용해 최적화가 가능하다.
    - **인라이닝**
        - 함수 호출 과정 없이 함수의 본문을 호출부로 바로 복사해 넣을 수 있어 호출 오버헤드가 **0이 된다.**
- **동작 방식:** 컴파일 타임에 함수 호출 부분에 실제 함수의 메모리 주소를 직접 넣는다.
- **예측 가능성:** CPU가 다음에 실행할 코드를 미리 알 수 있어 파이프라인 효율이 극대화된다.

**Dynamic Dispatch**

- 컴파일 타임이 아닌 런타임에서 메서드의 구현이 결정된다.
- 참조 카운팅 및 힙 할당과 같은 스레드 동기화 오버헤드는 발생하지 않지만,
컴파일 타임에 결정되지 않기 때문에 최적화가 힘들다.
- 다형성이 필요한 경우 사용된다.
- 컴파일러는 V-Table(Virtual Method Table)을 확인해 객체의 타입을 확인한 뒤 해당 주소로 점프한다.
- **비용**
    - **참조 확인:** V-Table을 보고 주소를 찾는 과정에서 메모리 읽기 연산 발생
    - **최적화 방해:** 컴파일러가 어떤 함수가 실행될지 모르기 때문에 **인라이닝이 불가**

| **구분** | **정적 디스패치 (Static)** | **동적 디스패치 (Dynamic)** |
| --- | --- | --- |
| **결정 시점** | 컴파일 타임 | 런타임 |
| **주요 대상** | Struct, Enum, final class | Class (non-final), Protocol |
| **속도** | **매우 빠름** (인라이닝 가능) | **상대적으로 느림** (테이블 참조 필요) |
| **유연성** | 낮음 (상속 불가능) | 높음 (다형성 활용 가능) |

**메서드 디스패치 관련 최적화 방안**

- 기본적으로 Struct / enum 등 값 타입을 적극 활용한다.
- Class를 사용할 경우 더 이상 확장이 필요없는 시점에는 반드시 `final`로 선언한다.
- 외부에서 참조될 일이 없는 모든 타입이나 변수에는 `private`을 붙인다.

### Protocol types

- 참조를 가지지 않거나 상속을 하지 않아도 **프로토콜**을 통해 다형성을 가질 수 있다.
- 그렇다면 어떻게 올바르게 method dispatch가 가능할까?

**상속 관계가 없을 때 method dispatch 방법**

- Protocol Witness Table
    - 클래스의 V-Table과 유사하지만, **상속 관계가 없는 서로 다른 타입(구조체, 클래스 등)들이 동일한 프로토콜을 채택했을 때** 다형성을 구현하기 위해 Swift가 사용하는 핵심 메커니즘
    - 특정 타입이 해당 프로토콜의 메서드들을 각각 어디에 구현해 놓았는지 그 **메모리 주소를 저장하는 리스트**

<img width="1280" height="791" alt="image" src="https://github.com/user-attachments/assets/b00872c0-9c7a-4c91-891e-a4ebaf9e6442" />


**그렇다면 어떻게 테이블 엔트리를 찾을까? (어떻게 알맞는 프로토콜 메서드 구현을 찾아 실행할까?)**
→ **The Existential Container** 사용

**The Existential Container**

- Swift에서 서로 다른 크기를 가진 값 타입(구조체 등)들을 동일한 프로토콜 타입으로 관리하기 위해 사용하는 특수한 메모리 레이아웃
- **5워드 구조**
    - **Value Buffer (3 Words):** 실제 데이터를 담는 공간.
        - 데이터가 3워드 이하(예: `Point(x, y)`)면 이 안에 직접 저장 (**Inline**)
        - 데이터가 3워드를 초과(예: `Line(x1, y1, x2, y2)`)하면 **힙 할당**을 하고, 그 주소값만 컨테이너에 담음. (Indirect)
            
            <img width="1280" height="767" alt="image" src="https://github.com/user-attachments/assets/70766bfd-a816-4324-900a-5cc1acedaf26" />

            
    - **VWT (Value Witness Table) (1 Word)**
        - 해당 타입의 할당, 복사, 해제 등 생명주기를 관리하는 함수 주소 테이블로, 4개의 엔트리를 가진다.
        
        <img width="1280" height="791" alt="image" src="https://github.com/user-attachments/assets/205c1ac6-1c92-4fc7-9d4a-190b8a5bade0" />

        
        - `allocate`: 프로토콜 타입 변수의 생명주기가 시작될 때, 해당 타입의 VWT 내부에 저장된 allocate 메서드 주소로 점프한다. (실행)
        따라서 힙에 메모리가 할당되고, 메모리 주소가 Existential Container의 value buffer에 저장된다.
        - `copy`: 변수가 할당될 때, 그 값은 할당된 힙 메모리에 복사될 것이고,
        바로 저장될 수 있는 작은 값의 경우 컨테이너의 value buffer에 저장될 것이다.
        - `destruct & deallocate`: 변수의 생명주기가 끝났을 경우, destruct 엔트리를 호출해 관련된 참조 카운트가 있다면 정리하고, deallocate를 호출해 할당한 메모리를 반납한다. (작은 값의 경우 해당 과정 없이 스택 포인터만 조절하면 될 것이다.)
    
    - **PWT (Protocol Witness Table) (1 Word)**
        - 해당 타입이 프로토콜의 메서드를 어디에 구현했는지 가리키는 메서드 주소 테이블로, 힙에 할당되며 해당 메모리 포인터가 컨테이너 내부에 저장된다.
        - Swift는 지역 변수가 존재할 때 해당 변수의 Existential Container 내부에 저장된 PWT 주소를 통해 테이블을 참조하여 올바른 프로토콜 메서드의 구현부를 실행한다.
        - **`projectBuffer`** 메서드
            
            <img width="1280" height="705" alt="image" src="https://github.com/user-attachments/assets/1c21e034-451d-4be8-a950-b64e2941d686" />

            
            - **VWT** 안에 포함된 함수 중 하나로, Existential Container에 담긴 **데이터의 실제 시작 주소를 찾아준다.**
            컴파일러 입장에서는 데이터가 컨테이너 내부에 있는지, 아니면 힙에 있는지 매번 분기 처리를 해야 하는데, 이를 추상화해서 어디에 있든 진짜 데이터 주소를 가져오는 도구이다.

**요약**

1. 핵심 구조: Existential Container (5-Word)

Swift는 서로 다른 크기의 타입을 공통된 프로토콜 타입으로 다루기 위해 **스택**에 5워드 크기의 컨테이너를 생성한다.

- **Value Buffer (3 Words):** 실제 데이터 저장소. (3워드 초과 시 힙 할당 후 포인터 저장)
- **VWT 주소 (1 Word):** 메모리 관리(생명주기) 설명서 주소.
- **PWT 주소 (1 Word):** 프로토콜 메서드 구현부 주소.

---

2. 메서드 실행의 3단계 흐름

- **Step 1. 데이터 주소 파악 (`projectBuffer`)**

CPU는 **VWT** 내의 `projectBuffer`로 점프하여 데이터가 컨테이너 내부에 있는지(Inline), 힙에 있는지(Indirect) 확인한 뒤 **실제 데이터의 시작 주소**를 반환받는다.

- **Step 2. 구현부 주소 파악 (PWT 참조)**

컴파일러는 컨테이너에 저장된 **PWT**주소를 참조한다. PWT는 해당 타입이 프로토콜의 기능을 어떻게 구현했는지 기록한 테이블로, 여기서 실행할 메서드의 정확한 **메모리 주소**를 찾을 수 있다.

- **Step 3. 최종 호출 (Indirect Jump)**

계산된 데이터 주소(`self`)를 들고, PWT에서 찾은 메서드 주소로 **최종 점프**하여 실행하여 동적 디스패치를 구현한다.

### COW의 필요성

- 문제 상황: 큰 구조체의 무분별한 힙 할당과 복사
    - `Line`처럼 3워드를 초과하는 구조체를 프로토콜 타입으로 사용하면 큰 오버헤드가 발생할 수 있다.
    - **매 할당 시 힙 할당:** 변수를 복사할 때마다(`let b = a`) VWT의 `copy`가 실행되면서 매번 새로운 힙 공간을 만들고 데이터를 복사한다.
    - **성능 저하:** 힙 할당은 스택 할당보다 훨씬 느리며, 복사할 데이터가 클수록 CPU 부하가 커진다.
    - **값 타입의 역설:** 성능을 위해 구조체를 썼는데, 정작 클래스보다 더 많은 비용을 지불하게 되는 상황이 벌어진다.
- 따라서 ‘쓰기 발생 시 복사’ 매커니즘인 COW를 활용할 수 있다.
- **해결 원리: Indirect Storage 도입**
    - **데이터의 클래스화:** 실제 데이터(예: 4개의 Double 값)를 직접 구조체에 두지 않고, 이를 관리하는 별도의 `Class` 타입으로 묶음.
    - **구조체의 경량화:** `Struct` 타입은 실제 데이터 대신 이*클래스 인스턴스의 참조만을 저장 프로퍼티로 가짐.
        - 이로 인해 구조체는 더 이상 4워드가 아닌, **1워드(8바이트)의 참조 변수**만 가지게 됨.
- **작동 방식 및 이점**
    - **Existential Container 최적화:** 구조체 크기가 1워드로 줄어들면서 컨테이너의 **Value Buffer내에 Inline 저장**이 가능해짐. 결과적으로 프로토콜 변수를 생성할 때 발생하는 추가적인 힙 할당이 사라짐.
    - **복사 비용 감소:** 값 복사가 일어날 때 데이터 전체를 복사하는 대신 참조 카운트만 증가시키므로 매우 빠름.
    - **지연 복사 (Copy-on-Write):** 데이터를 읽기만 할 때는 여러 구조체가 하나의 클래스 인스턴스를 공유함.
        - 데이터를 수정(Write)해야 할 때만 참조 카운트를 확인하여, 공유 중(2 이상)일 경우에만 실제 데이터를 복사함.

다음 메서드 실행이 확정된다.

- 위와 같이 호출 컨텍스트 당 한 개의 타입만 존재할 경우, 동적 디스패치가 필요 없으므로 Existential Container 할당이 일어나지 않는다. 대신 Point 타입의 PWT, VWT를 넘겨준다.
- 따라서 value buffer(3words)는 Stack에 저장한다. 이때도 동일하게 3워드에 들어가는 값은 그대로 저장하고, 3워드를 초과할 경우 힙에 메모리를 할당하여 주소를 저장한다.

**제네릭 코드가 프로토콜 타입보다 효율적인 이유**

- 제네릭 코드의 Specialization
    - 프로토콜 타입은 런타임에 Existential Container를 만들고 PWT를 뒤지지만, 제네릭은 컴파일 타임에 **실제 타입별로 함수를 복사해서 새로 만든다.**
    - **상황:** `func draw<T: Drawable>(item: T)`라는 제네릭 함수가 있고, 이를 `Point`와 `Line`으로 각각 호출한다고 가정할 수 있다.
    - **컴파일러의 동작:** 1. `draw(item: Point)`라는 전용 함수를 하나 찍어낸다.
    2. `draw(item: Line)`라는 전용 함수를 하나 더 찍어낸다.
    - **결과:** 이제 이 함수 안에서 `item.draw()`를 호출할 때, 컴파일러는 이 `item`이 100% `Point`인 것을 알고 있으므로 PWT를 뒤질 필요 없이 **`Point`의 `draw` 메서드 주소로 바로 점프한다.**
- **효율적인 이유**
    - **인라이닝 가능:** 함수 호출부 자체가 실제 코드로 대체될 수 있어, 점프 비용조차 0으로 만들 수 있음
    - **메모리 최적화:** 5워드 크기의 고정된 Existential Container를 사용하지 않고, 각 타입의 **실제 크기만큼 스택 메모리를 할당**하므로 힙 할당 오버헤드가 발생하지 않음
- **trade-off**
    - **코드 비대화:** 타입별로 함수를 복사하기 때문에 바이너리 크기가 커질 수 있지만 내부 최적화를 통해 더 가벼워질 수 있음

**Specialization은 언제 발생하는가?**

- 컴파일 타임에 타입을 확정할 수 있을때

```swift
func draw<T: Drawable>(_ item: T) { ... }

let p = Point()
draw(p) // 이 호출부에서 컴파일러는 T가 Point임을 알고 'Point용 draw'를 찍어냅니다.
```

- 정의와 호출부가 같은 모듈 내에 있을 때
    - Swift 컴파일러는 기본적으로 **모듈 단위**로 최적화
    - **성공:** `draw` 함수 정의와 이를 호출하는 코드가 **같은 앱 타겟**이나 **같은 프레임워크** 안에 있다면 특수화가 잘 일어남
    - **실패:** 만약 `draw` 함수 정의는 외부 라이브러리(A 모듈)에 있고, 호출은 내 앱(B 모듈)에서 한다면? 컴파일러는 라이브러리 내부를 마음대로 수정할 수 없으므로 특수화를 포기하고  더 느린 프로토콜 타입 방식(VWT/PWT)을 사용한다.

**통모듈 최적화 (Whole Module Optimization, WMO)**

- Xcode 프로젝트 설정에서 **Compilation Mode**를 "Whole Module"로 설정하면(Release 빌드 기본값), 컴파일러가 모듈 전체를 한꺼번에 분석한다.
- 이때 함수 호출 관계를 더 깊이 파악할 수 있게 되어, 특수화가 일어날 확률이 훨씬 높아진다.
만약 정의와 호출부가 다른 모듈에 있을 경우, 라이브러리 제작자가 함수 위에 **`@inlinable`** 키워드를 붙여줘야 함수 설계도를 호출부(App)에 노출시켜서 앱 컴파일 시점에 특수화가 일어날 수 있다.

## 5. 의문 / 추가 탐구 포인트

- **PWT, VWT는 어디에 저장될까?**
    - PWT는 프로토콜을 채택하는 타입마다 메소드를 어떻게 구현했는지를 저장하는 정적 메타 데이터로, 
    실행 중에 바뀌지 않고, 동일한 타입·프로토콜 조합에 대해 하나만 있으면 되므로, 일반적으로 코드/데이터의 정적 영역(읽기 전용 메타데이터 영역)에 놓인다.
    - 그래서 “PWT는 힙에 생긴다”라고 말하면 엄밀히는 틀리고, PWT는 정적으로 한 번 생성되어, 앱 로드 시 메모리에 로드되어 런타임에 공유된다고 한다.
    
- **Value buffer에 들어갈 수 있는 기준이 3워드인 이유가 뭘까?**
    - 결론: 3워드 기준은 대부분의 간단한 struct를 커버하면서 메모리 효율성을 유지하기 위한 Swift ABI의 선택임
    - 대부분 일상적인 데이터 구조는 보통 3워드 안에 담기고, 1-2워드로 작게 잡을 경우 웬만한 구조체들도 힙에 할당하게 되므로 성능이 떨어진다.
    - 4워드 이상으로 잡을 경우 스택 공간이 낭비될 여지가 있다. 따라서 3이 가장 적절했던 것.
