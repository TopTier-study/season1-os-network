### IPv6, IPv4

| 구분          | IPv4                                         | IPv6                                                         |
|-------------|----------------------------------------------|--------------------------------------------------------------|
| 주소 길이       | 32비트                                         | 128비트                                                        |
| 표시 방법       | 8비트씩 4부분 10진수 표시<br>ex) 203.252.53.55        | 16비트 8부분 16진수로 표시<br>ex) 2022:0221:ABCD:DCBA:0000:0000:FFFF:4002 |
| 주소 개수       | 약 43억개                                       | 2^128개 (약 43억 * 43억 * 43억 * 43억)                             |
| 주소 할당 방식    | A, B, C, D 등의 클래스 단위 비순차 할당                  | 네트워크 규모, 단말기 수에 따라 순차 할당                                     |
| 브로드캐스트 주소   | 있음                                           | 없음<br>(로컬 범위 내에서 모든 노드에 대한 멀티캐스트 주소 사용)                      |
| 헤더 크기       | 가변                                           | 고정                                                           |
| QoS 제공      | 미흡                                           | 제공                                                           |
| 보안          | IPSec 프로토콜 별도 설치                             | IPSec 자체 지원                                                  |
| 서비스 품질      | 제한적 품질 보장 (Type of Service에 의한 서비스 품질 일부 지원) | 확장된 품질 보장 (트래픽 클래스, 플로우 레이블에 의한 서비스 품질 지원)                   |
| Plug & Play | 불가 (DHCP 이용 시 가능)                            | 가능                                                           |

**IPv6**이 IPv4보다 `TCP 연결 설정 시간`, `왕복 지연 시간`에서 더 나은 성능을 가진다.
(**실제 프로토콜 자체의 속도 차이 X, NAT 제거와 최신 네트워크 인프라 최적화로 인해 실제 경로 latency가 줄어들기 때문**)

- 패킷을 단편화하지 않으면서 효율적인 라우팅 가능
- 지연에 민감한 패킷을 구분하는 QoS
- NAT를 없앰으로써 주소 공간을 32비트에서 128비트로 확장 (직접 주소 가능)
  - **IPv4**
    - 주소 부족
    - 내부 IP -> NAT -> 공인 IP -> 인터넷
    - 주소 변환 작업, 상태 테이블 관리, 패킷 검사로 인한 추가 latency 발생
  - **IPv6**
    - 단말이 직접 공인 주소를 가짐.
    - 단말 -> 인터넷
    - 중간 단계가 줄어들면서 latency 감소
    - wwdc 측정에서 IPv6가 더 빠르게 나온 이유
      1. NAT traversal X
      2. 네트워크 장비 최적화
         - 최신 통신사 인프라는 IPv6 중심
         - IPv4는 호환용 레거시
- 네트워크 레이어 보안 내장(IPSec)
- 손쉬운 네트워크 관리를 위한 무상태 주소 자동 구성
- 처리 오버헤드가 줄어든 개선된 헤더 구조

-> 서버&서비스가 네이티브 IPv6을 지원하면 **실제 사용자 체감 성능 향상**으로 이어질 수 있다.
(URLSession은 자동으로 IPv6 처리)

> [IPv4와 IPv6의 차이점 | 주니퍼 네트웍스 KR](https://www.juniper.net/kr/ko/research-topics/what-is-ipv4-vs-ipv6.html)

### 성능과 복원력을 높이는 기술들
#### 1) Explicit Congestion Notification (ECN)
: 네트워크가 혼잡해질 때 패킷을 버리지 않고 혼잡 시작 알림 비트를 설정하는 기술

- **기존 TCP 혼잡 감지 방법**
  - `패킷 손실 = 혼잡 신호`
    1. 네트워크 혼잡 시작
    2. 라우터 버퍼가 가득 차며 패킷을 버림
    3. 송신자가 혼잡 인지
    4. 속도 줄임
  - 이미 데이터 손실 발생 (비싼 패킷 손실)
  - 재전송 필요
  - latency 증가
  - 네트워크 낭비
- **ECN 동작 방식**
  - `패킷 손실 없이 혼잡 감지`
    1. 네트워크 혼잡 시작
    2. 패킷을 버리지 않고 혼잡 표시만 함
       - 혼잡 표시법: 혼잡해진 라우터에서 IP 데이터그램 헤더에 있는 ECN 비트 설정
    3. 수신 호스트의 TCP가 수신 데이터그램을 통해 ECN 혼잡 알림 비트 수신
    4. 수신 호스트의 TCP는 수신자-송신자 TCP ACK 세그먼트의 ECE(Explicit Congestion Notification Echo) 비트 설정
    5. TCP 송신자가 속도 줄임
    6. 이후 송신자는 다음 전송되는 TCP 수신자 세그먼트 헤더에 CWR(Congestion Window Reduced) 비트 1로 설정

- **패킷 손실과 재전송을 줄여** 성능을 높이는 기술
- iOS / macOS에서는 ECN 기본 활성화
- 서버에서 이를 지원하는지 확인해야 함.

> [\[Network\] 명시적 혼잡 알림\(ECN\)과 지연 기반 혼잡 제어 개념 및 특징](https://howudong.tistory.com/405#google_vignette)

#### 2) Multipath TCP (MPTCP)
: TCP 프로토콜을 확장하여 단말과 TCP 서버 간에 다수의 TCP 경로를 구성하고 다수의 경로로 동시에 데이터를 송수신하는 방법

- 전통적 TCP: 연결이 끊긴 후 다시 연결해야 함.
- 멀티패스 TCP: 연결이 끊기지 않음. ( = 복원력 ↑)

- TCP / UDP와 같은 4계층(전송 계층) 프로토콜
- Wi-Fi에서 셀룰러로 넘어갈 때와 같이 **네트워크 인터페이스가 바뀌어도 연결을 끊지 않고 이어갈 수 있음.** (2개 이상의 인터넷 연결 후 사용 가능)
  - 연결을 끊지 않고 경로만 바꾸기
- 더 높은 throughput
- **성능 + 복원력(resilience)**에 유리

> [\[네트워크\] MPTCT\(Multipath TCP\)란? - What is MPTCP?](https://wodonggun.github.io/network/What-is-MPTCP.html)

#### 3) TCP Fast Open (TFO)
: TCP 연결 설정 과정에서 초기 데이터를 함께 보내 왕복 지연을 줄일 수 있는 기술

- **기존 TCP 연결: 3-way handshake 과정을 거침.**
  - 클라 - 서버 간 연결이 설정되기까지 최소한 세 개의 패킷이 교환됨. ( = **초기 latency 발생**)
    1. 클라 -> 서버:  SYN 패킷 전송 (연결 요청)
    2. 서버 -> 클라: SYN + ACK 패킷 응답 (연결 승인)
    3. 클라 -> 서버: ACK 패킷 전송 (연결 완료)
  - 이 과정이 완료될 때까지 데이터 전송 불가
  - 웹 페이지 로딩, API 요청, 모바일 앱 데이터 요청 등에서 **체감 속도 느려질 수 있음**
- **TCP Fast Open 동작 방식**
  1. 클라 -> 서버: SYN + 데이터 포함
     - 클라이언트는 SYN 패킷을 보내면서 **데이터 함께 전송**
     - 이 데이터는 **TFO 쿠키**를 이용하여 서버에서 빠르게 인증됨.
  2. 서버 -> 클라: SYN-ACK + 데이터 처리
     - 서버는 SYN-ACK 응답과 동시에 데이터 처리 및 즉시 응답
  3. 클라 -> 서버: ACK + 데이터 요청 지속
     - 추가적인 데이터 필요 시 기존 연결을 유지하면서 데이터 전송 가능

- 연결 수립 자체에 드는 latency를 줄임. (웹 페이지 로딩, API 요청 속도가 최대 40%까지 향상될 수 있음)
- 네트워크 효율성 증가
  - 불필요한 handshake 과정이 생략되면서 대역폭 사용량 최적화
  - 데이터 센터 및 클라우드 환경에서 트래픽 처리량 증가 -> 비용 절감 효과
- 모바일 및 무선 네트워크에서 효과적으로 동작
  - 모바일 네트워크(LTE, 5G, Wi-Fi)에서는 빈번한 연결 해제 및 재연결이 발생함.
  - TFO 사용 시 네트워크가 재연결될 때도 데이터 전송 즉시 시작 가능
  - 온라인 게임, 실시간 메시징 등의 반응 속도 향상
- 사용자 경험(UX) 개선

> [최신 TCP 기술: TCP Fast Open \(TFO\)](https://shimdh.tistory.com/624)

#### 4) QUIC
: (wwdc18 당시 기준) 완성되지 않은 차세대 전송 프로토콜
(현재 2026 기준) IETF에서 표준화 완료된 프로토콜 (RFC 9000)

- HTTP/3 기반 프로토콜로 확정됨.
  - 대부분의 대형 서비스(Google 유튜브, 검색, Meta 페이스북, 인스타그램, Cloudflare, Amazon 일부 서비스)에서 사용 중
  - `왜 대부분일까?`
    1. 서버가 HTTP/3, QUIC를 지원해야 하는데 아직 모든 서버가 지원하지는 않음.
    2. 일부 방화벽 / 기업망에서 UDP를 차단하는데 QUIC는 UDP 기반이기 때문에 영향을 받음.
    3. fallback 구조
       - HTTP/3 (QUIC) 시도 -> 안되면 HTTP/2 (TCP)로 fallback
- TCP를 대체 후보
- 기존 TCP의 문제 완화
  1. **HOL Blocking 문제**
     - QUIC에서는 하나의 커넥션에서 패킷을 **스트림**이라는 논리적인 단위로 분리하여 패킷 전송
     - 동일하게 패킷 순서를 보장하나 패킷 손실에 의한 HOL delay는 **한 스트림으로 제한**
  2. **패킷 손실 시 재전송 왜곡 문제**
     - 신뢰성 연결을 보장하기 위하여 수신자가 패킷을 제대로 전송받지 않은 경우 송신자는 동일 패킷을 재전송하여 손실을 복구해야 함.
     - 송신자의 입장에서 ‘패킷이 전달되지 않았다’는 판단은 **Timeout**으로 결정
     - 클라이언트마다 서버로 통신하는 라운드트립 시간(RTT)이 모두 다르기 때문에 Timeout 시간도 다르게 설정해야 함.
     - **TCP**: SampleRTT 사용 -> 왕복 시간 예측
       - **패킷 재전송 시 동일한 시퀀스 번호**로 주기 때문에 서버가 보내준 ACK가 어떤 요청에 대한 것인지 판단할 수 없는 문제 발생 (**retransmission ambiguity** = 실제 값에 비해 SampleRTT가 길게 / 짧게 왜곡되며 문제 발생)
       ![](moonazn/%E1%84%89%E1%85%B3%E1%84%8F%E1%85%B3%E1%84%85%E1%85%B5%E1%86%AB%E1%84%89%E1%85%A3%E1%86%BA%202026-03-30%20%E1%84%8B%E1%85%A9%E1%84%92%E1%85%AE%203.39.53.png)
       > https://tcpcc.systemsapproach.org/algorithm.html
     - **QUIC**: **재전송 패킷도 새로운 번호 부여** -> 모호성 문제 해결
       - 서버에서 요청을 수행하는 데에 걸린 시간을 첨부하여 응답 -> 클라이언트의 정교한 RTT 계산 도움
       - TCP/IP보다 정확한 RTT 계산 방식을 통해 불필요한 패킷 재전송 방지 가능

### DNS TTL과 성능 비용
많은 서비스가 장애 전환을 빠르게 하기 위하여 **DNS TTL을 짧게 잡음.**

-> 일상적인 상황에서도 다음과 같은 문제가 생긴다.
- 캐시가 자주 만료됨.
- 매 요청마다 DNS 재조회 발생
- 그때마다 **추가 RTT(latency)** 발생

> 즉 드문 장애 상황을 위해 평소의 모든 요청에서 추가 round trip latency를 내는 셈이다.

#### Apple의 최적화 방안
**만료된 DNS 캐시를 먼저 활용 & 동시에 새 조회를 돌림.**
(Apple은 Happy Eyeballs 알고리즘과 함께 사용 -> 느린 DNS + 느린 경로 문제 동시 완화)

- 동작 방식
  1. 캐시에 만료된 값이 있어도 일단 사용하여 즉시 연결 시도
  2. 동시에 DNS 서버에 새 요청 수행
  3. 결과가 같으면 그대로 사용
  4. 결과가 다르면 비동기로 새로운 주소 전달 & 추가 연결 시도
- latency 줄임. (빠른 연결 시작)
- 가용성 유지 (최신 주소 확보)
- **Happy Eyeballs**: 여러 경로(대표적으로 IPv4, IPv6)를 동시에 시도하고 가장 빠른 연결을 사용하는 알고리즘

-> 가용성과 성능 사이의 트레이드오프 사례

- **SCNetworkReachability**: 어플리케이션이 시스템의 현재 네트워크 상태와 타겟 호스트에게의 접근 가능성을 결정하도록 해줌.
  - 어플리케이션으로부터 네트워크 스택에 전달되는 데이터 패킷이 로컬 디바이스를 떠날 수 있을 때 기기에 접근 가능(reachable)하다고 여겨진다.
- iOS 12부터는 Network.framework의 NWPathMonitor 클래스를 사용해서 네트워크 연결 감지 가능

개발자들은 **SCNetworkReachability**을 다음에 수행하는 네트워크 작업의 성공 여부에 대한 사전 점검 용도로 사용한다.
-> **부정적!**

#### 이유
현재 연결이 가능하더라도, *실제 요청을 보내는 시점에는 상황이 바뀔 수 있기 때문에* Reachability는 미래를 예측할 수 없다.

#### 제안 - waitsForConnectivity 옵션 사용하기
: 연결을 원할 시 시스템에 이를 알리고, 가능해질 때까지 기다리게 하는 방식

```swift
lazy var session: URLSession = { [weak self] in
    let config = URLSessionConfiguration.default

    config.waitsForConnectivity = true
  
    let session = URLSession(configuration: config, delegate: self, delegateQueue: OperationQueue.main)
    return session
}()  
 ```
- 이 session을 사용하여 생성되는 Task는 전부 네트워크 유실 시 연결이 될 때까지 대기할 수 있음.

## Part 2.
### 1) 지연 시간 감소
latency = 실제 앱이 느려지는 가장 중요한 원인 중 하나

- latency = `DNS 조회 시간` + `TCP 연결 설정 시간` + `TLS 연결 설정 시간` + `서버 응답 대기 시간` + `HTTP/1.1 구조 때문에 뒤 요청이 막히는 대기 시간 (HOL Blocking)`
- 즉 **요청이 실제로 처리되기 전까지 소모되는 전체 시간 비용** 의미

#### HTTP/1.1의 문제
같은 서버에서 여러 리소스를 받아야 할 때 HTTP/1.1에서는
1) 새 연결을 여러 개 열게 되거나
2) 하나의 연결에서 순차 처리가 일어남.

- 이때 발생하는 문제
  1. **연결을 여러 번 여는 비용**: 매번 DNS, TCP, TLS 비용이 반복됨.
  2. **Head-of-Line Blocking**: 한 요청의 응답이 끝나기 전까지 뒤 요청이 기다려야 함.
- -> 앱이 응답을 기다리는 유휴 시간이 커짐.

#### HTTP/2의 장점
HTTP/2는 **단일 연결 위에서 여러 스트림을 다중화**할 수 있음.
( = 병렬 응답을 받을 수 있음.)

- HTTP/1.1에 비해
  - 연결 수 ↓
  - HOL Blocking 문제를 HTTP 계층에서 완화할 수 있음.
  - 네트워크 대기 시간 ↓
- URLSession을 사용하는 앱은 클라이언트 코드 변경 없이도 서버가 HTTP/2를 활성화할 시 이 이점을 얻을 수 있음.

#### HTTP/2 Connection Coalescing
iOS 12와 macOS Mojave에서 HTTP/2 Connection Coalescing이 추가됨.
- **Connection Coalescing**: 같은 엔드포인트로 판단되는 경우 새 연결을 열지 않고 기존 연결을 **재사용** -> 사용자에게 반응성 ↑
- 예시) 서로 다른 서브도메인이라도 인증서가 커버하고 같은 IP 주소로 연결된다면 기존 연결을 재사용하는 것이 더 안전할 수 있음.
- 즉 **새 연결 생성 비용을 줄여 지연 시간을 줄이는 최적화** 방법

#### URLSession 객체 생성 남발의 위험
모든 URLSession 객체는 자신만의 connection pool을 가짐.

1. URLSession을 여러 개 만들면 연결 재사용의 이점을 가져가기 어려움.
2. URLSession 자체의 생성 비용과 메모리 비용이 적지 않음.

-> **필요 이상으로 세션 객체를 많이 만들지 말 것, 적은 수의 세션을 재사용할 것**

### 2) 처리량 극대화
- 처리량 = ‘더 많은 데이터를 더 효율적으로 보내는 것’
- 처리량 줄이기 = **전송하는 바이트 수를 줄이기**
  - Bad👎🏻: `“버터를 많이 넣은 크리미한 토마토 양파 그레이비에 버무린 구운 치킨을 주문할 수 있을까요?”`
  - Good👍🏻: `“버터 치킨을 받을 수 있을까요?”`

#### 쿠키 is not free
- 쿠키는 저장 비용과 조회 비용이 든다.
- 도메인 및 경로 속성과 일치하는 모든 요청에 첨부됨.
- **요청 크기가 빠르게 커질 우려**가 있음.

> **권장**
> - 도메인 / 경로 속성 신중히 설정하기
> - 꼭 필요한 쿠키만 사용하기
> - 필요 없어지는 경우 삭제하기
> - 가능한 한 서버에 상태를 저장하여 클라이언트 쿠키 수 줄이기

`쿠키 = 요청 크기와 성능에 영향을 주는 요소!`

#### HTTP 압축
: 클라이언트와 서버 사이에 전송되는 데이터를 단순히 압축하는 것
-> 대역폭을 보다 효율적으로 활용할 수 있게 된다.

- URLSession이 지원&권장하는 알고리즘 - `Gzip`, `Brotli`
  - Gzip: 널리 지원, 비교적 빠름
  - Brotli: 구조화된 텍스트와 HTML에 적합, 짧은 데이터에서 좋은 압축률을 가짐.
- 압축 = **“ 보내야 할 데이터 양 자체를 줄이는 방식의 최적화 ”**

### 3) 반응성 향상
반응성 = **’사용자에게 중요한 요청이 적절한 우선순위를 가지는가’의 문제**

#### QoS
어떤 큐에서 `task.resume()`을 호출했는지에 따라 작업의 우선순위와 delegate 메시지 전달에 영향을 준다.

- 급하지 않은 작업이라면 백그라운드 QoS 큐에서 시작하도록 하여 더 중요한 CPU 작업과 경쟁하지 않도록 하기

> 네트워크 요청과 CPU 스케줄링은 무관하지 X

#### networkServiceType
> [networkServiceType | Apple Developer Documentation](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/networkservicetype)

: 네트워크 트래픽 자체의 우선순위를 분류할 수 있도록 하는 URLSession 구성 객체의 속성

> “중요한 요청만 더 반응성 있게 처리되도록 표시하라”

#### waitsForConnectivity
: 연결이 안 될 때 무조건 실패시키지 않고 연결이 가능해질 때까지 기다리는 API

### 4) 시스템 자원 활용
#### Background Session
- 대용량 업로드/다운로드 -> 백그라운드 세션 활용하기
  - 시스템이 배터리, CPU, Wi-Fi 등 여러 조건을 고려하여 더 효율적으로 스케줄링할 수 있기 때문
  - 앱 프로세스 중단 or suspend 상태여도 작업을 이어갈 수 있음.

#### 캐싱
- 잘못된 캐시 = 심각한 디스크 I/O + 플래시 스토리지 마모
- 제안
  - 클라이언트: willCacheResponse 사용하기 (어떤 리소스를 캐시할지 제어)
  - 서버: cache-control 헤더 사용하기 (명확한 캐싱 정책 제공)

> 캐시는 무조건 좋은 것이 X, **재사용 가능성이 있는 데이터에만 사용**해야 함.
