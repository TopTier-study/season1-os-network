## 2. 내용 요약
### Network Link Conditioner
네트워크 상태에 따라 앱에 미치는 영향을 확인하기 위해 사용할 수 있는 도구. 실 사용시의 네트워크 환경을 시뮬레이션해 주는 개발자 도구.
- 원리: 네트워크 계층, 전송 계층의 패킷 흐름에 개입하여 네트워크를 훼손.
	- Bandwidth: 한 번에 통과할 수 있는 데이터 양을 제한.
	- Packet Loss: 전송되는 패킷 중 일부를 강제로 버림. (Retransmission 유도)
	- Delay: 패킷이 목적지에 도달하는 시간을 인위적으로 늦춤.
	- DNS Delay: 첫 연결 지연.
- 사용 예시
	- 인터넷 연결 끊김 대응: 인터넷 연결이 완전히 끊겼을 때 앱이 무한히 대기하는 등의 상황이 벌어지지는 않는가.
	- 네트워크 지연에 의한 동시성: Very Bad Network 옵션을 통해 네트워크 요청 중 입력에 대해서 버그가 발생하지는 않는가.
애플은 개발 후에 성능 개선을 하는 대신, 앱 개발 중에 Network Link Conditioner를 적극 사용하기를 권하고 있다. 
### 네트워크 성능 분석 도구
- Wireshark: 네트워크 랜카드를 지나가는 패킷을 시각화하는 도구. 
- tcptrace: 캡처된 패킷 덤프 파일(.pcap)을 분석하는 도구. 전체 네트워크 현황의 통계, 성능 지표를 제공. 
### IPv6
- IPv4
	- 주소 길이: 32비트(약 43억)
	- 형식: 192.16.0.1(10진수)
	- 헤더 크기: 가변(기본 20바이트, 최대 60 바이트)
	- 보안: 선택적
	- NAT 사용: 필수
- IPv6
	- 주소 길이: 128비트
	- 형식: 2001:0db8::...:ff00(16진수, 8개 섹터, 0은 콜론으로 생략 가능)
	- 헤더 크기: 40바이트
	- 보안: 기본 내장
	- NAT 사용: 불필요
NAT: IPv4의 주소 고갈을 해결하기 위해 공유기에 주소를 할당하고, 각 기긱에는 사설 ip를 할당해 정의하는 방식.
IPv6의 TCP 연결이 IPv4보다 우수하다.(L2, L4의 오류 검증을 믿고 체크섬 제거, 고정 길이 헤더의 장점) 많은 통신사들이 IPv6를 지원하는 만큼 앱도 IPv6 환경에서 완벽히 동작해야 한다. 
### ECN(Explicit Congestion Notification)
명시적 혼잡 알림. 기존에는 라우터에 패킷이 많이 몰릴 경우 후순위의 패킷을 그냥 버리고, 이러한 패킷의 유실로 혼잡을 파악했었다. 
ECN은 라우터가 혼잡할 경우, IP헤더에 혼잡 상황을 마킹해 처리하는 방식이다. 수신 측은 다음 ACK에서 이 상황을 송신 측에 전달해 패킷 전송 속도를 조절할 수 있다. 
macOS와 iOS에는 기본적으로 활성화되어있다. 다만 서비스에서 ECN을 지원하는지 확인하라고 한다. 
### 멀티패스 TCP
- 기존 TCP 방식
	- 사용자가 Wi-Fi를 사용하다 끊긴 경우 다시 연결해야 한다.
- 멀티패스 TCP
	- 연결 단위가 아닌 패킷 단위로 라우팅을 결정하기 때문에 연결이 끊어져도 다른 인터페이스로 즉시 전환할 수 있다.
### TCP Fast Open
초기 데이터를 TCP 연결 설정해 포함하여 전송하는 기술.
### QUIC(Quick UDP Internet Connections)
TCP의 단점(초기 연결 지연, 데이터 손실 시 전체 지연 등)을 극복하기 위해 UDP를 기반으로 설계. 보다 빠른 연결 속도와 보안(TLS 인증) 기본 내장이 특징.
### DNS 관련
- 기존 방식의 문제점
	-  DNS에서 받아온 주소의 캐시를 매우 짧게 설정함. 만약 해당 주소의 서버가 문제가 생길 경우 다른 서버로 연결을 이어나가기 위해서임. 하지만 실제로 데이터 센터(서버)가 문제가 생기는 경우는 희박함. 
	- 서버가 문제 없을 경우 매번 DNS 요청을 하는 것은 오버헤드.
- 최적화
	- Happy Eyeballs 알고리즘: 동시다발적인 요청 후 가장 먼저 성공한 것을 채택하는 방식. 
	- 캐시가 존재하는 경우 기본적인 DNS 요청 외에도 즉시 서버에 요청을 수행. 만일 서버에 문제가 생겼었다면 DNS가 새로 제공한 IP로 연결한 것이 더 빠르게 연결될 것. 
### 네트워크 사전 점검
- 기존 방식
	- 네트워크를 사용하기 전에 SCNetworkReachability 도구 등을 사용해 연결 상태를 점검하고, API 요청을 하는 방식을 사용함. 이러한 방식은 TOCTOU 문제를 일으킬 수 있음.
- 대안
	- waitsForConnectivity 옵션 사용: URLSessionConfiguration의 속성을 설정해 실제 네트워크 연결이 가능할 때 자동으로 진행. 
### 보안 변경
- TLS 1.3 적용: 핸드쉐이크 시간 감소 및 구형 알고리즘 삭제로 보안성 향상
- Certificate Transparency: 서버의 진위를 확인하기 위해 인증 기관(CA)의 인증서를 사용했었던 방식에는 인증 기관의 신뢰성에 대한 문제가 생김. 이에 인증 기관이 인증서를 발급할 때는 CT Log(공개된 장부)에 기록하도록 함. iOS 앱은 CT규격을 지키지 않은 서버에 대해 클라이언트에서 거부하도록 함. 
### Bonjour 적합성 테스트
하드웨어 장치가 Bonjour를 올바르게 구현하는지 확인할 수 있는 도구. Apple 생태계 신뢰성을 위해 테스트를 통과해야 함.
### BSD 소켓의 한계
C언어 기반의 BSD 소켓은 인터넷 네트워킹의 근간이었으나 무선 통신 환경에서는 Wi-Fi, 셀룰러를 오가는 환경에서 복잡한 네트워크 전환이나 전력 관리를 해주지 못함. 따라서 연결이 끊기면 개발자가 처음부터 끝까지 예외 처리를 다 해줘야 했음.
이에 등장한 것이 URLSession, Network.framework. 커스텀 프로토콜 통신 등이 필요한 경우에도 Network 프레임워크를 사용 권고.
### HTTP/2
- HTTP/1.1의 문제점
	- 여러번의 요청에 대해 매번 새로운 세션을 개설해야 함. DNS 조회, Handshake, TLS가 매번 발생. 
	- Head of Line Blocking: 단일 연결로 모든 요청을 수행해 위 문제를 해결하고자 한다면 응답이 올 때까지 다음 요청이 출발하지 못하는 현상 발생. 
- HTTP/2
	- 단일 연결 안에서 데이터를 여러 개의 Frame으로 쪼개 병렬로 주고받음. 여러 요청 역시 병렬로 처리할 수 있음.
	- 결과적으로 네트워크 유휴 시간 감소. 
#### Connection Coalescing(연결 병합)
도메인이 용도에 따라 서브 도메인으로 나뉘어 있는 경우가 많음. HTTP/2가 단일 연결을 사용함에도 도메인 이름이 다르면 다른 서버로 취급하여 연결 작업을 다시 해야 함.
iOS는 아래 조건을 만족한 경우 서브 도메인에 접근할 때 새로 연결을 하지 않고 기존 연결을 사용함.
- 보안 인증서가 와일드카드 인증서라 서브 도메인을 커버하는가.
- 두 서브 도메인이 실제로 가리키는 도착지 IP 주소가 같은가.
이러한 연결 이점은 동일한 URLSession 객체를 사용하여 작업을 생성할 때만 적용. 또한 URLSession 객체는 생성 비용도 높기 때문에 객체 수를 최소화해야 함. 
#### 처리량 극대화
- 쿠키
	- 앱이 서버와 통신할 때, 쿠키는 한 번 발급받으면 조건이 일치하는 모든 네트워크 요청에 자동으로 통째로 첨부됨. 개발자가 신경쓰지 않으면 불필요한 쿠키가 계속 누적됨. 
	- 쿠키의 domain과 path 속성을 아주 좁고 엄격하게 설정하여, 정말 해당 쿠키가 필요한 API 엔드포인트에만 날아가도록 제한해야 함. 
	- 만료되거나 필요 없는 쿠키는 클라이언트에서 즉시 삭제. 
	- 사용자의 상태 정보는 가급적 서버에 저장, 쿠키는 짧은 세션 ID정도만 남겨서 크기를 최소화.
- 헤더 압축
	- HTTP/1.1은 헤더 크기가 크지만 HTTP/2는 HPACK이라는 헤더 압축 알고리즘을 기본으로 타재하여 기본적인 헤더와 쿠키 크기가 작음. 
- HTTP 콘텐츠 압축
	- 데이터 본문 크기를 압축하는 기술. URLSession은 이 압축 해제 작업을 기본 지원. 
	- Gzip, Brotli 알고리즘을 지원함. 
### QoS
URLSession은 QoS를 물려받기 때문에 네트워크 작업의 우선 순위를 매겨 UX를 개선할 수 있음.
### responsiveData
QoS를 이용한 방법이 CPU에서 우선순위를 정했다면, 네트워크 망 자체에서의 우선순위를 정하는 방법. 
### waitsForConnectivity
통신이 끊겼을 때 시스템이 알아서 대기하도록 waitsForConnectivity = true로 설정하는 것 뿐만 아니라 urlSession(:taskIsWaitingForConnectivity:) 메서드를 활용해 연결되지 않는 경우 동작을 구현. 
### 백그라운드 세션
큰 용량의 파일에 대해 URLSession을 사용할 경우, 앱이 백그라운드로 내려가 OS가 앱을 Suspend시키면 다운로드도 중단됨.
백그라운드 세션을 만들면 앱이 종료되어도 별도의 프로세스에서 다운로드가 지속됨.
### 캐싱 디스크 I/O 최적화
모든 API 응답을 무조건 디스크에 캐싱할 경우 플래시 스토리지의 성능 저하를 초래할 수 있음. 
urlSession(:dataTask:willCacheResponse:completionHandler:)를 사용하면 응답이 캐시에 저장되기 직전에 가로챌 수 있고, 캐시 저장 여부를 선택할 수 있음.
