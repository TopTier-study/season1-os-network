# 프로세스 세부 학습

### 학습 키워드

`# process` `# IPC`

## 1. 핵심 개념

### Process

프로세스는 실행 중인 프로그램입니다. 멀티 스레드를 지원하는 시스템에서는 PCB에 각 스레드의 정보가 포함됩니다.

- **I/O-bound process**: 계산 작업보다 입출력 작업을 많이 하는 프로세스입니다.
- **CPU-bound process**: 입출력 작업보다 계산 작업을 많이 하는 프로세스입니다.

### 프로세스 생명주기

프로세스는 생성과 동시에 **ready queue**로 들어갑니다. 실행되거나 dispatched 될 때까지 ready queue에 머무릅니다. 실행 중에는 다음 사이클이 반복됩니다.

- I/O 요청을 보내면 **wait queue**로 들어갑니다. I/O 작업이 끝나면 wait → ready로 이동합니다.
- 자식 프로세스를 만들면 wait queue로 들어갑니다. 자식 프로세스가 terminated 되면 wait → ready로 이동합니다.
- 인터럽트가 발생하거나 할당된 시간이 만료되면 큐에서 지워지면서 ready queue의 맨 뒤로 다시 들어갑니다.

### CPU 스케줄링과 컨텍스트 스위칭

CPU 스케줄러는 준비 큐에 있는 프로세스 중 하나를 선택하고 하나의 CPU 코어를 그에게 할당하는 역할을 담당합니다.

- **the degree of multiprogramming**: 현재 메모리에 있는 프로세스. 메모리가 가득 차면 스와핑이 일어납니다.
- **context switch**: CPU 코어를 다른 프로세스에 할당. 이전 프로세스의 PCB 안의 컨텍스트를 저장하고, 새로운 프로세스의 컨텍스트를 가져와 실행합니다.
- 컨텍스트 스위칭 속도에 영향을 주는 것들
  - 메모리 속도
  - 복사되어야 하는 레지스터 수
  - 특정 instruction (모든 레지스터를 저장하거나 복원하는 instruction 등)

### IPC (Inter-Process Communication)

> 프로세스 간 자원 공유 개념을 학습하면서 떠올리면 좋은 상황입니다.  
> **Producer-Consumer Problem**: 생산자가 아이템을 만들고 소비자가 가져가서 사용합니다. 다 만들어지지 않은 아이템을 사용할 수 없습니다. 이 아이템들은 버퍼에 담깁니다.
>
> - **unbounded buffer**: 생산자는 항상 아이템을 만들 수 있습니다. 소비자는 만들어진 아이템만 소비합니다.
> - **bounded buffer**: 생산자는 버퍼가 차 있으면 소비자가 비울 때까지 대기합니다. 소비자는 버퍼가 비어 있으면 생산자가 채울 때까지 대기합니다.

### IPC 모델

IPC 모델은 크게 **공유 메모리**와 **메시지 전달** 방식으로 나뉩니다.

- 메시지 전달은 시스템 콜을 계속 발생시키므로 시간이 늘어납니다.
- 공유 메모리는 한 번 메모리 공간이 만들어지면 그 뒤로는 커널 개입 없이 routine memory access로 사용 가능하므로 더 빠릅니다.

### 공유 메모리 (Shared Memory)

한 프로세스의 주소 공간의 shared-memory segment에 영역이 만들어집니다.  
그 프로세스와 소통하고 싶은 다른 프로세스(소비자)는 해당 세그먼트를 자신의 주소 공간으로 가져옵니다.

데이터 형식과 주소는 프로세스들에 따라 결정되며 OS는 통제하지 않습니다.

### 메시지 전달 (Message Passing)

분산 환경에 적합한 방식입니다.

#### 1. Direct / Indirect Communication

- **Direct**: 상대의 이름을 알고 있는 방식입니다.
  - 생산자와 소비자가 서로 알고 있거나, 소비자만 생산자의 이름을 알고 있는 형태입니다.

- **Indirect**: 메일 박스 혹은 포트를 통해 전달하는 방식입니다.
  - 프로세스가 메일 박스를 관리한다면, 소유한 프로세스만 소비자가 될 수 있습니다.
  - 운영체제가 메일 박스를 관리한다면, 메일 박스를 생성한 프로세스가 기본적으로 수신 가능 프로세스입니다. 이 권한은 시스템 콜을 통해 변경할 수 있습니다.
  - 프로세스가 관리하면 프로세스가 종료될 때 메일 박스도 사라지지만, 운영체제가 관리하면 운영체제가 따로 제거합니다.

#### 2. Synchronous / Asynchronous Communication

- **Blocking send**: 상대가 수신할 때까지 대기합니다.
- **Nonblocking send**
- **Blocking receive**: 메시지를 가져올 수 있을 때까지 대기합니다.
- **Nonblocking receive**

#### 3. Automatic / Explicit Buffering

- **Zero capacity**: 메시지 큐의 최대 길이가 0입니다. 송신 프로세스는 수신 프로세스가 메시지를 가져갈 때까지 대기합니다.
- **Bounded capacity**: 메시지 큐의 최대 길이가 n입니다. n만큼 차 있지 않다면 자유롭게 메시지를 보내고 받습니다. 가득 차면 자리가 날 때까지 송신 프로세스가 대기합니다.
- **Unbounded capacity**: 송신 프로세스는 자유롭게 메시지를 보냅니다.

Zero capacity는 버퍼링이 없는 메시지 시스템으로 여겨지며, 나머지 둘은 자동 버퍼링 메시지 시스템으로 여겨집니다.

### Mach 메시지 시스템

Mach는 대부분 메시지 기반으로 소통하며 포트를 기반으로 메시지를 주고받습니다.

- 각 포트는 복수의 송신자가 존재할 수 있으나 수신자는 하나입니다.
- 포트를 만든 task만 해당 포트에서 메시지를 받을 수 있습니다.
- A 포트를 가진 a 작업이 B 포트의 b 작업으로부터 응답을 받고 싶다면, B 포트에게 A 포트로의 권한(MACH_PORT_RIGHT_SEND)을 승인해야 합니다.
- 포트에 대한 권리는 작업 단위로 관리되므로, 해당 작업에 포함된 모든 스레드는 동일한 권한을 가집니다. 같은 작업 내의 스레드들은 per-thread 포트를 통해 서로 메시지 교환이 가능합니다.
- 커널과의 소통은 작업이 만들어질 때 생성되는 Task Self port와 Notify port를 통해 이루어집니다.

메시지 시스템의 큰 문제는 송신 포트에서 수신 포트로 메시지를 복사하면서 발생하는 성능 저하입니다.  
Mach는 이를 해결하기 위해 가상 메모리 관리 기술을 사용합니다. 송신 메시지를 담은 송신 측 주소 공간을 수신 측 주소 공간으로 매핑하여 메시지 복사 없이 통신할 수 있도록 합니다. 단, 이는 시스템 내부(intra-system) 메시지에서만 가능합니다.
