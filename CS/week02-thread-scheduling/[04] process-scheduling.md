# 프로세스 스케줄링

### 학습 키워드

- 스케줄링, 스케줄러, 스케줄링 큐(Ready, Wait)
- I/O-bound, CPU-bound 작업
- Context Switching
- iOS 멀티태스킹 발전 과정

## 1. 핵심 개념

### 프로세스 스케줄링

**스케줄러의 역할**

- 멀티 프로그래밍 목적:  CPU가 놀지 않게 항상 실행될 프로세스를 준비해서 CPU 활용도 극대화
- 시분할 시스템 목적: 사용자 입장에서 여러 프로그램이 동시에 실행되고 있다고 느낄 정도로 프로세스 간에 CPU 코어를 매우 자주 교체하는 것
- 두 가지 목적을 만족하려면, 스케줄러가 각 core가 실행할 프로세스를 적절히 선택해야 함

**Single-core vs Multicore**

- 단일 코어 시스템은 한 번에 하나의 프로세스만 처리 가능
- 멀티 코어 시스템은 한 번에 여러 개의 프로세스 처리 가능
만약 코어 수보다 프로세스 수가 많다면, 남은 프로세스는 대기해야함
    - **Degree of multiprogramming**
        - 메모리에 동시에 올라갈 수 있는 프로세스의 수

**I/O-bound process, CPU-bound process**

- I/O-bound process → 프로세스의 실행 시간이 입출력 작업 시간에 제한받음
    - 연산보다 I/O 작업에 많은 시간이 드는 프로세스
- CPU-bound process → 프로세스의 실행 시간이 연산 시간에 제한받음
    - I/O 작업보다 연산에 많은 시간이 드는 프로세스
- 스케줄링 시 두 가지 요소를 모두 고려해야 함

**Ready Queue** 

- 연결리스트 형태
    - ready queue의 헤더는 첫 번째 PCB를 가리키고, 각 PCB는 다음 PCB를 가리키는 포인터를 가짐

**Wait Queue**

- 대기 상태에 있던 프로세스가 CPU를 할당받아 실행중이다가, 인터럽트를 받거나 특정 이벤트를 실행하기 위해 Wait queue에 들어갈 수 있음
- Waiting queue에 들어간 작업들은 기다리고 있던 이벤트가 종료되거나 처리 완료 신호(인터럽트)를 보내면 다시 Ready 큐에 들어감
- wait queue는 기다리는 대상에 따라 여러 개 존재함
    - I/O wait queue: 입출력 연산을 기다림
    - child termination wait queue: 자식 프로세스의 종료를 기다림
    - interrupt wait queue: 인터럽트 발생을 기다림

### CPU 스케줄링

**CPU 스케줄러의 역할**

- Ready queue에 있는 프로세스 중에서 CPU에 할당할 프로세스를 고르고, 할당함
- I/O-bound process의 경우 CPU 점유시간이 짧다.
- CPU-bound process의 경우 더 긴 시간 점유를 요구하지만, 독점하지는 않는다.
→ 시간이 지나면 강제로 CPU 점유를 해제하고 다른 프로세스에게 넘긴다

**Swapping**

- 스케줄링의 중기 형태
- 메모리에서 특정 프로세스를 제거하여 메모리에 동시에 올릴 수 있는 프로세스 수를 제한하는 것
    - 제거된 프로세스는 현재 상태를 저장하면서 메모리에서 디스크로 옮겨진다.
    - 다시 프로세스가 swapped-in될 경우, 저장해두었던 상태를 복원하면서 메모리에 올라간다.
- 이는 메모리가 오버커밋 되어 해제가 필요할 때만 필요로 한다.
    - **Memory overcommitted**: 프로세스들에게 할당해야할 메모리 양이 실제 가진 물리 메모리를 초과하는 경우 오버커밋 되었다고 함

---

### Context Switch

**상태 저장과 복원**

- 프로세스 실행 도중 인터럽트가 발생하면, 시스템은 CPU의 현재 상태(실행 중이던 프로세스의 상태)를 저장해야한다. (PCB)
- 프로세스가 다시 실행될 때 저장했던 상태를 복원한다.

**Context Switch**

- CPU 자원을 다른 프로세스로 교환할때, 현재 프로세스의 상태를 저장하면서 다른 프로세스의 상태를 복원하는 것
    - 인터럽트 발생 시, 커널은 이전 프로세스의 맥락을 PCB에 저장하고, 새로 실행될 프로세스의 상태를 로드
- 컨텍스트 스위칭 비용
    - 스위칭에 걸리는 시간 →  순수한 오버헤드
    - 메모리 속도, 복사되어야 하는 레지스터의 수, 특정 명령어의 존재 유무 등에 따라 달라짐.
    - 운영체제가 정교해지고 고도화될수록 문맥 교환시 처리해야 할 일의 양과 복잡도는 증가

## 2. 탐구 내용 (실무 / iOS 연결)

### 프로세스/스레드 관점

- iOS도 Darwin/XNU 위에서 동작하는 유닉스 계열 OS이므로, 기본적으로는 위와 같은 Ready/Wait 큐, 선점형 스케줄링, context switch 모델을 그대로 사용함
- 앱 개발자는 이를 추상화한 레벨의 API를 통해 간접적으로 관찰함

---

### I/O-bound / CPU-bound 작업과 iOS Background modes

- iOS는 정책적으로 I/O-bound 작업만 길게 허용하고 CPU-bound는 강하게 제한함
→ 따라서 일반적인 Background 상태의 앱은 일시 중지됨 (Suspended)

**Background modes**

- 백그라운드에서 실행되는 백그라운드 실행 모드는 제한적임
    - 과도하게 사용하면 기기 성능과 배터리 수명에 부정적인 영향을 줄 수 있기 때문 → 절제를 권장
    - 오디오 재생, 위치 업데이트 수신, 예약된 작업 처리 등 I/O-bound 작업이 대부분
- CPU-bound를 제한하는 이유
    - 유저가 보고 있지 않은 상황에서도 계속 CPU 자원을 사용하므로 배터리, 발열, 스케줄링 독점 문제 발생
- I/O-bound는 가능한 이유
    - 구조적으로 CPU 점유는 짧게 하고, 나머지는 대부분 시스템 데몬이나 커널, 드라이버가 주도하기 때문
    

**I/O-bound 친화적인 Background Mode들**

- ✅ Audio 재생
    - 네트워크 I/O + 오디오 출력
    - 사용자가 음악을 듣고 있다는 명시적인 ‘goal’이 있기 때문에 허용
- ✅ Location updates
    - GPS / 센서 이벤트 기반
    - OS가 위치 하드웨어를 공유 관리하면서, 이벤트가 발생할 때만 앱을 깨워 처리하게 함 → I/O 완료 인터럽트에 해당
- ✅ Bluetooth / accessory
    - 외부 디바이스 이벤트에 해당
- ✅ background URLSession (다운로드 등)
    - 대용량 업/다운로드를 **시스템 데몬**이 대신 수행 → 앱은 I/O 실제 진행을 담당하는 게 아니라 “결과를 받기 위해 잠깐 깨어나는(콜백)” 구조.
    - 즉, I/O-bound 코어 작업은 별도 프로세스가 하고, 앱 프로세스는 “이벤트 처리 + UI 업데이트” 정도만 수행.

**그럼 CPU-bound 작업들은?**

- 백그라운드 모드가 되면, **기본적으로 바로 일시 정지**됨 → Ready queue에 올라가지 않음.
- 제한적인 예외 상황
    
    
    | API | CPU-bound 허용도 | 특징 | 제약 사항 |
    | --- | --- | --- | --- |
    | **`beginBackgroundTask`** | **짧은 유예** | 모드 전환 시 user-intiated 작업을 마무리할 수 있도록 특정 시간만큼 허용 |   • endBackgroundTask(_:) 필수 호출 <br/>• CPU 점유 시간 많을 경우 → 종료 가능 |
    | **`BGProcessingTask`** | **제한적 허용** | OS 스케줄링, 배치성 작업용 (마이그레이션/인덱싱) |   • 연속/상시 CPU-bound 데몬 프로세스 실행 불가 |

- 실무 판단 기준
    - CPU-bound 작업이 30초 이상 걸린다면?
    → 백그라운드 대신 Foreground 전용으로 설계
    - "항상 돌아가야 하는" 연산이 필요하다면?
    → iOS 아키텍처로는 해결 불가 (서버로 분리하거나, 다른 방법 사용)

### iOS의 멀티태스킹 발전 과정

- 초기 버전 (iOS1 ~ 3)
    - 사용자 어플리케이션의 멀티 태스킹을 지원하지 않음
    - 다른 모든 앱은 suspended되고, 오직 하나의 앱만 포그라운드 상태에서 돌아갈 수 있었음
      
- **iOS 4 버전: 제한된 멀티태스킹을 최초로 지원**
    - 단일 포그라운드 앱 + 여러 개의 백그라운드 앱
    - 제한적이었으며, 아주 적은 어플리케이션 종류만 지원했음
- iOS 5~6: 멀티태스킹 안정화·내실화
    - iOS 4에서 도입한 멀티태스킹 모델을 유지하면서 OS 전반 안정화, API 확대 위주 업데이트
    - 시스템 앱과 주요 서비스(알림, iCloud 등)가 백그라운드와 연동되면서 멀티태스킹 체감은 커졌으나,
    서드파티가 마음대로 무제한 백그라운드를 쓰지는 못하는 구조 유지
- **iOS 7: 거의 모든 앱에 멀티태스킹 개방**
    - iOS 7에서 “모든 앱에 대한 멀티태스킹 지원”이 핵심 변화 중 하나로, 이전보다 훨씬 광범위한 백그라운드 실행이 가능해짐.
    - 앱 갱신 주기를 **OS가 스케줄링하는 방식**으로, 사용 패턴·네트워크 상태에 따라 백그라운드 Fetch 등을 자동 최적화해 배터리와 성능을 동시에 고려.
    - 개발자 입장에선 진짜에 가까운 멀티태스킹을 구현할 수 있게 되었지만, 여전히 시스템이 생명주기를 강하게 관리하는 “관리된 멀티태스킹” 모델 유지.
- iOS 9 이후(특히 iPad): 화면 기반 멀티태스킹
    - iOS 9부터 iPad에서 슬라이드 오버(Slide Over), 스플릿 뷰(Split View), PiP(그림 속 그림) 같은 화면 멀티태스킹 UI가 본격 도입.
    - 한 화면에 두 개 앱을 나란히 혹은 floating 형태로 띄우고, 사용자 제스처로 크기·위치 조절이 가능해 “동시 사용” 경험이 강화.
    - 이 단계부터는 단순 프로세스 멀티태스킹을 넘어서, UI 레벨 멀티윈도우 관리(씬, size class, 상태 복원 등)가 iPad 앱 개발의 핵심 이슈가 됨.
- iPadOS 분리 이후
    - 한동안 iOS와 코드베이스를 공유하던 iPad가 iPadOS로 분리되면서, 멀티태스킹 관련 고급 기능(다중 윈도우, 더 복잡한 레이아웃 등)은 점점 iPadOS 쪽으로 집중
    - 이로 인해 iPhone 중심의 iOS 자체는 “화면 멀티태스킹” 측면에서는 상대적으로 단순한 구조로 남게 되었고, iPad 계열에서만 데스크톱에 가까운 멀티태스킹 UX를 제공하는 방향으로 진화
