### 프로세스와 스레드의 Context Switching 과정 비교

- **프로세스 Context Switching (PCB 교체)**
    1. **커널 모드 진입:** 인터럽트나 시스템 콜에 의해 CPU가 유저 모드에서 커널 모드로 전환한다.
    2. **현재 상태 저장:** CPU의 레지스터 값(PC, SP 등)을 현재 실행 중인 프로세스의 **PCB**에 저장한다.
    3. **다음 프로세스 선택:** 스케줄러가 스케줄링 알고리즘에 의해 다음에 실행할 프로세스의 PCB를 결정한다.
    4. **메모리 맵 교체: 가상 메모리 주소 체계(Page Table)를 통째로 바꾼다. 이 과정에서 TLB(주소 변환 캐시)가 초기화되어 성능 비용이 발생한다.**
    5. **캐시 무효화: 이전 프로세스의 데이터가 들어있던 CPU 캐시 메모리가 사실상 무용지물이 되어 캐시 미스(Cache Miss)가 대량 발생한다.**
    6. **새 프로세스 실행:** 선택된 프로세스의 PCB에서 레지스터 값을 CPU로 로드하고 유저 모드로 돌아간다.

- **스레드 Context Switching (TCB 교체)**
    1. **커널 모드 진입:** (프로세스와 동일)
    2. **현재 상태 저장:** 현재 스레드의 PC, Register 값들을 해당 **TCB**에 저장한다.
    3. **다음 스레드 선택:** 같은 프로세스 내의 다른 TCB를 선택한다.
    4. **메모리 맵 유지: 같은 프로세스에 속해 있으므로 주소 공간(Page Table)을 교체하지 않는다. 따라서 TLB도 초기화되지 않는다.**
    5. **캐시 유지: 같은 프로세스 내 스레드는 Code, Data, Heap을 공유하므로 해당 영역의 캐시는 유지된다. 단, 각 스레드의 Stack은 독립적이므로 스레드 수가 많아질수록 Stack 데이터 간 캐시 경합이 발생하고, 한계를 넘으면 Cache Thrashing으로 이어진다.**
    6. **새 스레드 실행:** 선택된 TCB에서 정보를 로드하고 유저 모드로 돌아간다.

### 프로세스와 스레드 처리(생성-실행-회수) 비용 검증

프로세스와 스레드의 생성 오버헤드를 직접 비교&검증 해보기 위해 아래 실험을 수행했다.

- 코드 실행 환경: macOS, C source, POSIX API 및 Pthreads 라이브러리 사용
- 단순한 객체 생성 비용만을 측정하는 것이 아니라, 실제 OS 환경에서 다수의 작업이 병렬적으로 수행될 때 발생하는 **스케줄링 오버헤드와 컨텍스트 스위칭 부하**를 실험 데이터에 실질적으로 반영하고자 **생성-실행-자원 회수에 이르는 전체 비용(시간)** 을 측정했다.
- 측정 방법
    - 생성 객체의 수를 `1, 5, 10, 50, 100, 500, 1,000, 5,000, 10,000개`까지 늘리면서 측정 후, 
    프로세스와 스레드의 생성 비용 변화 추이를 그래프로 시각화
- 실행 결과
    
    <img width="3600" height="2100" alt="image" src="https://github.com/user-attachments/assets/acf8c0eb-ff25-4159-96ad-589904bddad5" />

    
    - 전체적 경향
        - 프로세스: 전체적으로 완만하고 일정하게 증가하는 경향을 보임
        - 스레드: 일정하게 증가하다가, **특정 구간에서 가파르게 증가하는 경향**을 보임
     
    - 구간 별 경향
    
       ```c
       1. N = 1 ~ 500
           - 대부분 일정하게 스레드가 프로세스보다 빠름
       2. N = 500 ~ 5000
           - 스레드의 시간 증가율이 프로세스보다 가팔라지기 시작.
       3. N = 10000
           - 두 방식의 비용 차이가 거의 없는 지점 발생
       ```
    
    - N = 1,000일 경우와 N = 10,000일 경우 **객체 1개 당 처리 비용 비교**
        
        
        | **생성 개수 (N)** | **프로세스 1개당 시간 (sec)** | **스레드 1개당 시간 (sec)** |
        | --- | --- | --- |
        | **1,000** | 0.113(s) / 1,000(개) = **0.000113s** | 0.020(s) / 1,000(개) = **0.000020s** |
        | **10,000** | 1.181(s) / 10,000(개) = **0.000118s** | 1.166(s) / 10,000(개) = **0.000116s** |
        | **비교** | **약 0.00011초로 일정 (선형적 증가)** | **약 6배 증가** |
      
    - 이를 종합적으로 판단했을 때,  
      프로세스는 처음부터 일정한 비용을 가지고 유지되는 경향을 보이는 반면 스레드의 경우 특정 개수를 넘어가면 처리 비용이 증가하면서  
      극단적으로 많을 경우 프로세스와 처리 비용이 거의 동일해진다는 것을 알 수 있다.

    - 객체 수가 **특정 범위를 넘어갈 때 프로세스에 비해 스레드 생성 비용이 크게 증가하는 이유**  
      → 생성 객체 수가 늘어나면서, 저렴한 생성 비용보다 **스케줄링 오버헤드가 차지하는 비중이 커졌기** 때문이다.
    
      요인 1. 스레드 경합과 스케줄링 복잡도 증가
    
        - 프로세스의 경우 개수가 늘어나도 각자의 주소 공간이 독립적이므로 커널은 단순히 정해진 스케줄링 알고리즘에 따라 프로세스를 고르면 됨
        - 스레드의 경우 여러 스레드들이 공유 자원에 접근하면서 커널은 많은 스레드 간 우선순위를 조정하고 동기화하는 복잡한 알고리즘을 수행해야 함
    
      요인 2. 캐시 오염
    
        - 프로세스는 처음부터 격리된 구조라 캐시 공유를 기대하지 않으며,
        교체 시마다 발생하는 비용이 크지만 일정하다.
        - 스레드가 적정 수를 유지할 때는 Cache hit을 기대하고 높은 효율을 낼 수 있는데,
        너무 많은 수의 스레드가 존재하면 **캐시의 용량 한계로 인해 Cache thrasing이 발생해서 결국 속도가 더 느린 RAM에 직접 접근하는 횟수가 증가하며 비용이 증가**하게 된다.
    
      요인 3. 커널 모드 전환 오버헤드의 누적
    
        - 스레드 생성 및 스케줄링, 회수 등 커널 모드에서 수행되는 작업을 위해 유저 → 커널 모드 스위칭이 빈번히 발생한다.
        - 프로세스는 생성 시부터 독립적인 주소 공간을 할당받아 관리하므로 높지만 일정한 고정 비용(Fixed Cost)을 유지한다.
        - 반면, 스레드는 경량화된 자원이라는 이점이 있지만, 극단적인 부하 상황에서는 **실제 연산보다 커널 모드 전환 및 스케줄링에 따르는 시스템 오버헤드가 더 커지는 역전 현상**이 발생하여 효율성이 급격히 저하된다.
  - 결론
    
    - **스레드는 프로세스에 비해 가볍지만 무한대로 그 수를 늘리면 성능적 한계와 비효율이 발생하며,
    이는 곧 스레드의 경량성이 시스템의 물리/관리적 부하에 종속적인 이점이라는 것을 시사한다.**
    - 프로세스의 경우 독립적인 메모리 주소 공간 할당 및 페이지 테이블 관리라는 **'고정된 고비용 오버헤드'** 가 성능의 하한선을 형성한다. 따라서 개수가 늘어나도 상대적인 성능 저하 폭이 일정하게 유지되는 안정성을 보인다.
    - 스레드의 초기 비용은 낮으나, 생성되는 객체 수가 증가함에 따라 **캐시 오염(Cache Thrashing), 커널 모드 전환 누적, 스케줄링 경합** 등의 **'가변적 누적 비용'** 이 급격히 증가하며, 극단적 상황에서는 이 누적 비용이 프로세스의 고정 비용을 추월하게 된다.

### 스레드 풀 개념의 등장

- 실제로 멀티스레드 환경에서 프로그램은 수백~수천개의 스레드를 포함하지만, 위 실험처럼 무분별한 스레드 생성은 성능 저하를 넘어 시스템 마비로 이어질 수 있다.
- 또한 개발자는 생성한 스레드에 작업을 할당할 때 경쟁 상태를 유발하지 않도록 독립적인 Task를 식별해야 하는데, 이 **과정에서 실수가 발생하면 데이터 부정합이나 데드락과 같은 치명적 결함으로 이어질 위험이 크다.**
- 따라서 많은 스레드를 개발자가 직접 생성하고 관리하는 것이 아닌, 시스템 차원에서 최대로 활용할 수 있는 스레드의 수를 제한하고 관리해주는 스레드 풀의 개념이 등장했다.

### GCD

- 내부적으로 스레드 풀을 관리하는 Apple의 시스템 프레임워크.
- 개발자는 Task를 던지기만 하면 → GCD가 알아서 스레드에 할당/스케줄링/회수 등의 작업을 처리한다.
- 스레드 풀의 최대 크기는 시스템 상태에 따라서 동적으로 조정된다.
- [자세히](https://github.com/TopTier-study/season1-os-network/blob/main/CS/week02-thread-scheduling/%5B01%5D%20thead-management.md)

- 문제점 - Thread explosion
    - GCD에서 스레드 풀의 크기는 고정되지 않는다. 이는 GCD에서 스레드 풀의 크기가 고정되는 것은 ‘모든 작업이 블로킹을 일으키지 않는다’는 것을 전제로 하기 때문이다.
    - 따라서 특정 스레드가 블로킹되면 GCD는 이를 "이 스레드는 지금 일을 못 하고 있다"고 판단하고, 큐에 남은 작업을 처리하기 위해 **새 스레드를 추가로 생성**한다. 이 패턴이 반복되면 스레드 수가 코어 수를 훨씬 초과할 수 있다.
    - 결국 위에서 스레드를 직접 생성했을때와 같이 스케줄링 오버헤드가 커지는 문제점이 다시 발생할 수 있다.

### Swift Concurrency의 등장

Apple은 이를 해결하기 위해 성능과 효율성을 고려한 새로운 동시성 모델을 구축했다.

### 어떤 점이 개선되었나?

- **스레드 수를 CPU 코어 수만큼만 생성**한다.
    - 스레드 폭발 문제 가능성을 원천 차단하고, context switching 오버헤드를 줄일 수 있다.
    
- **Non-blocking Suspend (협력적 스레드 양보)**
    - Swift Concurrency는 스레드가 일하지 않고 기다리는 차단 상태가 되는 대신, 하던 작업을 잠시 중지하는 Suspended 상태가 되도록 한다.
    - 처리 시간이 오래 걸리는 함수 앞의 `await` 키워드를 만나면 실행중이던 비동기 함수의 실행은 일시 중단되지만, 작업을 처리하던 해당 **스레드는 차단되지 않고 즉시 해제된다**.
    - 해제된 스레드는 런타임에 의해 즉시 다른 대기 중인 작업에 할당된다.
      
- Async 함수 실행 시 내부 메모리 동작의 변화 (자세한 과정은 wwdc 참고)
    - **Continuation:** 함수가 `await`를 만나면 **스택에 쌓여있던 지역 변수와 실행 지점 정보를 힙 영역의 'Async Frame' 형태로 추가**한다.
    이때 비동기 함수가 점유하고 있던 기존 스택 상단의 프레임은 제거되어 스레드에서 해제되며, 해당 스레드는 즉시 런타임에 의해 **다음에 실행 대기 중인 다른 작업의 스택 프레임을 쌓아 수행할 수 있는 상태**가 된다.
    - 따라서 코어 수만큼의 스레드 수를 유지할 수 있고, `await` 코드를 만났을 때 커널이 개입하는 전통적인 TCB 교체가 **아닌 User mode의 힙 영역에서 작업(Async frame)이 전환되는 것으로 Context switching 비용을 최소화**할 수 있다.
      
- 구조적 동시성 (Structured Concurrency)
    - 런타임은 수많은 Task들 간의 관계를 **계층적 트리 구조**로 관리하여 의존성을 추적한다.
    - **의존성 추적:** 부모-자식 간 관계는 Swift 코드 레벨에서 나타낼 수 있고(`async let`또는 `TaskGroup`),  부모 Task는 생성된 모든 자식 Task들이 완료되거나 취소되기 전까지 종료되지 않는다.
    - **자원 관리 자동화:** 부모 Task가 취소되면 트리 하부의 모든 자식 Task에게 취소 신호가 자동 전파되므로, 불필요한 자원 낭비를 최소화할 수 있다.

## 3. 의문 / 논점

### 1. Async Frame의 힙(Heap) 할당 오버헤드

전통적인 스레드 기반 비동기 모델은 TCB 교체 매커니즘을 사용한다. 반면 Swift Concurrency는 실행 상태를 보존하기 위해 **Async Frame을 힙 영역에 할당**한다.

> Async frame의 힙 할당 오버헤드는 thread context switching 비용과 비교했을 때 어떤 근거로 더 효율적인 선택으로 판단되었는가? **작업의 단위가 매우 작고 빈번**할 경우, 오히려 힙 할당 오버헤드가 성능의 새로운 병목이 될 가능성은 없는가?
> 
<details>
  <summary>힙 할당 비용 vs TCB context switching 비용에 대하여</summary>
    <br/>
  힙 할당은 오직 유저 모드에서 수행되는 작업이지만 TCB context switching은 커널이 개입하고 여러 교체 작업이 수행되므로, 비용 자체는 힙 할당이 훨씬 적다고 할 수 있다.
</details>

<details>
  <summary>작업의 단위가 매우 작고 빈번할 경우, Swift concurrency의 힙 할당 오버헤드가 성능의 새로운 병목이 될 가능성과 이를 해소하는 방법</summary>
    <br/>
  이는 실제로 발생 가능한 문제 상황으로, 아래 코드는 매우 작은 작업에 대해 많은 Task를 생성하는 케이스를 재현한다.

  
  ```c
    // ❌ 위험한 패턴: 매우 작은 작업을 대량으로 Task 생성
    func processItems(_ items: [Int]) async {
        for item in items {
            // 루프마다 Task 생성 = 루프마다 힙 할당
            async let result = Task {
                return item * 2  // 작업 자체는 나노초 수준
            }
        }
    }
  ```
    
  이 경우 실제 연산은 매우 작은데도 불구하고 매 반복마다 Task가 생성되면서 Async frame이 힙에 할당된다. 이로 인해 실제 작업보다 런타임 오버헤드가 더 커질 수 있다.
    
  오버헤드를 발생시키는 주요 원인은 다음과 같다.
    
  1. 힙 할당 비용 (Heap Allocation Overhead)
     - Async 함수가 `await` 지점을 가질 경우 실행 상태를 저장하기 위한 **Async frame**이 힙에 할당된다. 매우 작은 작업이 반복적으로 실행되면 이러한 힙 할당 비용이 누적되어 오버헤드로 작용한다.
        
  2. Allocator Churn
     - 작은 객체의 빈번한 메모리 할당/해제 **패턴**이 반복되면 메모리 allocator가 지속적으로 동작하게 되고, 이로 인해 캐시 미스나 메모리 트래픽 증가 같은 추가적인 비용이 발생할 수 있다.
        
    
  Swift Concurrency는 이러한 문제때문에 작은 작업에 많은 Task를 생성하는 것을 권장하지 않으며, 다음과 같은 최적화 메커니즘을 제공한다.
    
  1. 컴파일러 수준 최적화
     - Swift 컴파일러는 `async` 함수에 실제 **suspension point(`await`)가 존재하는지 분석**하여, suspend가 발생하지 않는 경우 **Async Frame 생성 및 힙 할당을 생략**할 수 있다.
        
  2. Task Local Allocator
     - Swift Concurrency Runtime은 Async Frame과 Task 관련 메모리를 **일반 `malloc` 대신 Task 전용 allocator**로 관리한다.  
        Task가 생성될 때 비교적 큰 메모리 블록을 확보하고, 그 내부에서 작은 객체들을 **선형(bump) 방식으로 할당해서** 반복적인 allocation 비용을 줄인다.
        
  3. Structured Concurrency
     - `TaskGroup`과 같은 구조화된 concurrency 모델을 통해 Task의 생성과 생명주기를 관리하여 **과도한 Task 생성으로 인한 오버헤드를 완화**한다. 
        
</details>

### 2.  구조적 동시성에서의 '작업 취소' 설계 철학에 대한 해석

구조적 동시성에서는 부모 Task가 취소될 경우 해당 취소 신호가 자식 Task로 전파된다. 그러나 이 신호는 **취소 사실을 전달하는 신호일 뿐, 자식 Task를 강제로 종료시키는 신호는 아니다.**

실제로 작업을 중단하려면 개발자가 코드 내에서 주기적으로 `Task.isCancelled`를 확인하거나 `try Task.checkCancellation()`을 호출하여 취소 상태를 처리해야 한다.

이러한 설계는 강제성이 없기 때문에, 부모 Task가 취소되었더라도 자식 Task가 취소 상태를 확인하지 않는다면 작업이 계속 실행될 수 있으며,  
이로 인해 불필요한 자원 사용이 발생하는 ‘논리적 고아 작업(logical orphan task)’이 남을 수 있다는 우려가 제기될 수 있다.

그러나 Apple은 작업을 강제로 종료할 경우 발생할 수 있는 **데이터 일관성 문제나 자원 정리 실패 등의 안정성 저해 가능성**을 고려하여, 
강제 종료 방식 대신 **협력적 취소(cooperative cancellation)** 모델을 채택하였다.

결론적으로 Swift가 선택한 설계는 **"즉각적인 취소(immediate cancellation)"보다 "안전한 취소(safe cancellation)"를 우선시한 것**이라고 볼 수 있다. 
따라서 구조적 동시성이 보장하는 것은 취소 신호의 전파 구조(cancellation propagation)이지, **취소의 실제 이행 자체는 아니라는 점**을 이해할 필요가 있었다.
