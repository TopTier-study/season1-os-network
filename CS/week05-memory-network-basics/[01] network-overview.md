## 1. 핵심 개념

### 네트워크

컴퓨터, 서버, 라우터 등 2대 이상의 장치를 유무선으로 연결하여 데이터를 교환하고 리소스를 공유하는 통신망

#### **등장 배경**
<img width="1024" height="559" alt="image" src="https://github.com/user-attachments/assets/e4f9c586-df4b-4032-9aff-b7fadd2a420a" />



#### 1950년대

- 메인프레임 1대를 여러 사용자가 카드·천공지로 배치 처리(대량 데이터를 순차 처리)하던 시기
- 카드 한 장에 한 줄의 코드 정도를 담을 수 있는 정도로, 상호작용 없이 간단한 수학 계산에만 사용하였다.

#### 1960년대

- 시간 분할 시스템이 등장하면서 여러 단말기가 하나의 중앙 컴퓨터에 동시에 접속해 상호작용할 수 있게 되었고, 자연스럽게 **여러 장비를 통신선으로 연결하는** 초기 네트워크 구상이 생기게 되었다.
- 같은 시기, 미국 군사 시스템 등에서 레이더·컴퓨터를 전화선/모뎀으로 연결하는 초기 컴퓨터 네트워크가 구축되었고, 원격지 컴퓨터 간 데이터 전송에 대한 요구가 더 확산되었다.
    
    > 꼭 같은 장소에서 접속해야하나?, 다른 장소에서 접속할 수는 없을까?
    > 
- 1960년대 후반, 폴 바란과 도널드 데이비스 등이 최초로 **패킷 교환 개념**을 제안하면서, 오늘날 데이터 네트워크의 이론적 기반이 만들어졌고, 이를 토대로 1969년 ARPANET이 구축되어 최초의 패킷 교환 컴퓨터 네트워크로 동작하기 시작했다.

#### 1970년대

- 학교나 가정과 같은 좁은 범위에서 네트워크를 이용하기 위해 호스트와 구리/광섬유 케이블 등의 유선 통신 매체를 연결해 데이터를 주고받을 수 있게하는 이더넷 기술이 등장했다.

#### 1980년대

- 이더넷이 상용화되었고, TCP/IP 표준화·보급 등을 거치면서 WAN 통신도 가능하게 되어 “네트워크의 네트워크(인터넷)”라는 개념이 실현되었다.

#### 1990년대

- 최초의 웹 브라우저, WWW이 등장하고 인터넷이 대중화됨
    - 인터넷 통신망에서 웹사이트를 HTML로 작성하고, URL로 위치를 지정하고, HTTP로 데이터를 전송하는 정보 시스템

#### 2000년대

- 모바일 기기가 보급되고 클라우드 기술이 등장하면서 아무데서나 인터넷을 사용할 수 있게 되었다.

### 인터넷의 동작 원리

#### 이더넷

- LAN 내부 호스트를 연결해 유선으로 데이터를 주고받는 기술
- 이 기술만으로는 인터넷 통신 불가 ..

#### 라우터

- 네트워크와 네트워크를 연결해 데이터 패킷이 목적지까지 가장 빠르고 안전하게 도달할 수 있도록 최적의 경로를 설정해 주는 장비
- 라우터를 통해 수많은 네트워크들이 연결되어 인터넷이 구성된다.
- ISP(Internet Service Provider): 특수한 라우터를 관리하면서 거대한 인터넷 접속망을 구성하고, 관리한다.

#### IP, DNS

- 인터넷 상의 호스트를 구별하기 위한 주소, IP주소를 식별하기 쉬운 도메인 이름으로 관리하는 서버가 DNS

#### 패킷 교환

- 데이터는 패킷 단위로 쪼개어져 특정 경로를 따라 전송된다.
- 패킷에는 데이터(페이로드)뿐만 아니라, 수신지/송신지 주소나 메타데이터 등 여러 정보가 담겨 있다.
- 현재 대부분의 통신 방식이다.

### 현대 네트워크 환경에서 고려해야 할 것

#### 연결성

- 유선, 무선, 위성 등 다양한 통신 매체를 통해 이종 기기 간 통신이 보장된다.
- 언제 어디서나 연결되는 것을 넘어 끊기지 않아야 한다.

#### 신뢰성

- 데이터가 전송 중 유실되지 않도록 하는 TCP의 재전송 메커니즘과 경로 하나가 끊길 경우
다른 길을 찾는 **동적 라우팅** 기술이 핵심이다.

#### 성능

- 지연 시간(Latency)을 최소화하면서 최대 전송 속도인 대역폭을 극대화하는 것이 목표이다.
- 최근에는 물리적 거리를 극복하기 위해 사용자와 가까운 곳에 서버를 두는 엣지 컴퓨팅 기술이 강조됨

#### 확장성

- 사용자, 기기, 트래픽이 급증하더라도 네트워크의 기본 성능이나 서비스 품질을 저하시키지 않고, 장비 추가 등을 통해 유연하게 처리 용량을 늘릴 수 있어야 한다.
- Scale-up: 기존 장비의 사양을 업그레이드하는 방식
- Scale-out: 네트워크에 노드나 장비를 추가해서 확장하는 방식

#### 보안

- Zero-trust 원칙 준수
- 데이터 전송 시 탈취를 막기 위한 TLS/SSL 암호화가 필수

#### 자원 효율성

- **가상화 (SDN/NFV):** 비싼 하드웨어 장비 대신 소프트웨어로 네트워크 기능을 제어(Software Defined Networking)하여 유연하게 자원을 배분한다.
- **트래픽 셰이핑:** 네트워크의 통신량을 제어하여, 패킷을 지연시킴으로써 대역폭을 확보하고 통신 성능을 보장하거나 최적화하는 일

#### 분산 & 장애 대응

- 장애는 반드시 발생할 수 있다는 전제하에 대응 방안 설계
- **분산 거점:** 데이터 센터를 여러 지역에 나누어 운영하여 특정 지역에 재난이 발생해도 서비스가 유지되도록 한다.
- **이중화 (Redundancy):** 모든 핵심 장비와 회선을 두 개 이상 구축하여 하나가 고장 나면 즉시 예비 장비가 투입되는 **Failover** 시스템 구성

### API 호출 시 네트워크, 운영체제 관점에서 세부 동작 직접 확인하기

#### CURL (Client of URL)

터미널에서 HTTP, HTTPS, FTP 등 다양한 프로토콜을 사용하여 서버와 데이터를 주고받는 강력한 명령줄 도구 및 라이브러리

**지원하는 주요 기능**

- **다양한 프로토콜:** HTTP, HTTPS, FTP, SFTP, SMTP, POP3, LDAP 등 지원.
- **메서드 제어:** GET, POST, PUT, DELETE, PATCH 지정 가능
- **헤더 수정:** User-Agent, Content-Type 등 HTTP 헤더를 직접 설정 가능.
- **인증 지원:** Basic Auth, OAuth2, Cookie 등을 이용한 로그인 처리.
- **프록시 및 타임아웃:** 네트워크 지연 시뮬레이션이나 보안망 통과 기능.

**활용 예시**

- 웹 페이지 html 요청

```swift
# 기본 호출 (GET 요청)
curl https://www.google.com
```

- API 요청 및 데이터 전송 (헤더, 메소드 자유롭게 설정)

```swift
# POST 요청으로 데이터 전송 (-d: 데이터, -H: 헤더)
curl -X POST https://api.example.com/v1/login \
     -H "Content-Type: application/json" \
     -d '{"username": "admin", "password": "123"}'
```

- 리다이렉트 추적

```swift
curl -L http://google.com # https로 자동 리다이렉트
```

- 속도 제한 걸기 (대역폭 테스트)

```swift
# 초당 100K로 다운로드 제한
curl --limit-rate 100K -O https://example.com/largefile.zip
```

- 상세 통신 로그 추적

```swift
curl -v https://api.github.com
```

#### curl 요청 생성 및 전송

- 네트워크 관점: 송신 호스트의 L7 계층에서 요청이 전송된다.
- `jsonplaceholder`: 가상 REST API 서버로 프론트엔드 개발 및 테스트를 위해 누구나 무료로 사용할 수 있는 무료 클라우드 서비스이다.
- `-v` 명령어 인자를 붙여 통신 과정을 로그로 출력한다.

```swift
curl -v https://jsonplaceholder.typicode.com/posts/1
```

#### 요청이 전송되고 응답이 오기까지 어떤 일이 일어날까?

**(OS단)**

- 터미널 쉘은 현재 프로세스를 fork하고, curl 실행 파일을 올려 실행한다.
- curl 프로세스는 고유한 PID를 얻고, 명령어 인자 `-v`가 메모리 스택 영역에 적재된다.

**IP 주소 찾기**

<img width="1080" height="126" alt="image" src="https://github.com/user-attachments/assets/f5072741-43d1-406b-81ee-c5b16ee63b65" />

- 현재는 도메인 주소만 알고 있지, 정확한 IP주소를 알지 못한다.
- curl은 IP주소를 얻기 위해 libc에 포함된 `getaddrinfo()` 시스템콜을 호출한다.
- OS는 `/etc/hosts` 파일(로컬 네임 서버)이나 로컬 DNS 캐시를 검색한다.
    - **데이터가 없다면 DNS 서비스용 포트인 53번 포트를 통해 DNS 서버로 패킷을 전송해 IP주소를 얻는다.**
- `Cloudflare`에서 제공하는 IP 주소가 2개인 이유?
    - 부하 분산: 하나의 IP에 트래픽이 몰리는 것을 방지하고자 여러 대의 에지 서버에 각각 다른 IP를 부여해 관리
    - 고가용성: 하나의 서버가 고장날 경우, 다른 서버로 즉시 재연결할 수 있도록 설계

**TCP 3-way handshake로 연결 통로 확보**

- IP 값 응답을 받으면, 이제 상대방 서버와 연결할 준비가 되었는지 묻는 단계를 거친다.
- 다른 터미널 창에 아래 코드를 쳐서 송수신 패킷을 모니터링하면서 요청을 전송하면,
TCP 핸드셰이크 과정을 보다 자세히 확인할 수 있다.

```swift
sudo tcpdump -i en0 host jsonplaceholder.typicode.com and port 443
```

<img width="1193" height="365" alt="image" src="https://github.com/user-attachments/assets/f04c8151-cd02-4ae7-ae72-c09d5654248d" />


- 국내 네트워크 통신의 평균 RTT는 10ms로, 140ms만에 서버에서 응답이 온 것으로 보아 수신 호스트가 해외 서버임을 알 수 있다.
- **`mac.kornet`**: 통신사가 KT(Kornet)임을 알 수 있다.
- 이때 로컬에서 생성되는 패킷들은 송신 버퍼에 담겼다가, 맥북에 내장된 무선 랜카드 인터페이스를 통해 전달된다.
- OS는 서버의 응답이 올 동안 프로세스를 대기 상태로 전환하고 CPU를 반납한다.
- 서버의 응답 패킷이 NIC에 도착하면, NIC는 CPU에 하드웨어 인터럽트를 발생시키고, 커널은 curl을 다시 실행중 상태로 깨운다.

#### 보안 장벽 (TLS handshake)

- HTTPS를 사용하므로 TCP 핸드셰이크를 통해 파이프가 뚫린 후, 데이터 암호화를 위한 비밀 키를 공유한다.

<img width="1806" height="1018" alt="image" src="https://github.com/user-attachments/assets/fef1dec1-82d6-4a8c-b070-25049e3c6291" />


- `Client hello / Server hello` 메시지 교환으로 서로 인식하고, 암호 방식을 합의한다.
- `(IN), TLS handshake, Certificate` / `SSL certificate verify ok.`
    - 서버가 전송한 인증서를 통해 신뢰할 서버인지 검증한다.
- `TLS handshake, Finished` / `SSL connection using TLSv1.3`
    - 디피-헬만 키 교환 방식을 사용해 비밀키를 생성하고 이후부터 모든 데이터를 암호화해서 주고받는다.

#### 데이터 요청 및 수신

- GET 요청 전송 및 응답, tcpdump 로그의 4번째 과정에 해당
    
    <img width="2048" height="1258" alt="image" src="https://github.com/user-attachments/assets/1e7b1972-c8ef-476b-bdca-b4f0e33d7a98" />

    
- **`< HTTP/2 200`**: 요청 처리 성공
- **`server: cloudflare`**: 이 데이터는 Cloudflare라는 전 세계적인 가속 네트워크망을 거침
- **`cf-cache-status: HIT`**
    - 서버가 데이터를 새로 생성한 게 아니라, 이미 저장해둔(캐싱된) 데이터를 전송함.
- **`cf-ray: ...-LAX`**
    - cloudflare의 데이터 센터 식별자, LAX라는 것은 LA에 있는 엣지 서버에서 요청을 처리했음을 의미한다.
- **`Connection #0 ... left intact`**
    - 통신이 끝났지만, TCP 통로를 유지해서(Keep-alive) 다음 요청 시 핸드셰이크 과정을 생략하고 바로 처리할 수 있도록 한다는 것
    - 그러나 curl은 단발성 도구로, 보통 요청 처리가 끝나자마자 프로세스가 종료되어 OS에 의해 유지되지 않고 종료된다.
- curl은 암호화된 상태로 도착한 데이터를 로컬에서 복호화해 출력하고 종료된다.
