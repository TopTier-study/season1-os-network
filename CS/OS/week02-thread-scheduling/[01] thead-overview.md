# 스레드의 등장과 싱글스레드/멀티스레드

### 학습 키워드

- 스레드 등장 배경
- 싱글스레드, 멀티스레드
- 멀티스레딩의 3가지 모델

## 1. 핵심 개념

### 스레드 등장 배경

**스레드**

- 프로그램의 가장 작은 실행 단위
- 스레드마다 식별 ID, PC, 레지스터 값, 스택 등의 값을 가짐
- code, data, files 영역은 한 프로세스 내의 스레드끼리 공유함

**프로세스 생성 오버헤드** 

- 전통적인 프로세스 → **단일 실행 흐름**을 가짐 (한 번에 하나의 작업만 수행 가능)
- 그러나 프로세스가 한 번에 여러 작업을 수행해야 하는 경우가 있음
    - 가령, 웹 서버에 수 많은 클라이언트의 요청이 동시에 올 때
    - 이 경우 한 번에 하나의 작업만 처리 가능하다면 ? → 클라이언트는 오랜 시간 대기해야함
    - 따라서 요청이 올 때마다 작업을 처리할 수 있는 새 프로세스를 생성할 수 있음
    - **그러나 요청마다 프로세스를 생성하는 것은 오버헤드가 크고, 프로세스는 메모리를 공유하지 않으므로 IPC 비용 발생.**
- 따라서 프로세스를 매번 생성하는 것보다, 한 프로세스 내에 자원을 공유하고 가벼운 여러 개의 스레드를 두는 것이 효율적임

---

### 싱글스레드 vs 멀티스레드

- 현대 컴퓨터, 모바일 기기에서 돌아가는 프로그램은 대부분 멀티스레드
- 자원 활용을 극대화하고 한 번에 여러 작업을 동시에 수행할 수 있지만, 그만큼 설계가 복잡하고 동기화 문제가 발생할 여지가 있음
- 싱글스레드의 경우, 자원 활용도와 처리 속도는 낮지만 단순하므로 작업량이 적고 단순한 경우 더 유리할 수 있 (오히려 스레드 관리 비용이 더 클 수 있음)

| **구분** | **싱글 스레드 (Single-Thread)** | **멀티 스레드 (Multi-Thread)** |
| --- | --- | --- |
| 정의 | 한 프로세스 내에 하나의 실행 흐름만 존재 | 한 프로세스 내에 여러 개의 실행 흐름이 존재 |
| **작업 방식** | 한 번에 하나의 작업만 수행 | 여러 작업을 동시에(병렬/병행) 수행 |
| **자원 공유** | 해당 없음 (혼자 다 씀) | **Stack을 제외한** Code, Data, Heap 공유 |
| **응답성** | 작업이 길어지면 화면이 멈춤 (Blocking) | 한 스레드가 지연되어도 다른 스레드가 응답 가능 |
| **경제성** | 구현이 단순하고 안정적임 | 생성 및 소통 비용이 저렴함 (오버헤드 적음) |
| **위험성** | 하나가 죽어도 그 프로세스만 문제 | **한 스레드의 오류가 프로세스 전체를 종료**시킬 수 있음 |

---

### 멀티스레드 환경의 이점

- 반응성
    - 특정 스레드가 긴 연산을 하거나, 차단되어도 지속이 가능
    - 특히 사용자 인터페이스에 유용
        - 사용자가 버튼을 클릭하고 처리하는 작업에서 시간이 걸릴 경우, 싱글 스레드는 해당 작업이 완료될 때까지 반응이 없지만, 멀티 스레드인 경우 그 동안 별도 스레드에서 다른 작업을 처리할 수 있기 때문
- 자원 공유
    - 프로세스의 경우, 데이터를 공유하려면 개발자가 직접 구현해야하며, 비용이 많이 듦
    - 스레드는 기본적으로 프로세스 내에서 메모리와 자원들을 공유함
        - 같은 주소 공간 내에서 바로 소통 가능 → 비용 적음
- 경제성
    - 기본적으로 스레드는 한 프로세스 내의 자원을 공유하므로, 생성 및 문맥 교환 비용이 적게 듦
    - 스레드 생성이 프로세스 생성보다 빠르고 메모리도 적게 차지
- 확장성
    - 멀티스레딩은 멀티 코어 시스템에서 더 효율이 극대화
        - 병렬적으로 여러 코어에서 실행 가능

---

### 멀티코어 프로그래밍

- single-CPU → multi-CPU→ multi-core 환경으로 변화
- 처리할 작업이 다수인 상황에서?
    - single-core: 하나의 코어에 여러 스레드가 번갈아가면서 실행되는 것이 곧 동시성
    - multi-core: 여러 코어에서 물리적으로 병렬 실행 가능
    - **동시성 vs 병렬성**
        - 동시성: 논리적으로 한 번에 여러 프로그램이 실행되는 것
        - 병렬성: 물리적으로 존재하는 여러 처리자가 동시에 실행하는 것
        - 따라서, 병렬성을 만족하지 않아도 동시성은 만족 가능

---

### 프로그래밍적 어려움

**멀티 코어 시스템이 발전하면서 여러 개의 코어들을 효율적으로 사용하기 위한 과정에서 여러 어려움들 존재**

- Identifying tasks
    - 서로 독립적이어서 물리적으로 다른 코어에서 병렬 실행 가능한 Task를 찾아야 함
    - 독립적이지 않은 tasks → 의존성 관리 필요
- Balance
    - 최대한 모든 Task들이 동일한 가치를 지닌 동일한 양의 일을 수행하게 하는 것
    - 멀티 코어를 쓰는 의미를 살리기 위함
- Data splitting
    - 프로그램이 여러 Task들로 분리되면, Task에 의해 처리되는 데이터들도 분리될 수밖에 없음
- Data dependency
    - 단순히 여러 스레드에서 같은 값을 사용하는게 아니라,
    특정 값에 대한 여러 Task들의 선후관계(의존성)가 생길 수 있음 → 물리적 제약
    - 개발자는 의존성을 고려해 특정 순서로 Task의 실행을 동기화해야 함
- Testing and debugging
    - 여러 코어에서 병렬 실행될 때, 단일 스레드 어플리케이션에서보다 테스트 및 디버깅이 까다로움
        - 실행 순서 보장 안 됨
        - **하이젠버그**(스레드 간 타이밍 차이로 존재하던 버그를 재현하기 어려움)

---

### **병렬성의 종류**

**Data parallelism, Task parallelism**

- Data parallelism
    - 한 데이터를 부분 집합으로 나눠 각 코어에 배정하고, 각 코어는 주어진 데이터에 대해 같은 연산을 수행
- Task parallelism
    - 데이터가 아닌, 작업 단위를 코어에 배정하는 것 → 따라서 각 코어는 서로 다른 연산을 수행
- 둘은 상호 배타 관계가 아님, 따라서 프로그램은 두 가지 방식을 섞어서 사용할 수도 있음.

---

### 멀티 스레딩 모델

**User threads, Kernel threads**

- User threads는 커널 상위에서(커널의 개입 없이) 제공되고, Kernel threads는 운영체제에 의해 직접적으로 관리됨
- 유저 스레드(User space)와 커널 스레드(Kernel space) 사이의 관계를 정의하는 방법에 대해 3가지 모델이 존재

**Many-to-One Model (User-Kernel)**

- 스레드 관리(생성 및 교체)는 유저 공간의 스레드 라이브러리에 의해 수행되므로, 효율적이고 빠름
- 커널 입장에서는 프로세스를 하나로만 보기 때문에, **물리적인 멀티코어 병렬 실행이 불가능
→ 현대에서 거의 쓰지 않음**
- 스레드 하나가 입출력(I/O)으로 대기 상태가 되면 전체 프로세스가 멈춤

**One-to-One Model**

- 하나의 유저 스레드가 하나의 커널 스레드에 대응되는 모델
- 하나가 대기해도 다른 스레드가 실행될 수 있음, 따라서 물리적 멀티코어 병렬 실행 가능
- 유저 스레드가 생길 때마다 커널 스레드를 생성해야하고, 많은 수의 커널 스레드는 시스템 성능에 부하를 줄 수 있음
- 가장 많이 쓰이는 모델, Linux, Windows가 해당

**Many-to-Many Model**

- 유저 스레드 수 이하의 커널 스레드 집합을 사용하는 방법
- 일대일 모델의 '병렬성'과 다대일 모델의 '효율성'을 절충. 필요한 만큼 유저 스레드를 만들어도 커널 스레드가 이를 적절히 분담하여 코어에 배분함
- **Two-level mode**
    - 멀티 플렉싱(유저 스레드 수가 커널 스레드 수 이상이므로 적절하게 번갈아가며 수행하는 것)과 더불어
    특정 유저 스레드를 특정 커널 스레드에 바인딩하기도 함
- 가장 유연하지만, 구현하기 힘들고, 코어 수가 증가하면서 커널 스레드 수를 제한할 필요성이 줄어듦

## 2. 탐구 내용 (실무 / iOS 연결)

### Xcode의 Thread Sanitizer의 역할 (매우 간단)

**하이젠버그**

- 프로그래밍에서 테스트를 수행할 때 발생되는 버그의 형태 중의 하나로, 문제를 발견하고 수정하기 위한 디버깅을 수행하려고 하면 문제점이 사라지는 형태의 버그.
- 특히 멀티스레드 환경에서는 스레드 간의 실행 순서가 매번 무작위로 달라진다.
따라서 버그를 잡으려고 로그를 찍거나 디버거를 붙이는 순간, 스레드의 **실행 순서가 미세하게 바뀌면서 관측되던 에러가 사라지는 현상이 발생할 수도 있다.**

**하이젠버그를 논리적으로 추적하고 동시성 문제를 찾아내는 TSan**

- **논리적 인과관계 분석**
    - 에러가 물리적으로 발생하는 '순간'만 포착하는 게 아니라, **메모리 접근 기록**을 바탕으로 '동기화 장치 없는 동시 접근'이라는 설계 결함을 찾아냄.
    - **컴파일 타임**에 LLVM 레벨에서 메모리에 읽고 쓰는 모든 코드에 감시용 코드를 삽입
- **그림자 메모리(Shadow Memory)**
    - 프로그램이 실행되는 동안 사용되는 컴퓨터 메모리에 대한 정보를 추적하고 저장하는 데 사용되는 기술로, TSan은 실제 메모리의 각 위치에 대해 '어떤 스레드'가 '어떤 순서(Vector Clock)'로 접근했는지 기록하는 별도의 공간을 운영함.
    - 컴파일 타임에 심어두었던 코드를 바탕으로, **런타임에 실시간으로 데이터를 기록**함
- **추적 대상**
    - 데이터 경합(Data Race), 초기화 미비, 잘못된 잠금 순서 등 동시성 문제 전반.
- **사용 시 주의할 점**
    - macOS 64비트 시스템을 제외하고 실기기에서 동작 안 함
    - 진단 기능 삽입으로 인한 메모리 사용량 급증 (5~10배)
    → 앱이 2배에서 20배까지 느려질 수 있음. 따라서 진단 시에만 사용하는 것 권장
