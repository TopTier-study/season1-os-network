## 1. 내가 학습한 주제
- 인터럽트
- 시스템 콜
- 예외

## 2. 핵심 문제
- 타이머 인터럽트와 시스템 콜은 누가 발생시킬까
* 사용자 코드가 커널 기능을 요청할 때 왜 직접 못 하고 시스템 콜을 거칠까
* 예외(Exception)는 정상 흐름? 비정상 흐름?

## 3. 탐구 내용
### 인터럽트
: 외부 하드웨어가 CPU에게 지금 처리할 일이 있다는 것을 알리는 신호

- 발생시키는 주체: **하드웨어**
- 예) 타이머 인터럽트
  - 일정 시간마다 발생
  - CPU가 실행 중이던 코드 stop
  - 커널로 전환
  - 스케줄러 실행
- 운영체제 관점에서 선점형 스케줄링이 가능하게 한다.
- **한 프로세스가 CPU를 독점하지 못하도록** 한다.
- **비동기적** (현재 실행 중인 명령과 무관하게 발생)

#### 흐름
1. 하드웨어 신호 발생
2. CPU 현재 명령 중단
3. 커널 모드 전환
4. 인터럽트 핸들러 실행
5. 복귀

### 시스템 콜
: 사용자 프로그램이 커널 기능을 요청

- 발생시키는 주체: **사용자 코드**
- 예) `FileManager.default.createFile(...)`
  - 내부적으로 syscall 호출 -> 커널 모드 진입 -> 파일 생성 수행

#### 흐름
1. 사용자 코드가 syscall instruction 실행
2. 커널 모드 전환
3. 커널 함수 실행
4. 결과 반환
5. 사용자 모드 복귀

#### 왜 직접 커널 기능을 사용하지 못할까?
CPU에는 privilege level이 존재한다.
- 커널 모드 (ring 0)
- 사용자 모드 (ring 3)
  - 파일 시스템 직접 접근 X
  - 페이지 테이블 수정 X
  - 디바이스 제어 X

### 예외 (동기 인터럽트)
: CPU가 명령어 실행 중 문제 감지 시 발생하는 이벤트

- 발생시키는 주체: **CPU 자체**
- 예)
  - 0으로 나누는 연산
  - 잘못된 메모리 접근
  - Page Fault
  - illegal instruction

#### 흐름
1. 명령어 실행 중 오류 감지
2. CPU가 자동으로 커널 진입
3. 예외 핸들러 실행
4. 복구 or 프로세스 종료

#### 예외는 정상 흐름일까?
- **Page Fault** → 정상 흐름일 수 있음.
  * 메모리 없으면 디스크에서 가져옴.
  * 디스크 접근은 수 ms 단위 → CPU 연산(ns) 대비 **매우 느림**.
- **Segmentation Fault** → 비정상
  * 잘못된 주소 접근

즉 예외는 상황에 따라 정상/비정상 모두 가능하다.

### Trap
: 현재 실행 중인 명령어에 의해 즉시 발생하는 예외

- **CPU가 발생시키는 동기적(synchronous) 예외의 한 종류**
- 현재 실행 중인 명령어와 직접적으로 관련이 있음.
- CPU가 모드 전환을 수행
  - 시스템 콜은 일종의 trap이다.
- 발생시키는 주체: 사용자 코드가 유도하고, 물리적으로는 CPU가 발생시킴.

## 4. 실무 / iOS 연결 지점

### a) 파일 읽기
```swift
try Data(contentsOf: url)
```
1. **URL 해석/브리지**
   * url이 file URL인지 확인
   * 경로 문자열로 변환/정규화(심볼릭 링크, 상대경로 등)
2. **open 계열 시스템 콜**
   * open() / openat() 같은 syscall로 파일 디스크립터(fd) 획득
   * 커널에서:
     * sandbox/권한 검사
     * 파일 존재 확인 및 inode(또는 유사 객체) 찾기
     * 프로세스의 fd 테이블에 엔트리 생성
3. **read 계열 시스템 콜**
   * read(fd, buf, n) 반복 또는 pread류
   * 커널에서 페이지 캐시에 데이터가 있으면 **디스크 접근 없이** 복사만 수행
     * 페이지 캐시에 데이터가 없을 경우
       * 스토리지에 I/O 요청
       * 현재 스레드는 **blocked(sleep)** 상태로 전환
       * I/O 완료 인터럽트가 오면 깨워서 이어서 진행
4. **유저 공간 버퍼 채우기**
   * 커널이 읽은 바이트를 user buffer로 복사
   * Foundation이 필요한 만큼 반복해서 읽어 Data로 구성
5. **close**
   * close(fd)로 fd 반환

### b) 네트워크 요청
1. **socket()**
   * 커널에 소켓 객체 생성
2. **connect()**
   * 원격 IP/port로 연결 요청
   * 커널 TCP 상태 머신 진입
     * SYN 전송 → SYN-ACK 대기 → ACK
   * 보통 connect는 “완료될 때까지 기다리면” 스레드가 blocked 가능
3. **send()/write()**
   * 유저 버퍼의 데이터를 커널 send buffer로 복사
   * 커널이 패킷 단위로 쪼개어 전송 스케줄
4. **recv()/read()**
   * 수신 데이터가 없을 경우 스레드 blocked
   * 데이터 도착 시 커널 recv buffer에서 유저 버퍼로 복사 후 반환
5. **패킷 도착 경로**
   * 무선칩/NIC가 패킷 수신
   * 하드웨어 인터럽트 발생
   * 커널 네트워크 스택이 패킷 처리
   * 해당 소켓을 기다리던 스레드를 runnable로 변경
   * 스케줄러가 CPU를 배정하면 유저 코드가 이어서 recv() 반환

### c) 타이머 기반 RunLoop
1. **(Hardware) 타이머 인터럽트 주기적 발생 (비동기)**
2. **(Kernel) 인터럽트 핸들러 실행**
   - 현재 실행 컨텍스트 저장
   * 커널 모드로 전환
   * 타이머 관련 처리
     * 스케줄링 퀀텀 만료 체크
     * sleep 중인 타이머(예: usleep, timers, dispatch timers) 만료 처리
     * 깨어나야 할 스레드를 runnable로 변경
3. **(Kernel) 스케줄러가 실행/선점 판단**
   - 스레드 변경 시 컨텍스트 스위칭
4. **(User) 메인 스레드가 CPU를 받으면 RunLoop가 이벤트 처리**
   - 메인 스레드가 runnable 상태이고 우선순위/상황이 맞으면 CPU를 받음

### d) 앱 크래시
1. **(User) 문제 발생**
   * 예)
     * null/해제된 포인터 접근 → EXC_BAD_ACCESS
     * 잘못된 명령 실행 → illegal instruction
2. **(CPU) 동기 예외(Exception/Fault) 발생**
   * 현재 명령 실행 중 fault
   * 커널로 트랩
   * 커널이 원인/주소/레지스터 상태를 기록
3. **(Kernel) 예외를 시그널/예외 형태로 프로세스에 전달**
   - 보통 Mach exception(예: EXC_BAD_ACCESS)로 내부 처리
4. **(User) 크래시 핸들러/리포터가 있으면 실행**
5. **(Kernel) 프로세스 종료**
   * 커널이 프로세스 자원 정리
     * 스레드 제거
     * fd 닫기
     * 메모리 매핑 해제
     * PID 회수
