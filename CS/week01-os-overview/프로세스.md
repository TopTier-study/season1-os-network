## 2. 핵심 개념 / 문제

### 프로그램
: 실행 파일을 의미 (실행 전에는 **보조기억장치 내의 정적 데이터**일 뿐임.)

- 작성된 소스 코드 파일이 **컴파일 과정**을 거치면 컴퓨터가 이해할 수 있는 기계어로 번역되어 실행할 수 있는 파일이 된다. -> ‘프로그램’
  - 컴파일 과정
    ```
    소스 코드 파일 -> 전처리 --(컴파일러가 오류 처리, 코드 최적화 작업)-> 어셈블리어 --(어셈블러가 어셈블리어로 작성된 프로그램을 기계어로 변환)-> 목적 코드 --(링커가 필요한 라이브러리 기록 및 심볼 참조 정보 저장, 심볼 테이블 생성)-> 실행 파일(exec)
    ```

### 프로세스
**보조기억장치에 저장된 프로그램을 로더를 통해 메모리에 적재하고 실행**한다. = **‘프로세스를 생성한다’**
( 즉 프로세스란 = 주기억장치에 올라간 프로그램이 CPU에 의해 처리되는 상태 )

#### 개념 추가
- 프로세서가 할당되는 개체로서 디스패치가 가능한 단위
  - **디스패치**: 여러 프로세스들 중 한 프로세스를 선정하여 CPU에 할당하는 과정
    - 프로세스가 ready -> running으로 상태 전이
- 운영체제가 관리하는 최소 단위의 작업
- 프로그램과 달리 메모리에 주소 공간을 갖는 능동적 객체
- 프로그램이 인스턴스화된 형태

#### 특징
- 계층적 구조
  - 프로세스는 실행 도중 시스템 호출을 통해 다른 프로세스를 생성할 수 있음.
    - **fork** 시스템 호출 -> 부모 프로세스가 자신의 **복사본**을 자식 프로세스로 생성 (iOS는 Copy-on-Write 사용)
      - 메모리 내 내용 동일
      - **PID**와 **저장된 메모리 위치**는 다름
    - **exec** 시스템 호출 -> 자신의 메모리 공간을 새로운 프로그램으로 **덮어씀**.
      - 코드, 데이터 영역: 실행할 새 프로그램의 내용으로 변화
      - 힙, 스택 영역: 초기화
      - 자식 프로세스가 exec를 호출하지 않는 경우 부모와 자식은 같은 코드를 병행하여 실행하는 프로세스가 됨.
- 각 프로세스마다 고유 PID를 가짐.
- 프로세스는 `new, ready, running, blocked, terminated` 상태를 가짐.
  - new: 프로그램이 메모리에 적재되어 PCB를 할당받은 상태
- 운영체제는 프로세스마다 고유의 가상 메모리 공간 제공
  - 코드, 데이터, 힙, 스택 영역으로 세분화
- 프로세스 생성 시마다 고유의 PCB 생성, 프로세스 종료 시 PCB는 제거됨.
  - **PCB(Process Control Block)**: 프로세스와 관련된 정보, 즉 하나의 프로세스 수행을 재개하기 위해 기억해야 할 정보(문맥)를 저장하는 자료 구조 (커널 영역에 저장)
- 포그라운드 프로세스, 백그라운드 프로세스로 나뉨.
  - OS 관점에서의 구분 기준은 UI 여부가 아닌, **입력 제어권** & **이벤트 수신 권한** & **활성 실행 컨텍스트**이다.
  - 포그라운드 프로세스: 시스템의 입력 스트림(키보드, 마우스, 터치 등)과 이벤트 디스패치의 우선 대상이 되는 프로세스
  - 백그라운드 프로세스
    - 포그라운드와 달리 사용자와 직접적인 상호작용을 하지는 않지만(사용자 입력 장치 직접 점유 X), **간접적인 방식으로 상호작용**할 수 있음.
      1. 간접 상호작용: 사용자는 UI 앱이나 다른 프로세스를 통해 접근할 수 있음. 로그 출력, 파일 생성, 소켓 통신 등 (예시: 서버 프로세스, 데몬 등)
      2. 시그널 기반 상호작용: `kill -SIGSTOP pid`와 같이 실행 제어
      3. UI 없는 상호작용: CLI 입력 없이 설정 파일 수정, 소켓 요청, API 호출 등의 방법으로 상호작용
    - **macOS** (유닉스 모델 기반): launchd 데몬 (최초 실행 프로세스) 등
    - **iOS**: 시스템 서비스, 백그라운드 작업 등
      - iOS는 **배터리 성능이나 공유 자원을 고려하여 백그라운드에서 실행되는 앱의 런타임을 제한**하고 있음.

## 1) 프로그램 파일이 어떻게 프로세스로 변환될까?
### 1-a. 선제 질문: 실행 파일은 무엇일까?
디스크에 있는 실행 파일은 단순한 코드 덩어리가 아니라 **실행 가능한 메모리 구조 설계도**이다.

- 실행 파일 구조
  - 기계어 코드
  - 초기 데이터
  - 읽기 전용 데이터
  - 심볼 테이블
  - 로딩 정보
  - 링킹 정보
  - 메타데이터

 운영체제는 일반 바이트 파일을 바로 실행할 수 없기 때문에 Executable Format이 필요하다.
(어디가 코드인지, 데이터인지, 어디부터 실행할지, 무엇을 추가로 로딩해야 하는지 알아야 함.)

- **Executable Format**: 디스크에 있는 코드와 데이터가 어떤 구조로 메모리에 배치될지 정의한 규칙
  - 이 구조는 실질적으로 **메모리 사용량, 페이징 동작, 디스크 접근, 런치 성능에 직접적인 영향**을 줌.


### 🍎 Mach-O (Mach Object file format)
: macOS / iOS에서 사용하는 실행 파일 포맷 (Executable Format)

> - Mach: 커널 중 하나
> - Mach-O: 마이크로 커널(운영체제에 요구되는 최소한의 매커니즘을 제공하는 초소형 커널)의 초기 예시로 언급됨. 그러나 모든 Mach 버전이 마이크로 커널인 것은 아님.
> - macOS, iOS, iPadOS, tvOS, watchOS에 사용되는 Apple의 XNU가 Mach를 기반으로 함.
>   - XNU(X is Not Unix): Apple에서 만든 운영체제 커널
> (참고: https://zeddios.tistory.com/908)

#### Mach-O 구조
![](%E1%84%91%E1%85%B3%E1%84%85%E1%85%A9%E1%84%89%E1%85%A6%E1%84%89%E1%85%B3/Mach-O%20%E1%84%80%E1%85%AE%E1%84%8C%E1%85%A9.png)

- **Segment**
  - 메모리 매핑 단위
  - 페이지 단위 정렬
    - 이유: 가상 메모리와 직접 연결되기 때문이다. (운영체제는 페이지 단위로 로딩, 보호, 교체, 공유를 수행)
  - Segment 크기는 페이지 단위 (4KB 배수)
  - 성능 관점에서의 핵심 2개: __TEXT Segment (Read Only), __DATA Segment (Read / Write)
- **Section**
  - 코드 / 데이터를 논리적으로 구분함.
  - 페이지 할당이 강제되지 않음.
  - Segment 내부 구성 요소

#### __TEXT Segment (Read-only)
: 실행 코드, 상수, 문자열 등을 포함하는 읽기 전용 영역

- 주요 Section:
  - __text: 실행 파일에 대한 컴파일된 기계 코드
  - __const: 실행 파일에 대한 일반 상수 데이터
  - __cstring: 리터럴 문자열 상수 (소스 코드에서 인용된 문자열)
- **여러 프로세스 간 공유 가능**
- 메모리 부족 시 그냥 버리고 필요 시 디스크 재로드 (Swap보다 비용 ↓, 그러나 디스크 접근 비용이 발생함.)
  - **문제**: 코드 페이지가 자주 버려지고, 다시 디스크에서 읽다보니 디스크 접근 비용이 증가함.
  - **해결 전략**: **Locality of Reference** (같이 실행되는 코드끼리 같은 페이지에 배치하기)

#### __DATA Segment (Read & Write)
: 전역 변수, 초기화된 데이터, 초기화되지 않은 데이터가 포함되는 영역

- 주요 Section:
  - __data: 초기화된 데이터
  - __bss: 초기화되지 않은 데이터 (런타임에 0으로 초기화)
- 공유 불가
- Copy-on-Write
- 프로세스 별로 독립되어 있음.
- 프레임워크의 전역 변수가 많으면 프로세스마다 복사 비용과 메모리 사용량 증가 (페이징 부담 증가)
  - **문제**: 쓰기가 가능하기 때문에 공유가 불가하고, 전역 변수가 많을 시 메모리 낭비가 발생함.
  - **해결 전략**: const(상수) 적극 활용 (변경되지 않는 데이터는 __TEXT에 저장될 수 있도록 하기 `const int value = 10;`)

#### 추가 Optional Segments
- Symbol Table: 함수명, 전역변수명 등 심볼의 이름과 주소를 매핑하는 테이블
- String Table: 심볼의 이름 등 문자열 정보가 저장되는 테이블

#### 1) Executable
: 프로세스로 실제 실행 가능한 메인 바이너리

- Loader가 직접 처리하는 대상
  - 독립적인 주소 공간을 가짐.
  - 운영체제가 실행한다는 것은 **Entry Point가 필요**하고 **프로세스가 생성 가능**해야 한다.
  - 이를 제외한 다른 옵션 Mach-O Type으로 설정할 시 직접 실행 불가능
    - 라이브러리는 Entry Point, 독립 실행 흐름이 없음. (호출 당하는 코드가 X)
- 프로세스 생성 과정에서의 중심이 됨.

#### 2) Dynamic Library (dylib / Framework)
: 독립 실행 불가능, 다른 Executable에 의해 로딩되는 코드 모듈

- Runtime Linking 대상
- 프로세스 생성 시
  - Loader / dyld에 의해 메모리 매핑
  - **__TEXT 영역 공유**
    - Dynamic Library는 여러 프로세스가 동일 파일을 참조하고 시스템 전체에서 재사용함. -> 공유 특성 중요
    - Executable 타입도 TEXT 영역을 기술적으로 공유할 수 있지만 보통 다른 프로세스가 같은 Executable을 사용하지 않음.
  - __DATA 영역 Copy-on-Write 적용
- Dynamic Linking은 주로 런치 시점에서 발생 -> 런치 시간에 영향

#### 3) Static Library
: Runtime에 존재하지 않고 빌드 시점에 Executable 내부로 포함되는 코드

- Loader 입장에서 별도의 개체가 아님.
  - Runtime Linking X (빌드 시점에 링크)
  - 추가 로딩 X
  - 독립 매핑 X

#### 4) Bundle
: 실행 목적이 아닌 리소스 제공

- 링크 대상 X, 런타임에 로드됨.
- Bundle은 프로세스 생성 대상이 아님.
  - Entry Point X
  - 실행 흐름 X
  - Loader 실행 대상 X
- 실행 개체(Executable)와 리소스 개체(Bundle)을 분리하는 데에 의미가 있음.

#### 5) Relocatable Object File
: 링킹 이전 상태의 오브젝트 파일(.o)

- 최종 메모리 주소가 확정되지 않은 상태의 바이너리 -> 실행 불가
- Loader 처리 대상 X
- 링커에 입력되는 재료 개념
  - 개발자가 직접 설정하는 일은 별로 없지만 .o 파일을 개별적으로 디버깅하여 빌드 에러를 해결해야할 때 사용할 수 있음.

#### Loader의 대상이 되는 옵션
- Executable: 프로세스 생성
- Dynamic Library: 이미 존재하는(생성한) 프로세스 주소 공간 안으로 들어감.

### 1-b. 프로그램 -> 프로세스 변환 과정
#### 1. 사용자가 실행 요청
- 아이콘 클릭
- exec 호출
- 앱 런치

#### 2. 운영체제가 Loader 호출
- **Loader**: 실행 파일을 실제 프로세스로 만드는 주체
  - Loader가 하는 일
    1. 가상 주소 공간 생성 (코드, 데이터, 힙, 스택, 라이브러리 영역 포함)
    2. 실행 파일을 메모리에 매핑
       - 이때 파일을 메모리에 다 복사하는 것이 아니라 메모리 매핑 후 **필요한 페이지만 로딩**하는 방식으로 진행된다.
    3. 코드 / 데이터 배치 (세그먼트 매핑)
    4. Entry Point(실행 시작 지점) 설정 
    5. Dynamic Linking 환경 구성
       - 라이브러리 매핑 준비
       - 심볼 해결 구조 준비

#### 3. Dynamic Linking 수행
- 실행 시점(Runtime)에 라이브러리를 연결하는 과정
  - (컴파일 시점에는 링킹 정보만을 기록하고 실제 연결은 진행하지 않는다.)
  - 런치 시점에 Dynamic Linking 비용이 증가할 수 있음.
    - 💭 **런치가 느려지는 이유가 무엇일까?**
      - 로딩 대상 증가
      - 심볼 해결 작업 증가
      - 초기 메모리 매핑 증가
      - 디스크 접근 증가 가능성
      - Page Fault 증가 가능성
    - **💭 모든 코드를 static linking 하면 속도가 빨라질까?**
      - Static Linking은 실행 파일 내에 라이브러리 코드가 저장되기 때문에 메모리 소모가 매우 크다. 따라서 런치 시 Linking 비용이 감소하기는 하지만 메모리 관점에서 매우 비효율적일 수 있다. (속도와 메모리 효율의 trade-off)

## 2) 같은 코드가 여러 프로세스에서 실행되면 메모리는 복사될까?

### 1. 코드 영역(TEXT)
같은 실행 파일 또는 동일한 시스템 라이브러리를 여러 프로세스가 사용하더라도 코드 영역은 **복사되지 않고 공유**된다.

#### 이유
- 코드 영역은 Read-only
- 변경되지 않으므로 이는 복사할 필요가 X
- 운영체제는 메모리 매핑을 통해 **하나의 물리 메모리 페이지를 여러 프로세스의 가상 주소 공간에 매핑**한다.

#### 결과
- 물리 메모리 사용량 절감
- 코드 중복 로딩 방지

### 2. 데이터 영역(DATA)
데이터 영역은 Writable 특성을 가지므로 **프로세스 별로 분리**된다.

#### 이유
- 전역 변수, 상태 데이터는 변경 가능
- 따라서 프로세스 간 상태 간섭 방지가 필요하다.

#### 동작 방식
- 초기에는 공유 가능
- 쓰기 발생 시 **Copy-on-Write** 적용
- 해당 프로세스에만 메모리 복사 발생

> 따라서 **여러 앱이 동일한 시스템 라이브러리를 사용하는 경우**에도 위의 원칙이 적용된다. 이를 통해 메모리 효율성과 시스템 안정성을 동시에 확보할 수 있다.

## 3) 다중 프로세스 구조
### 목적
#### 1. 안정성
- 프로세스가 분리될 경우
  - 렌더링 크래시 ≠ 브라우저 크래시
  * 플러그인 오류 ≠ 메인 앱 오류
  * Helper 크래시 ≠ 전체 앱 종료
- 예) Chrome / Safari
  - 탭별 프로세스
  - Renderer 프로세스 분리
  - -> **일부 탭이 크래시나는 경우에도 전체 브라우저는 유지됨.**

(safari 다중 프로세스 확인)

#### 2. 격리
- 프로세스는 기본적으로 **독립적인 메모리 공간과 자원**을 가진다.
- 따라서 권한과 오류 영향 등이 격리된다.
- 운영체제가 각 프로세스를 더 정밀하게 제어할 수 있다.
  - CPU 스케줄링 분리
  - 메모리 압박 대응 용이
  - 우선순위 조정 가능
  - 필요 시 부분 종료 가능

#### 3. 보안
- 예) 브라우저
  - Renderer 프로세스 - 제한 권한
  - 메인 프로세스 - 높은 권한
  - -> **취약점 발생 시 전체 시스템 권한이 탈취되는 것을 방지할 수 있음.**

#### 4. 병렬성
- 멀티코어 환경 최적화
  - 예) 렌더링 / 네트워크 / GPU 작업 분리

### iOS에서 다중 프로세스 구조가 제한적인 이유
1. 모바일 환경의 물리적 제약
   - 프로세스 생성 시 독립 주소 공간, 페이지 테이블, 스케줄링 엔트리 등이 필요함.
   - 즉 프로세스 수가 증가할수록 시스템 부담이 증가함.
   - 이는 제한된 메모리, 배터리, CPU 자원을 가진 모바일 환경에서 물리적으로 제약이 있을 수 밖에 없음.
2. 메모리 비용
   - 프로세스마다 독립적인 데이터, 스택, 힙 영역이 필요함.
   - 모바일에서는 메모리 효율이 중요함.
   - 따라서 **iOS 앱을 설계할 때에는 프로세스를 남발하지 않아야** 함.
3. 배터리 효율
   - 프로세스 증가 시 컨텍스트 스위칭, 스케줄링 오버헤드 증가
   - -> Energy Impact 증가
4. 앱 생명주기 모델과의 충돌
   - iOS 앱은 언제든 terminate가 가능한 구조임.
   - 백그라운드 실행 제한적
   - 시스템이 적극적으로 메모리를 회수함.
   - -> 다중 프로세스 구조인 경우
     - 관리 복잡도 증가
     - kill / suspend 시 상태 일관성 문제 증가

-> iOS에서 다중 프로세스가 불가능하지는 않지만 **시스템이 허용한 형태**로만 가능하다.
- Extension (Widget / Intent 등)
- 시스템 프레임워크 내부 구조
(공통적으로 OS가 생명주기를 관리하고, 자원 사용에 제한이 있다는 특징이 있음)

### IPC (Inter-Process Communication, 프로세스 간 통신)
: 서로 다른 프로세스 간 정보를 주고 받는 통신 방식

- 프로세스는 독립적
- 다중 프로세스 환경에서는 다른 프로세스와 정보(데이터)를 주고받는 IPC가 필수적으로 요구됨.

#### 1. 메시지 전달 방식
: 서로 독립된 공간에 있는 프로세스들이 자원을 공유하기 위해 **커널에 있는 공유 공간**을 활용하여 데이터를 주고 받는 방식

- 직접 통신: 프로세스가 공유하고자 하는 자원을 커널의 메시지 큐로 전달하면 **커널이 직접 그 자원이 필요한 프로세스에게 전달**
- 간접 통신: 프로세스가 공유하고자 하는 자원을 커널의 메시지 큐로 전달하면 **그 자원이 필요한 프로세스가 직접 커널에서 읽음**
- 메시지 전달 시마다 운영체제가 개입하기 때문에 커널 의존성 ↑, 속도 ↓
  - 그러나 자원 동기화 문제 발생 X (커널이 관리하기 때문에)

#### 2. 공유 메모리 방식
: 프로세스들이 **주소 공간의 일부를 공유**하는 방식

- 공유 메모리 할당 시스템 콜 -> 커널이 해당 프로세스에 메모리 공간 할당 -> 어떤 프로세스든 해당 메모리 영역에 접근 가능
- 중간 관리자가 없기 때문에 속도 ↑
- 동기화 문제 발생 가능


## 4. 실무 / iOS 연결 지점 

### 1) 앱 프로세스 강제 종료(kill) 대비하기
#### 문제 상황
운영체제는 메모리 압박 시 프로세스를 강제로 종료할 수 있고, 이는 예측이 불가능하다.

#### 전략
- **복원해야 하는 상태 영속화**하기
  - 사용자 생성 데이터(작성 중 텍스트 등), 업무 진행 상태, UI 상태(마지막으로 보던 화면) 등을 로컬 DB, UserDefaults, 임시 스냅샷 등을 활용하여 저장할 수 있다.
- 중요한 데이터는 즉시 저장하는 구조로 설계하기
  - 저장 시점 예시
    - **사용자 입력 이벤트 단위**: 사용자가 텍스트를 편집할 때/토글을 변경할 때
    - **life-cycle 이벤트**: 백그라운드 진입 시점 등
    - **비동기 작업 완료 단위**
  - 예) 사용자가 텍스트를 입력할 때 디바운스를 적용하여 자동으로 저장되도록 설계하고, 프로세스가 강제 종료된 후 재실행할 때 **이전에 작업하던 내용을 복구할 수 있도록** 하기
- 재실행되어도 안전한 구조로 설계하기 (위의 예시도 포함)
  - 예) 업로드 요청을 재전송하는 경우에도 **중복 생성되지 않도록** 서버에서 id 기준으로 처리하도록 구현
- 초기화 비용 최소화하기
  - 초기화 비용을 늘리는 요인 예시
    - DIContainer에서 무거운 객체를 런치 시점에 전부 생성
    - 큰 데이터 전체 로딩/정렬
    - 네트워크 동기 호출
  - 최소화 전략
    - **Lazy Init**
    - **Warm Cache**: 첫 화면에 필요한 최소 데이터만 먼저 로드하고, 나머지는 백그라운드에서 단계적으로 로드하는 방식
    - 리스트는 **페이징/부분 로딩**
    - 네트워크 **비동기 호출** & **placeholder** 활용
