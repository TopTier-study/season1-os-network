## 탐구 내용

### 컴퓨터 시스템의 구성

- 하나 이상의 CPU + 여러 개의 Device Controller들이 시스템 버스를 통해 메모리를 공유하는 형태로 구성
- **Memory Controller**
    - CPU와 Device Controller들은 병렬적으로 실행될 수 있으므로 메모리에 대한 순차 접근을 보장하기 위해 이들의 접근을 동기화함.
- **Device Controller**
    - 특정 하드웨어 장치를 직접 제어하는 전자 회로 또는 장치.
    - 컨트롤러의 종류에 따라, 하나의 컨트롤러에 여러 개의 디바이스가 붙을 수 있음 (ex: USB 허브를 통해 USB 컨트롤러에 여러 개 연결)
- **Device Driver**
    - 각각의 Device Controller는 그에 대응하는 Driver를 가짐
    - 운영체제와 하드웨어 장치 사이에서 중계 역할을 하는 소프트웨어.
        - 컨트롤러에 명령을 보내고, 상태를 받아 OS에 전달
    - 운영체제가 하드웨어를 제어할 수 있도록 공통적 인터페이스 제공

### 입출력 연산 수행 과정을 통해 Interrupts 개념 이해하기

보통의 입출력 연산을 수행한다고 생각해보자.

<img width="635" height="208" alt="image" src="https://github.com/user-attachments/assets/5d551ffa-b515-4696-8a74-e212eb806eb2" />


1. os 또는 응용프로그램에서 입출력 요청이 내려오면 
2. 드라이버는 명령을 컨트롤러의 적절한 레지스터에 로드한다.
3. 컨트롤러는 레지스터에 적재된 명령을 읽고 파악한 뒤 장치 내부 동작을 시작하고, 필요한 경우 장치에 있는 데이터를 장치의 로컬 버퍼로 옮긴다.
4. 컨트롤러가 명령 수행을 완료하면 드라이버에게 완료 사실을 알려준다. 
    - 여기서 드라이버가 받는 신호가 바로 **인터럽트(Interrupt) 개념**이다.
    - 인터럽트는 **하드웨어 → 소프트웨어로 알림**을 주는 신호
    - 인터럽트가 발생하면 CPU는 현재 수행 중인 작업을 잠시 멈추고 **인터럽트 처리 루틴(ISR)을 실행**
5. 드라이버 처리 후 OS/응용 프로그램에 반환
    - 드라이버는 인터럽트를 통해 알림을 받고, **장치 로컬 버퍼에서 OS가 접근 가능한 메모리로 데이터 복사**를 수행한다.
    - 읽기 연산의 경우, 드라이버는 데이터를 가리키는 포인터를 OS나 애플리케이션에 반환한다.
    - 제어권이 다시 OS의 다른 프로세스나 애플리케이션으로 넘어간다.

### 인터럽트 개요

- 하드웨어 장치는 **인터럽트 라인을 통해 CPU에 인터럽트 신호를 발생시킬 수 있다.**
- CPU가 인터럽트를 수락하면,
    
    **현재 실행 중이던 프로그램의 상태를 저장한다.**
    
    - 프로그램 카운터(PC)
    - 프로세서 상태 레지스터(플래그)
    - 필요 시 일부 일반 레지스터
- 그 다음, CPU는
    - 해당 인터럽트에 대응하는 인터럽트 서비스 루틴(Interrupt Service Routine, ISR)의 주소를 찾아
    
    그 위치로 실행을 이동한다.
    
- ISR이 실행되어 인터럽트 원인을 처리하고 나면,
    
    CPU는 저장해 두었던 상태를 복원하고
    
    **중단되었던 명령부터 다시 실행을 재개한다.**
    

---

**인터럽트 핸들러가 호출되는 방식**

- 인터럽트는
    
    **빠르고 빈번하게 발생할 수 있기 때문에**,
    
    각 인터럽트에 대해 직접 분기하지 않고
    
- **인터럽트 벡터 테이블(Interrupt Vector Table)** 을 사용하여
    
    **간접적으로 인터럽트 처리 루틴을 호출한다.**
    

---

**인터럽트 벡터 테이블**

- 인터럽트 벡터 테이블은
    - 각 인터럽트 번호에 대응하는
    - **ISR의 시작 주소를 저장한 테이블**이다.
- 특징
    - 인터럽트는 **고유한 번호(벡터 번호)** 를 가진다.
    - 이 번호를 인덱스로 사용하여 해당 ISR 주소를 테이블에서 찾는다.
    - 이 테이블은 보통 **미리 정해진(낮은 주소 영역의) 메모리 위치**에 존재한다.

---

### 인터럽트 처리 매커니즘

- 장치 컨트롤러는 interrupt-request line에 신호를 보냄으로써 인터럽트를 발생시킨다.
- CPU는 인터럽트를 받아서, 인터럽트 핸들러에 전달한다.
- 인터럽트 핸들러는
    - 상태를 저장해두었다가, 인터럽트의 원인을 결정하고, 적절한 처리를 수행하며 상태를 복원한다.
    - return_from_interrupt 명령어를 실행해 CPU를 인터럽트 이전의 실행 상태로 되돌린다.

하지만 현대 운영체제에서는 보다 정교한 인터럽트 핸들러 기능이 필요하다.

- 중요한 처리중일 때는 인터럽트 처리를 지연 또는 차단할 수 있어야 한다.
- 발생한 인터럽트를 해당 장치에 맞는 인터럽트 핸들러로 빠르게 전달해야 한다.
- 여러 인터럽트가 비동기적으로 발생할 수 있으므로, 운영체제가 우선순위에 따라 인터럽트를 구분하고 긴급한 정도에 따라 처리할 수 있어야 한다.

현대 컴퓨터 하드웨어에는 위 세 가지의 기능을 **CPU와 interrupt-controller hardware를 통해 제공**한다.

**Interrupt Controller**

- 여러 장치에서 들어오는 인터럽트 요청을 모아서 우선순위를 판단하고 CPU에 전달할 인터럽트를 선택하는 하드웨어이다.

**Maskable vs Non-Maskable Interrupts**

- 대부분의 현대 컴퓨터 CPU는 논리적으로 두 종류의 인터럽트 라인을 구분한다.
- **Maskable**
    - CPU에 의해 **일시적으로 무시(마스크)** 될 수 있는 인터럽트
    - 중요한 임계 구간(critical section)이나 커널 내부 처리 중에
        
        인터럽트를 차단하기 위해 사용된다.
        
- **Non-Maskable**
    - 하드웨어의 치명적 오류, 복구 불가한 메모리 오류와 같이 무시될 수 없는 인터럽트

---

**벡터화된 인터럽트 매커니즘의 목적**

- 단일 인터럽트 핸들러가 어떤 처리를 해야하는지 알기 위해 모든 가능한 인터럽트 소스를 탐색하는 것을 줄이는것 (인덱스를 통해 접근)
- 그러나 보통 컴퓨터는 인터럽트 벡터 테이블에 있는 주소들보다 많은 수의 장치를 가짐
    - 여러 장치에서 인터럽트가 들어올 때, 겹칠 수 있음 (같은 인터럽트 벡터 공유)
    - **Interrupt chaining** 으로 해결
        - 하나의 벡터에 여러 핸들러를 체인 형태로 연결하고, 각 요소들이 인터럽트 핸들러의 시작 주소를 가리키는 것.
        - 벡터 테이블 크기 증가에 따른 오버헤드와 모든 인터럽트를 단일 핸들러로 처리하는 것에 대한 비효율 사이의 절충안.

---

**Interrupt priority levels**

- 인터럽트가 우선순위 레벨을 가지는 것
- 레벨 값들은 CPU가 모든 인터럽트를 무시하지 않고도 낮은 우선순위의 인터럽트 처리를 지연할 수 있게하고, 높은 순위의 인터럽트가 선점하여 처리될 수 있게함

---

### Storage Structure

- CPU는 명령어를 메모리에서 로드해오므로, 어떤 프로그램이든 메모리에 저장되어야 한다.
- 범용 목적 컴퓨터는 대부분의 프로그램들을 다시 쓰기 가능한 메인 메모리에서 실행한다.
- 메인 메모리는 DRAM이라 불리는 반도체 기술을 통해 구현된다.
- **Bootstrap program**
    - 컴퓨터 전원을 켰을 때 첫 번째로 실행되는 프로그램, 실행되면 운영체제를 메모리에 올리고 제어권을 넘긴다.
    - RAM은 휘발성 메모리이므로 전원이 꺼지면 사라져 부트스트랩 프로그램을 저장할 수 없다.
    - 따라서 컴퓨터는 해당 프로그램을 저장하기 위해 EEPROM(Electrically erasable programmable read only memory)에 저장된 쓰기 빈도가 낮고 비휘발성인 저장소 펌웨어를 사용한다.
    - **EEPROM(Electrically Erasable Programmable Read Only Memory)**
        - 수정될 수 있지만, 자주 변경되지 않음
        - 속도 느림, 따라서 사용 빈도가 낮은 정적 프로그램이나 데이터를 포함
        - 아이폰은 기기의 시리얼 넘버와 하드웨어 정보를 저장하는데에 EEPROM을 사용함

### 전형적인 명령 실행 사이클

- **폰 노이만 구조 기반**(CPU, 메모리, 입출력 장치가 하나의 공통 버스로 연결되어, 프로그램(명령어)과 데이터를 동일한 메모리에 저장하고 순차적으로 처리하는 현대 컴퓨터의 기본 설계 방식)
- 메모리에서 명령어를 fetch, 명령어를 레지스터에 store
- 해석된 명령어에 맞는 연산자를 메모리로부터 fetch 해오고 내부 레지스터에 저장함
- 연산이 실행된 후, 연산 결과는 다시 메모리에 store

---

### Secondary Storage

- 우리는 이상적으로 모든 프로그램과 데이터가 영구적으로 메인 메모리에 존재하는 것을 원함
- 그러나 메인 메모리 크기의 물리적 한계와 비휘발성때문에 어려워, 대부분의 컴퓨터는 보조 저장 장치를 제공함.
- 메인 메모리를 확장하는 개념으로, 많은 양의 데이터를 영구적으로 저장하는 것을 목적으로 함.
- 메인 메모리에 비해 속도가 느려서, 보조 저장 장치에 대한 적절한 관리가 중요

**종류**

- HDD(Hard-dist drives)
- NVM(Nonvolatile memory)

---

### Tertiary Storage

- 더 많은 양의 데이터를 저렴하게 장기 보관하기 위한 저장 계층
- 매우 느림, 백업 / 보관용으로 사용

**종류**

- Optical disk
- Magnetic tapes

**Volatile vs Nonvolatile**

- Volatile Storage
    - 전원이 꺼지면 내용도 사라짐, 보통 메모리라고 나타냄
- Nonvolatile Storage
    - 전원이 꺼져도 내용을 유지함.
    - **Mechanical:**  HDD, optical disks, holographic storage, magnetic tape
        - 더 크고, 저렴하며, 느림.
    - **Electrical:** flash memory, FRAM, NRAM, SSD

### I/O Structure

- 신뢰성, 시스템 성능에 대한 중요도와 장치들의 다양한 특성들 때문에 운영체제의 큰 부분은 입출력을 관리하기 위해 존재함

**DMA(Direct Memory Access)**

- 컴퓨터는 버스를 통해 다양한 장치들 사이에 데이터를 전달하는데, 이때 CPU가 직접 작은 단위로 반복 전송하는 방식은 데이터의 크기가 작다면 괜찮지만 크면 오버헤드가 커진다.
- 해당 문제를 해결하기 위해 **I/O 장치와 메모리 사이의 데이터 전송을 CPU가 아닌 전용 하드웨어가 수행**하는 DMA 방식이 등장했다.
- 입출력 장치에 대한 버퍼, 포인터, 카운터를 세팅한 후 DMA 엔진은 **데이터 블록 전체를 장치와 메인 메모리 사이에서 직접 전달**한다.
- 데이터 블록 전송이 끝나면, 엔진은 드라이버에게 **블록마다 한 번의 인터럽트**로 연산 완료를 알린다.
- 엔진이 이 연산을 수행하는 동안, CPU는 해당 작업에 묶이지 않고 다른 작업을 수행할 수 있다.
- 일부 고성능 시스템에서는 전통적인 공유 버스 구조 대신 **스위치 기반 인터커넥트(switch-based interconnect)**를 사용하여 여러 컴포넌트가 동시에 통신할 수 있도록 한다.
