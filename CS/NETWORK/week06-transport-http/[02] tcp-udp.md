### 네트워크 계층의 한계와 전송 계층의 역할

#### 네트워크 계층의 IP

IP는 신뢰성 있는 전송보다 빠른 전송이 우선시되므로 아래와 같은 특징을 가진다.

- 비신뢰성: 패킷이 수신지까지 제대로 전송되었다는 보장을 하지 않는다. 통신 과정에서 패킷의 데이터가 손상되거나 중복되어도 확인을 하지 않고, 재전송도 하지 않으며, 순서대로 도착한다는 보장도 하지 않는다. (최선형 전달)
- 비연결성: 송수신 호스트 간에 사전 연결 작업을 거치지 않는다.

ICMP

- IP의 비신뢰성을 해결하는 게 아니라 보완하기 위해 나온 프로토콜. 전송 과정에서 발생한 오류 보고와, 네트워크에 대한 진단 정보를 포함한다.
- 네트워크 상의 간단한 문제 진단이나 테스트를 위해 사용되는데, ping, traceroute, tracert 등의 명령어가 해당 프로토콜을 기반으로 동작한다.

#### 전송 계층

- 신뢰성 통신
    - TCP는 신뢰성있는 전송을 위해 재전송 매커니즘을 통해 오류 제어, 흐름 제어, 혼잡 제어 등의 다양한 기능을 제공한다.
    - UDP는 전송 계층에서 신뢰성보다 성능을 우선시해야 할 경우 사용될 수 있다.
- 연결형 통신
    - TCP를 통해 지원, 데이터 송수신 전에 연결을 수립하고, 송수신하는 동안에는 연결을 유지하다가 송수신이 끝나면 연결을 종료한다.
- 응용 계층과의 연결 다리
    - 라우팅을 통해 컴퓨터로 도착한 패킷은 응용 계층의 특정 어플리케이션에 전달되어야 하는데, 이때 포트라는 개념을 통해 정확한 어플리케이션에 패킷이 전송될 수 있다.
    - NAPT(포트 기반 NAT)
        - NAPT를 통해 하나의 공인 IP를 여러 사설 IP가 공유할 수 있다.
        - NAPT는 [내부 IP : 내부 포트]와 [공인 IP : 변환된 외부 포트]를 매핑하여 테이블에 기록한다.
        - 따라서 외부에서 봤을 때 같은 IP를 가지더라도 포트 번호가 다르기 때문에 호스트를 식별할 수 있게된다.
    - 포트 포워딩
        - 하나의 공인 IP를 여러 사설 IP가 공유할 경우, 외부에서 내부 네트워크에 처음 패킷을 전송할 때외부에서는 어떤 호스트로 보내야할 지 알 수 없다.
        - 포트 포워딩 설정을 통해 어떤 [공인 IP 주소 : 외부 접속 포트]에서 접근했을 때, 어떤 [사설 IP: 내부 전달 포트]로 전달할 지 정의해둘 수 있다.

### 전송 계층의 핵심 프로토콜, TCP (Transmission Control Protocol)

신뢰할 수 있는 통신을 위한 연결형 전송 계층 프로토콜

#### Segment

- TCP 프로토콜의 전송 단위, TCP 헤더와 페이로드(TCP MSS)로 이루어진다.

**TCP 헤더가 포함하는 것**
<img width="580" height="322" alt="image (1)" src="https://github.com/user-attachments/assets/74d01d25-ba17-40f1-83e9-4644def78bf4" />



- 송/수신 포트: 송수신지 호스트의 특정 어플리케이션을 식별
- 순서 번호 (Sequence number)
    - 데이터가 MSS 단위의 여러 세그먼트로 쪼개져서 전송될 때, 송수신되는 세그먼트의 순서를 보장하기 위한 번호
    - `초기 순서 번호(랜덤) + 송신한 바이트 수`
- 확인 응답 번호 (Acknowledgment number)
    - 상대 호스트가 보낸 세그먼트에 대한 응답으로 보통 다음으로 수신하길 기대하는 순서 번호를 명시한다. (다음으로 1번 세그먼트 보내줘!)
    - `수신한 순서 번호 + 1`
- 제어 비트: 현재 세그먼트에 대한 부가 정보로, 8비트로 표현
    - `ACK:` 세그먼트 승인을 나타내는 비트
    - `SYN`: 연결 수립을 위한 비트
    - `FIN`: 연결 종료를 위한 비트
- 윈도우: 한 번에 수신하고자 하는 데이터의 크기(수신 윈도우의 크기)

#### TCP 연결 수립/종료 단계

**3-way handshake (연결 수립)**

- Active open: 연결을 처음 요청하는 호스트의 동작
- Passive open: 연결 요청을 받고 나서 연결을 수립해주는 호스트의 동작

**4-way handshake (연결 종료)**

- Active close: 연결을 종료하려는 호스트의 동작
- Passive open: 연결 종료 요청을 받아들이는 호스트의 동작

#### TCP 상태

TCP는 신뢰할 수 있는 통신을 유지하기 위해 ’상태’를 유지하고 활용하는 `Stateful`프로토콜이라고 할 수 있다.

- 연결이 수립되기 전의 상태
    - `CLOSED` : 아무런 연결이 없는 상태
    - `LISTEN` : 일반적으로 서버로 동작하는 패시브 오픈 호스트는 연결을 대기하고 있는 `LISTEN` 상태를 유지한다.
- 연결 중인 상태
    - `SYN-SENT` : 액티브 오픈 호스트가 SYN을 보내고 그에 대한 ACK를 기다리는 상태
    - `SYN_RECEIVED` : 패시브 오픈 호스트가 SYN+ACK를 보내고 그에 대한 ACK를 기다리는 상태
    - `ESTABLISHED` : 연결이 수립된 상태. 3-way 핸드셰이크가 끝나면 두 호스트는 해당 상태가 된다.
- 연결 종료 상태
    - `FIN_WAIT-1` : 액티브 클로즈 호스트가 FIN을 보내고 그에 대한 ACK를 기다리는 상태
    - `CLOSE_WAIT` : 패시브 클로즈 호스트가 FIN에 대한 ACK를 보내고 기다리는 상태
    - `FIN_WAIT-2` : 액티브 클로즈 호스트가 ACK를 받고 나서 상태의 FIN 세그먼트를 기다리는 상태
    - `LAST_ACK` : 패시브 클로즈 호스트가 FIN을 보내고 그에 대한 ACK를 기다리는 상태
    - `TIME-WAIT` : 액티브 클로즈가 상대의 FIN을 수신하고 이애 대한 ACK를 전송한 뒤 잠시 기다리는 상태
        - 패시브 클로즈 호스트는 ACK를 수신하면 바로 연결을 종료하고 CLOSED 상태가 되지만, 액티브 클로즈 호스트는 `TIME-WAIT` 상태로 잠시 대기하다가 `CLOSED` 상태로 전이한다.
        - 이러한 과정이 필요한 이유는 마지막으로 전송한 ACK가 올바르게 전송되지 않을 경우를 위해서이다. (이때는 패시븤 클로즈 호스트가 FIN을 다시 전송한다.)
    - `CLOSING` : 동시에 연결을 종료하려고 할 때 전이되는 상태
        - 양쪽 모두가 연결 종료를 요청하고, 서로의 종료 응답을 기다리고 있는 경우, 양쪽 모두 `CLOSING` 상태로 전이한다.
        - ACK를 수신하면 각자 `TIME-WAIT`상태로 접어든 뒤 종료한다.

#### TCP 데이터 전송 단계

TCP는 신뢰성을 보장하기 위해 데이터 전송 단계에서 **오류/흐름/혼잡제어** 등의 매커니즘을 수행한다.

**오류 제어: 재전송 기법**

잘못된 세그먼트를 재전송하는 방법으로 신뢰성을 보장할 수 있다.

오류 제어 과정은 크게 1) 오류를 감지하는 방법, 2) 잘못된 세그먼트를 재전송하는 방법으로 나누어 볼 수 있다.

- 오류 감지
    - 수신지로부터 중복된 ACK가 도착했을 경우
        - 전송한 세그먼트가 전송 도중 누락되거나, 내용이 바뀌거나, 순서가 바뀌었을 경우 수신지에서는 이를 감지해 중복된 ACK를 전송해 재전송을 유도한다.
    - 타임아웃이 발생했을 경우
        - 송신지는 각 세그먼트마다 전송 후 재전송 타이머를 시작한다. 해당 타이머가 종료될때까지 ACK를 받지 못하면 오류로 간주해 세그먼트를 재전송한다.
- 재전송 기법 (Automatic Repeat Request)
    - Stop-and-wait ARQ
        - 가장 단순한 방법, 하나의 세그먼트에 대한 ACK를 수신하기 전까지는 절대 다른 세그먼트를 전송하지 않는다.
        - 병목 현상으로 네트워크 효율이 낮아져 성능 저하로 이어질 수 있다.
    - Go-Back-N ARQ
        - **연속해서 메시지를 전송할 수 있는 파이프라이닝**을 사용해, 특정 세그먼트의 ACK를 기다리지 않고 다른 세그먼트를 전송할 수 있도록 하는 방법
        - 도중에 잘못 전송된 세그먼트가 발생할 경우, 해당 세그먼트부터 모두 재전송한다.
        - 송신 호스트가 보낸 세그먼트가 유실되었을 경우, 수신 호스트는 이후 받은 세그먼트가 있더라도 모두 폐기한다.
        - ‘N’의 의미는 ‘N번 까지의’ 세그먼트가 올바르게 전송되었는지 확인한다는 의미이며, 해당 방식의 ACK를 **누적 확인 응답**이라고 한다.
    - Selective Repeat ARQ
        - 동일한 파이프라이닝 방식을 사용하지만, 잘못된 세그먼트 이후 모든 세그먼트를 재전송하는 것이 아닌,  선택적으로 재전송하는 방법이다.
        - 수신 호스트는 올바르게 수신한 세그먼트에 대해서는 전부 ACK를 전송하기 때문에 누적 확인이 아닌, 개별 확인 방식이라고 한다.
    - 빠른 재전송
        - ‘타임 아웃’이 발생하고 나서야 재전송하는 방법의 비효율을 줄이기 위한 방법으로, 수신지로부터 3번의 중복된 ACK가 도착했을 경우 오류로 간주하고 재전송하는 방법이다.

**흐름 제어: 슬라이딩 윈도우**

파이프라이닝 기반의 재전송 방법에서는 **항상 호스트가 한 번에 처리할 수 있는 세그먼트의 양을 고려하여 전송**해야 한다.

- 송/수신 버퍼와 버퍼 오버플로우
    - 호스트는 받은 세그먼트를 바로 처리하기 전에 임시로 자신의 버퍼에 저장한다.
    - 이때 송신 호스트가 수신 버퍼의 크기를 고려하지 않고 많은 데이터를 전송할 경우 버퍼 오버플로우가 발생한다.

TCP는 이러한 문제를 방지하고자 흐름 제어 매커니즘을 통해 송신 호스트가 수신 호스트의 처리 속도를 고려하며 송수신 속도를 균일하게 유지하도록 한다.

- 슬라이딩 윈도우
    - 윈도우: 송신 호스트가 파이프라이닝 할 수 있는 최대량, 즉 수신지의 확인 응답을 받지 않고 한 번에 전송할 수 있는 데이터 양
    - 메모리 버퍼 위에서 동작하는 논리적인 개념으로, 송신지가 수신지에서 확인 응답을 받을 때마다 그 개수마다 윈도우를 옮겨 새로운 데이터를 채우는 것을 슬라이딩 윈도우라고 한다. 반대로 수신지에서도 세그먼트를 받고 ACK를 보낼때마다 수신지의 윈도우 상태를 관리한다.

**혼잡 제어**

모든 호스트가 라우터에게 전송 가능한 최대 양으로 세그먼트를 전송할 경우 라우터에 과부하가 생겨 모든 정보를 처리하지 못할 수 있고, 이에 따라 재전송이 발생하면 혼잡 현상이 더욱 악화되는 혼잡 붕괴 상황이 발생할 수 있다.

이러한 문제를 제어하기 위해 송신 호스트는 네트워크 혼잡도를 판단하고 혼잡한 정도에 맞게 유동적으로 전송량을 조절하는 혼잡 제어 매커니즘을 수행한다.

**혼잡 윈도우 (cw)**

- 혼잡 없이 전송할 수 있는 데이터 양
- 이 값은 수신지로부터 판단하는 게 아니라 **혼잡 제어 알고리즘**을 통해 송신지에서 알아서 계산해야 한다.

**AIMD (Additive Increase / Multiplicative Decrease)**

- 혼잡이 감지되지 않을 경우, 윈도우 사이즈를 RTT마다 1씩 선형적으로 증가시키고 혼잡이 감지되면 윈도우를 절반으로 떨어뜨리는 동작을 반복하는 알고리즘
- 세부적으로 느린 시작, 혼잡 회피, 빠른 회복 알고리즘을 통해 정교하게 혼잡 윈도우 사이즈를 조절한다.

**느린 시작**

- 기존의 AIMD 방식에서는 윈도우 내의 모든 세그먼트에 대한 ACK가 도착했을 경우, cw 값을 1씩 증가시키므로, 초기 전송 속도가 느리다는 문제가 있다.
- 느린 시작 매커니즘은 cw 값을 1로 시작해, ACK가 도착할 때마다 cw를 1씩 늘려서 결국 RTT마다 2배씩 늘어나는 방식으로 동작한다.
- **느린 시작 임계치와 혼잡 상황 감지 시 대처 방법**
    - 느린 시작으로 cw 값이 지수적으로 증가하다가 os단에 설정 되어있는 **느린 시작 임계치에 도달하면 느린 시작을 중단하고 혼잡 회피 단계로 전환**한다.
    - cw 값이 증가하다가 **타임아웃**이 발생할 경우, **cw를 다시 1로 내리고 임계치는 혼잡이 감지되었을 시점의 cw의 절반으로 조정한 후 다시 느린 시작을 재개**한다.
    - 3번의 중복된 ACK를 수신했을 경우, **재전송 이후 빠른 회복 매커니즘**을 수행한다.

**혼잡 회피**

- 느린 시작 임계치를 넘었기 때문에 혼잡 상황을 우려하여 **RTT마다(cw만큼 패킷을 보내고 그 ACK들이 도착하는 데 걸린 시간) cw 값을 1MSS씩 증가시켜 선형적으로 증가**하도록 하는 방법
- 혼잡 회피 도중 타임아웃이 발생할 경우, **cw를 다시 1로 내리고 임계치는 혼잡이 감지되었을 시점의 cw의 절반으로 조정한 후 다시 느린 시작을 재개**한다.
- 3번의 중복된 ACK를 수신했을 경우, cw 값과 임계치를 절반으로 내리고 빠른 회복 알고리즘을 수행한다.

**빠른 회복**

- 3번의 중복된 ACK를 수신했을 경우, 빠른 재전송과 함께 해당 과정이 수행된다.
- 빠르게 전송률을 회복하기 위해 **느린 시작을 건너뛰고 혼잡 회피를 수행**한다.

#### 기존 혼잡 제어 방식의 단점을 보완한, 명시적 혼잡 알림 (ECN)

송신지에서 알고리즘을 통해 혼잡 윈도우를 직접 계산하지 않고, 라우터의 도움으로 혼잡을 제어할 수 있는 방법

- 선택적인 기능이며, 두 호스트가 모두 ECN 방식을 지원해야한다.
- 해당 기능을 지원하는 호스트가 TCP/IP 프로토콜로 정보를 주고받을 때, IP 헤더와 TCP 헤더에 ECN 관련 필드비트가 추가된다.
    - IP 헤더: ‘서비스 필드’ 내의 오른쪽 두 비트 사용
    - TCP 헤더: ‘제어 비트’ 내의 왼쪽 두 비트 사용
- ECN을 사용하면 문제가 발생한 이후에야 혼잡 제어가 수행되는 것이 아닌 세그먼트를 통해 더 빠르게 혼잡을 감지할 수 있다.

### UDP (User Datagram Protocol)

비연결형 통신을 수행하는 신뢰할 수 없는 전송 계층 프로토콜로, 신뢰성이 중요하지 않은 통신의 경우 사용할 수 있다.

#### Datagram

- UDP 프로토콜의 전송 단위, 8바이트의 헤더 + 페이로드로 구성

**UDP 데이터그램 헤더**

<img width="1280" height="500" alt="image (16)" src="https://github.com/user-attachments/assets/f30bf544-5034-4945-bee5-8a579ba906e4" />



- 송/수신지 포트
- 길이: 헤더를 포함한 UDP 데이터그램의 바이트 수
- 체크섬: 데이터그램 전송 과정에서 오류가 발생했는지 여부를 검사하기 위한 필드, 수신지는 해당 필드의 값을 토대로 해당 데이터그램의 손상 여부를 확인하고, 비정상일 경우 폐기한다. (데이터그램이 훼손되었는지를 나타내므로 신뢰성과는 관련이 없다.)

#### UDP의 특징

**비연결형 프로토콜**

- `3-way handshake` 같은 연결 설정 과정이 없으며, 데이터를 일방적으로 전송한다.

**비상태유지 (Stateless)**

- 송신측과 수신측 사이의 **연결 상태(State)를 유지하거나 관리하지 않는다.**
- 각 데이터그램은 서로의 존재를 모르는 독립적인 개체로 취급된다.

**비신뢰성 (Unreliability)**

- **확인 응답(ACK) 없음:** 데이터가 수신측에 잘 도착했는지 확인하지 않는다.
- **재전송 / 흐름 / 혼잡 제어 없음:** 네트워크 상황에 상관없이 일정한 속도로 데이터를 전송한다.

**데이터그램 단위 전송**

- 독립된 데이터그램 그대로 메시지 경계를 유지한다. (송신자가 보낸 크기 그대로 수신자가 받음).
- 각 데이터그램은 **순서가 없으며** 서로 다른 경로로 전송될 수 있다.

**최소한의 오버헤드**

- 헤더 크기가 **8바이트**로 고정되어 매우 작다.
- 복잡한 제어 로직이 없어 CPU 및 메모리 자원 소모가 적다.

#### UDP가 필요한 이유

**실시간성 보장 (Low Latency)**

- TCP의 가장 큰 단점인 패킷 하나가 밀리면 뒤에 오는 패킷들이 모두 대기하는 **Head-of-Line Blocking** 현상이 일어나지 않는다.
- UDP는 이를 무시하고 들어오는 대로 처리하므로 지연 시간을 최소화해야 하는 서비스에 필수적이다.
- *예시: 온라인 게임, 화상 회의(Zoom), 보이스톡(VoIP)*

**네트워크 부하 감소**

- 서버가 수만 명의 클라이언트와 통신해야 할 때, TCP처럼 일일이 연결 상태를 유지하는 것은 큰 오버헤드를 발생시킨다.
- UDP는 상태를 관리하지 않으므로 서버의 부담이 훨씬 적다.
- *예시: DNS 쿼리 (단순 질의응답)*

**유연성**

- TCP는 OS 커널에 로직이 박혀 있어 수정이 불가능하지만, UDP는 "껍데기"만 제공한다. 따라서 개발자가 **애플리케이션 계층에서 필요한 만큼의 신뢰성만 직접 구현**할 수 있다.
- *예시: HTTP/3 (QUIC) - UDP 기반으로 속도와 신뢰성을 모두 잡음*

**일대다 통신 (Multicast / Broadcast)**

- 1:1 통신만 가능한 TCP와 달리, UDP는 하나의 패킷을 여러 명에게 동시에 뿌리는 멀티캐스트 및 브로드캐스트가 가능하다.
- *예시: IPTV 방송, LAN 내 장치 검색*

### QUIC (Quick UDP Internet Connections) 개요

구글에서 웹 최적화를 위해 개발하고 IETF에서 표준화한 **UDP 기반의 전송 계층 프로토콜로,** 현대 인터넷의 표준인 **HTTP/3**의 핵심 기반 기술이다.

<img width="271" height="186" alt="image (8)" src="https://github.com/user-attachments/assets/d46a212f-8ea3-4286-b195-b13ea1864e40" />


#### QUIC의 등장 배경

**TCP의 고착화**

- 문제: TCP는 OS 커널에 구현되어 있어 업데이트가 매우 느리고, 중간 장비(방화벽, 라우터)들이 오래된 TCP 옵션만 인식하여 패킷을 드랍하는 현상이 발생.
- **해결:** 아무 기능 없는 **UDP를 도화지 삼아 응용 계층에서 TCP가 지원하는 기능들을 직접 구현**하는 방식으로 커널 업데이트 없이 배포 가능하게 함.

**핸드셰이크의 지연**

- **문제:** TCP handshake, TLS handshake 과정이 각각 따로 일어나 데이터 전송 전까지 여러 번의 RTT가 소요됨.
- **해결:** 연결과 암호화 설정을 하나로 통합하여 지연 시간을 획기적으로 단축함.

**Head-of-Line Blocking (HOLB)**

- **문제:** TCP는 모든 데이터를 하나의 순서 있는 스트림으로 처리함. 패킷 하나만 유실되어도 뒤의 패킷들이 모두 대기해야 함.
- **해결:** UDP 위에서 독립적인 여러 스트림을 운영하여 유실된 스트림만 멈추도록 설계함.

**모바일 환경의 이동성**

- **문제:** TCP는 `IP/Port` 기반이라 Wi-Fi에서 LTE로 바뀌면 IP가 변해 연결이 끊김.
- **해결:** IP가 아닌 고유 ID를 통해 네트워크가 바뀌어도 연결을 유지함.

#### 세부 동작 방식

**연결 및 보안**

- **1-RTT / 0-RTT 핸드셰이크 및 TLS 1.3 내장**
    - 처음 연결 시 **1-RTT** 만에 보안 연결 완료 후 데이터 전송
    - 재연결 시에는 이전에 공유한 키를 사용해 기다림 없이 즉시(**0-RTT**) 데이터를 전송함.
    - 보안이 선택 사항인 TCP와 달리, QUIC은 암호화가 기본이며 프로토콜 내부에 TLS 1.3이 통합되어 있음.

<img width="1400" height="1028" alt="image (9)" src="https://github.com/user-attachments/assets/a3bd9307-d3de-4c0a-8116-834ade3fc8ed" />

<img width="2248" height="1160" alt="image (11)" src="https://github.com/user-attachments/assets/b41dc08f-2f55-4706-9c4a-b5be4143fcb1" />

**멀티스트리밍**

- **독립적 전송**
    - 하나의 UDP 연결 안에서 여러 개의 파일을 각기 다른 스트림으로 전송함.
- **개별 오류 복구**
    - 1번 스트림(이미지) 패킷이 깨져도 2번 스트림(JS 파일)은 즉시 앱으로 전달됨. TCP의 **전체 멈춤(HOLB) 현상을 제거**함.

**연결 식별 및 이동성**

- **Connection ID (CID)**
    - 서버와 클라이언트는 서로를 IP 주소가 아닌 **64비트 고유 ID**로 식별함.
- **Connection Migration**
    - 사용자가 이동하며 IP가 바뀌어도 CID가 같으면 서버는 클라이언트를 그대로 인식하고 통신을 이어갈 수 있어 재연결로 인한 지연이 줄어듦

**향상된 오류 및 혼잡 제어** 

- **패킷 번호의 유일성**
    - 재전송 시에도 기존 번호를 재사용하지 않고 **새로운 패킷 번호**를 부여하므로 ACK가 왔을 때 원래 패킷인지 재전송 패킷인지 명확히 구분하여 더 정확한 RTT 계산이 가능함.
- **유연한 알고리즘 적용**
    - 혼잡 제어 로직이 앱 영역에 있으므로, 서비스 특성에 맞춰 최신 알고리즘을 즉시 적용할 수 있음.

#### QUIC 방식의 단점

- CPU 부하 증가 및 구현 복잡도: 하드웨어적으로 지원되는 TCP와 달리 소프트웨어적으로 처리하기 때문에 CPU 부하가 크고, 개발자가 직접 관리해야 한다.
- TCP에 비해 호환성이 낮다.

**재전송 패킷 식별의 어려움**

- QUIC는 재전송 패킷이라도 매번 새로운 패킷 번호를 설정해 보내기 때문에, TCP처럼 흐름을 특정지을 수 없었고, 와이어샤크로 패킷을 관찰해도 해당 페이로드가 암호화되어 있어서 처음에는 어떤 패킷이 재전송 패킷인지 정확히 식별할 수 없었다.
- 시간 순대로 정렬하고, 처음부터 length가 같은 패킷을 몇 개 관찰하니 운좋게 아래처럼 wireshark가 재전송 패킷으로 의심하는 부분을 찾을 수 있었다.
- 아래처럼 `offset`과 `length`가 동일한 패킷이 여러번 전송되는 것을 통해 해당 패킷들의 재전송이 발생했음을 짐작할 수 있다.

**SACK vs ACK Frame**

- TCP에서는 SACK 옵션을 통해 누락된 부분 중 어느 부분을 수신했는지 알려줄 수 있는데, 이 필드는 최대 4개의 유실 구간(블록)만 보고할 수 있다.
- QUIC는 수신측에서 `ACK Frame`을 사용해서 어떤 번호를 받았고 어떤 번호를 받지 못했는지 완벽하게 보고하여 재전송 효율을 높인다.

<img width="401" height="217" alt="image (15)" src="https://github.com/user-attachments/assets/ad431acc-c8ef-4195-80d5-15d431bab90a" />


- `Largest Acknowledged: 3`
    - 받은 것 중 가장 큰 번호는 **3번** 패킷
- `First ACK Range: 0` ****
    - `Largest Acknowledged`로부터 거꾸로 몇 개의 패킷을 연속해서 받았는지
    - 3번 하나 받았어.
- **`Gap: 1`**
    - `Largest Acknowledged` 앞에 1개의 유실 지점이 있다는 뜻 (2번 유실)
- **`ACK Range: 0`**
    - 유실된 패킷을 제외하고, 다시 연속으로 받은 패킷들의 개수
    - 그럼 1번 패킷은? → 2번만 유실되었으므로, 이전 ACK에서 이미 보고됨.
- 실제로 `quic.packet_number == 2`로 필터링을 걸어보면, 여러 패킷에서 재전송 경고를 발견할 수 있었다.
- 또한 `quic.packet_number == 1`로 필터링을 걸었을 때는, 재전송 경고를 발견할 수 없었다.

#### TCP vs QUIC 실측 비교 정리

| **비교 항목** | **TCP (Transmission Control Protocol)** | **QUIC (Quick UDP Internet Connections)** |
| --- | --- | --- |
| **식별 번호 (ID)** | **Sequence Number (순서 번호)** 기반 | **Packet Number (패킷 번호)** 기반 |
| **재전송 시 번호 변화** | 유실된 패킷과 **동일한 seq** 사용 | 재전송 시마다 **새로운 PN** 부여 (유일성) |
| **재전송 판별 근거** | 동일 seq의 중복 출현 (Retransmission) | **reused stream offset** 경고 및 동일 CID/Length/offset |
| **수신 확인 방식** | **SACK** (Selective ACK) 옵션 사용 | **ACK Frame** (Gap, Range 필드) 사용 |
| **피드백 정밀도** | 헤더 크기 제한으로 최대 4개 블록 보고 | 가변 길이 프레임으로 **무제한 유실 구간** 보고 |
| **데이터 가시성** | 페이로드 평문 노출 (HTTP 기준) | **페이로드 전체 암호화** (TLS 1.3 기본 내장) |


## 3. 의문 / 논점

### Go-Back-N ARQ의 수신 측 동작만 보면 오류가 발생한 이후의 세그먼트는 어차피 다 버리는데 왜 굳이 많이 보낼까?

- **평상시(오류 없을 때):** Stop-and-Wait보다 **N배 빠르다.**
- **오류 발생 시:** 수신자가 뒤를 다 버리고 송신자가 다시 다 보내야 하므로 비효율이 생긴다. (이게 싫어서 만든 게 **Selective Repeat**)
- **결론:** **오류가 날 때의 손해**보다 **평상시에 얻는 속도 이득**이 압도적으로 크기 때문에 의미가 있는 방식이다.
