## 1. 핵심 개념

### 블로킹, 논블로킹?

: 함수를 호츨할 때 실행의 제어권을 누가 갖는지에 대한 개념

**Blocking**

- 호출자가 피호출자의 실행이 완전히 끝날 때까지 아무것도 하지 못하고 기다려야하는 상태, 즉 제어권이 피호출자에게 넘어가는 것
- 일반적인 함수 호출은 기본적으로 블로킹 상태라고 볼 수 있다.

 **CPU-bound/IO-bound 작업과 Blocking 방식의 문제**

- CPU 연산량이 많은 CPU-bound 작업은 CPU 활용도는 높지만 그동안 다른 작업은 처리되지 못해서 병렬성이 저하된다.
- IO 대기 시간이 긴 IO-bound 작업의 경우 처리가 완료될 때까지 호출자 스레드는 놀게 되어 자원이 낭비된다.
- 이러한 비효율을 해결하고자 호출자 스레드를 멈추지 않게 하는 방식이 Non-blocking 이다.

**Non-blocking**

- 호출된 함수가 작업 완료 여부와 관계없이 제어권을 즉시 반환하여 호출자가 다른 일을 할 수 있는 방식
- 동작 흐름
    - 호출자 A 함수가 논블로킹 작업 B 함수를 호출하고, 제어권이 B로 넘어감
    - B 함수는 운영체제를 통해 작업을 등록만 한 뒤 제어권을 즉시 A로 반환
    - A는 B 처리 완료 알림이 오기 전까지 다른 작업을 실행
    - B 처리가 완료되면 적절한 방식으로 완료 결과 전달
- 작업 완료를 알리는 방법
    - 콜백
        - 작업 요청 시, ‘작업이 끝나면 실행할 함수’를 전달하는 방식
        - 피호출자가 작업을 마치고 넘겨받은 콜백 함수를 실행한다.
        - 콜백 지옥이 생기면 가독성이 떨어지고 디버깅이 어렵다.
    - 폴링
        - 호출자가 상태 변수나 함수를 통해 반복적으로 완료 여부를 체크하는 방식
        - 단순하지만 계속 물어보는 과정에서 CPU 사이클이 낭비된다.
    - 이벤트 루프
        - 중앙 알림 센터를 사용하는 방식
        - 피호출자가 작업을 완료하면 이벤트를 발생하고 해당 이벤트를 구독하던 호출자가 반응한다.
        - 호출자와 피호출자 간 느슨한 결합이 만들어진다.
    - 미래 객체 (Promise, Future, async/await)
        - 비동기 작업의 결과물에 대한 대리자를 미리 받아두는 방식
            - 호출자는 당장 결과값 대신 특정 객체를 받고, 나중에 데이터가 채워지면 해당 객체를 통해 값을 꺼낸다.
            - async-await은 이러한 미래 객체를 다루는 방식을 읽기 편하게 개선한 것이다.

### 동기/비동기 개념과 구분

- 둘을 헷갈리는 경우가 많은데, 동기/비동기는 실행 결과를 받는 방식에 관한 개념이고 블로킹/논블로킹은 ‘제어권’을 누가 갖는지에 관한 개념이다.
- 그러나 제어권을 언제 돌려주느냐가 곧 결과를 어떻게 전달받느냐에 영향을 주므로,
주로 동기-블로킹 방식과 비동기-논블로킹 방식 형태로 관련지을 수 있다.

**2 x 2 조합 분석해보기**

- **동기-블로킹 (Sync-Blocking)**
    - 상황: 점원에게 커피를 주문하고, 커피가 나올 때까지 카운터 앞에서 멍하니 서서 기다린다.
    - 특징: 제어권도 뺏겼고(Blocking), 결과도 바로 받아야 한다.(Sync).
    - 사례: 일반적인 함수 호출, `Data(contentsOf: url)` 등.
- **비동기-논블로킹 (Async-Nonblocking)**
    - 상황: "진동벨 울려주세요" 하고 자리에 가서 편하게 내 할 일을 한다. 벨이 울리면 그때 커피를 받으러 간다.
    - 특징: 제어권도 바로 돌려받고(Non-blocking), 결과도 나중에 알림으로 받으면 된다.(Async).
    - 사례: `URLSession`, `Swift Concurrency`, 현대적인 네트워크 통신 대부분.
- 동기-논블로킹 (Sync-Nonblocking)
    - **상황:** 주문 후 제어권은 돌려받아 자리에 앉았는데, **1초마다 카운터에 가서 "커피 나왔어요?"라고 물어본다.**
    - **특징:** 제어권은 있어서 딴짓을 할 순 있지만(Non-blocking), 결과를 계속 물어보면서 체크한다(폴링)
    - **사례:** 작업이 끝났는지 확인하는 루프(Status Check).
- 비동기-블로킹 (Async-Blocking)
    - **상황:** "커피 다 되면 진동벨 울려주세요"라고 하고 자리에 앉으려는데, **점원이 내 팔을 붙잡고 못 가게 한다.**
    - **특징:** 결과는 나중에 받기로 했는데(Async), 제어권을 뺏겨서 아무것도 못 한다(Blocking).
    - **사례:** 의도치 않은 설계 오류

### 성능에 영향을 주는 부분

- 블로킹
    - 스레드가 대기 상태로 묶이게 된다.
    - 이후 멈춘 스레드 대신 다른 스레드로 전환하기 위한 컨텍스트 스위칭 비용이 발생한다.
- 논블로킹
    - 작업 완료 알림을 위한 추가적인 비용이 생긴다.
    - 비동기 알림을 처리하기 위해 실행 흐름을 바꿀 때마다 컨텍스트 스위칭 비용이 발생한다.
    - 작업 단위가 너무 작을 경우 이러한 오버헤드가 더 커질 수 있다.

---

### 무엇이 더 좋은 방법일까?

- 어떤 성격의 작업인지를 고려해 두 방식의 트레이드오프를 비교해서 적절한 방식으로 동작하는 API를 사용해야한다.

| 구분 | 블로킹(Blocking) | 논블로킹(Non-blocking) |
| --- | --- | --- |
| 스레드 사용 | 요청마다 스레드가 오래 묶이기 쉬움, 스레드 수 증가 | 소수 스레드로 많은 작업 처리 가능, 스레드 수 절약 |
| CPU 사용 | I/O 대기 동안 스레드는 잠들어 CPU는 거의 안 씀 | I/O 완료 이벤트 처리·상태 관리에 CPU를 더 사용 가능 |
| 컨텍스트 스위칭 | 스레드가 많아질수록 OS 컨텍스트 스위칭 비용 증가 | 스레드 수가 적어 OS 컨텍스트 스위칭 비용 감소 |
| I/O-bound 대규모 처리 | 동시 연결이 많아지면 스레드/컨텍스트 스위칭이 병목 | 대규모 동시 연결 처리에 적합, 고동시성 서버에 유리 |
| CPU-bound 작업 | 스레드 수를 코어 근처로 제한하면 단순하고 효율적 | 필요 이상으로 논블로킹 복잡성을 도입할 필요는 적음 |
| 코드 복잡도 | 동기적 흐름이라 이해·디버깅이 쉽고 직관적 | 상태 머신, 콜백, 이벤트 루프 등으로 구조가 복잡해짐 |
| 디버깅 난이도 | 호출 스택 따라가기 쉬워 버그 추적이 비교적 간단 | 콜백 체인, 비동기 흐름 때문에 재현·추적 난이도 높음 |

## 2. 탐구 내용 (실무 / iOS 연결)

### iOS에서는 케이스별로 어떤 방식을 권장하고, 지양할까?

---

### 네트워크 통신

- **논블로킹 방식 사용**
    - 대기 시간이 길고 가변적인 네트워크 작업은 스레드 블로킹을 방지하고 자원을 효율적으로 활용하기 위해 논블로킹 방식을 사용한다.
- **주요 도구:** `URLSession`, `Swift Concurrency(async/await)`
- **❌ 지양:** `Data(contentsOf:)`
    - 작업이 끝날 때까지 해당 스레드를 물리적으로 점유한다.
    - 백그라운드 스레드의 경우 스레드를 낭비시켜 극단적이면 스레드 풀 고갈 문제가 발생할 수 있다.
    - 메인 스레드에서는 UI 프리징이 발생할 수 있기 때문에 사용을 엄격히 금지한다.

---

### 파일 I/O (File Input/Output)

- **논블로킹 방식 (권장)**
    - **특징:** 대용량 파일(고화질 이미지, 동영상 등)을 읽거나 쓸 때 제어권을 즉시 반환하여 UI가 멈추는 현상을 방지한다.
    - **주요 도구**
        - **`URLSession` :** 로컬 파일 시스템과 네트워크 간의 이동을 비동기로 처리할 때 표준으로 사용된다.
- **제한적 블로킹 방식**
    - **어떤 상황에서 사용될 수 있을까?**
        - **초소형 설정 파일:** `Info.plist`나 앱 구동에 필수적인 작은 로컬 `JSON` 설정 파일을 읽을 때.
        - **테스트 환경:** 사용자 경험이 고려 대상이 아닌 단위 테스트 환경에서 Mock 데이터를 불러올 때.
    - **주요 도구:**  **`Data(contentsOf: fileURL)`**, **`String(contentsOfFile:)`, `FileManager`**의 대부분의 동기 메서드들.

---

### 스레드 동기화 및 자원 보호 (Thread Safety)

- **전략적 블로킹 활용:** 여러 스레드가 동시에 접근하는 임계 구역에서는 데이터 무결성을 위해 짧은 시간 동안의 블로킹을 권장한다.
- **주요 도구:** `DispatchQueue.sync`, `NSLock` 등을 사용한다. 이는 매우 짧은 찰나의 제어권을 통제하여 Race Condition을 방지한다.
- **❌ 지양:** 논블로킹 방식 `DispatchQueue.async`를 남발할 경우, 모든 수정 로직이 파편화되어 실행 순서의 정합성을 보장하기 어렵고 디버깅 난이도가 상승한다.

---

### 시간 지연 (Delay)

- **협력적 논블로킹 지향:** 대기 시간 동안 스레드 자원을 다른 작업이 쓸 수 있도록 개방하는 방식을 사용한다.
- **주요 도구:** `Task.sleep(nanoseconds:)`
    - 이는 해당 작업만 '중단'시키고 스레드 제어권은 시스템에 반납하는 논블로킹 방식이다.
- **❌ 지양:** `Thread.sleep(forTimeInterval:)`
    - 스레드 자체를 잠재워 자원을 낭비하며, 메인 스레드에서 호출할 경우 앱의 모든 반응을 차단한다.

---

### CoreData

- 사용 환경에 따라 블로킹과 논블로킹 모드를 선택적으로 운용한다.

<img width="1280" height="647" alt="image" src="https://github.com/user-attachments/assets/f798c037-1e55-43c9-b3b8-8a79f1d52130" />


- **동작 방식**
    - Context: 인메모리 객체와 DB의 상호작용을 관리하는 중간 계층
    - 데이터 정합성을 유지하면서도 UI 반응성을 놓지 않기 위해 스레드 분리 모델을 사용한다.
    - **View Context**
        - 메인 스레드에서 동작하도록 설계된 컨텍스트로, 테이블이나 컬렉션 뷰에 대한 데이터 소스를 바로 UI에 표시할 수 있게 한다.
        - 무거운 작업을 수행할 경우 블로킹 위험이 있다.
        
        ```swift
        // 메인 스레드 (View Context)
        let context = persistentContainer.viewContext
        
        let newUser = User(context: context)
        newUser.name = "Gemini"
        
        do {
            // 소량의 데이터이므로 메인 스레드에서 즉시 저장 (동기-블로킹)
            try context.save() 
            print("UI 데이터 저장 완료")
        } catch {
            // 에러 처리
        }
        ```
        
    - **Background Context**
        - CoreData가 관리하는 별도의 큐를 할당받아 백그라운드에서 논블로킹으로 데이터를 처리한다.
        - 백그라운드에서 데이터를 저장하는 작업을 처리하고 끝나면 변경사항을 view context에 병합하는 방법으로 처리할 수 있다.
        - 백그라운드 컨텍스트에서 사용 가능한 API
            - `performBackgroundTask` : 내부적으로 임시 컨텍스트를 생성하고 파기하는 방식 (일회용 방식)
                
                ```swift
                // 별도의 백그라운드 전용 큐 생성
                persistentContainer.performBackgroundTask { bgContext in
                    // 이 클로저 내부는 'Private 전용 큐'에서 실행됨
                    
                    for i in 1...10000 {
                        let log = EventLog(context: bgContext)
                        log.timestamp = Date()
                        log.details = "Log number \(i)"
                    }
                    
                    do {
                        // 대량 저장이 일어나는 동안 메인 스레드는 UI를 계속 그림 (논블로킹)
                        try bgContext.save()
                        print("백그라운드 대량 저장 완료")
                    } catch {
                        print("저장 실패")
                    }
                }
                // performBackgroundTask는 호출 즉시 제어권을 반환하므로 
                // 아래 코드는 위 저장 작업과 상관없이 바로 실행됨
                print("백그라운드 작업 요청 후 즉시 실행되는 코드")
                ```
                
        - `perform`: 동일한 논블로킹 방식이지만, 수동으로 컨텍스트를 생성하고 해당 컨텍스트를 재사용할 수 있음
            
            ```swift
            // 1. 백그라운드 컨텍스트 직접 생성
            let bgContext = persistentContainer.newBackgroundContext()
            
            // 2. perform 호출 (비동기)
            bgContext.perform {
                for i in 1...10000 {
                    let log = EventLog(context: bgContext)
                    log.details = "Log \(i)"
                }
                try? bgContext.save()
                print("1. 백그라운드 저장 완료") 
            }
            
            // 3. 제어권 즉시 반환
            print("2. 바로 실행됨") 
            
            // 출력 순서: "2. 바로 실행됨" -> (시간 흐른 뒤) -> "1. 백그라운드 저장 완료"
            ```
            
        - `performAndWait`: 블로킹 방식으로, 작업 완료 시까지 호출 스레드를 블로킹하여 작업의 순차적 완료를 보장한다. 마찬가지로 생성한 컨텍스트를 재사용할 수 있다.
            
            ```swift
            let bgContext = persistentContainer.newBackgroundContext()
            
            // 2. performAndWait 호출 (동기)
            bgContext.performAndWait {
                for i in 1...10000 {
                    let log = EventLog(context: bgContext)
                    log.details = "Log \(i)"
                }
                try? bgContext.save()
                print("1. 백그라운드 저장 완료")
            }
            
            // 3. 작업이 끝날 때까지 여기서 대기
            print("2. 이제야 실행됨")
            
            // 출력 순서: "1. 백그라운드 저장 완료" -> "2. 이제야 실행됨"
            ```
            

## 3. 의문 / 논점

### Non-blocking은 항상 빠르다?

- 특히 CPU 연산이 많은 CPU-bound 작업인 경우 폴링이나 완료 알림 등의 추가적인 로직으로 오버헤드가 발생하면 오히려 블로킹 방식보다 느려질 수도 있다.

### Filemanager는 왜 기본적으로 동기 방식으로 설계되었을까?

- 파일 시스템 작업은 대개 작업 의존성을 가진다. (해당 파일이 존재해야 다음 작업 실행) 만약 해당 작업이 비동기로 동작한다면, 개발자는 매번 콜백 코드를 작성해야 하는 복잡함을 감수해야한다.
- 파일 시스템은 여러 프로세스/스레드가 동시에 접근 가능한 공유 자원이기 때문에 데이터 무결성을 위해 기본적으로 동기 방식으로 동작하는게 더 적절하다.
- 동기 방식으로 동작하는 POSIX 시스템 콜을 추상화한 도구로서, 동기 방식을 유지해 호환성과 안정성을 보장할 수 있는 한편 스레드 관리의 책임을 개발자에게 위임해 오래 걸리는 작업의 경우 백그라운드에서 실행되게하여 유연성을 확보할 수 있다.
