## 1. 핵심 개념

### 페이징의 등장 배경

**가변 분할 방식과 외부 단편화 문제**

- 메모리를 프로세스 크기에 맞게 할당하는 가변 분할 방식에서, 남는 공간이 불연속적이어서
남은 메모리의 총 크기는 충분하지만, 연속적으로 할당할 수 있는 공간이 없어 공간이 낭비되는 문제 존재
- 이를 해결하는 방법으로 페이징 등장
- 하드웨어 + 운영체제의 협력으로 구현된다.

### 기본적인 방법

**고정 크기 분할**

- 물리 메모리를 Frame이라 불리는 고정된 크기의 블록으로 나눔
- 가상 메모리(프로세스가 차지하는 논리적 주소 공간)는 동일한 개념으로 Page 단위로 나눔
- 보조기억장치 또한 고정된 크기의 블록으로 나뉘어짐

**Page Table**

- 각 프로세스마다 가지며, 각 프로세스의 page table이 저장되어 있는 주소를 page table base register가 저장
- 가상 메모리의 단위인 페이지를 물리 메모리 단위인 프레임으로 변환하는 정보를 가지고 있다.
- 해당 테이블은 운영체제가 소유하며, page table base register 값을 통해 MMU가 주소 변환을 하게 한다.

**Page number, Page offset**

- CPU가 바라보는 가상 주소는 페이지 넘버(p bit)와 페이지 오프셋(d bit)의 조합으로 나타냄
- Page number
    - 특정 프로세스가 가지는 페이지 테이블의 인덱스
    - 해당 값을 p비트로 표현한다면 라면 페이지 테이블의 엔트리 수는 2^p개
- Page offset
    - 참조되는 프레임 내부의 주소
- 물리 메모리의 base register 값 == 프레임 주소 + page offset

**MMU의 주소 변환 과정**

- page number 값을 가져와 페이지 테이블 내의 인덱스로 사용
- 일치하는 페이지 테이블 엔트리에서 매핑되는 frame number를 찾음
- page number를 frame number로 변경함 →  base address 완성 (frame number*frame size + offset)

**Page Size**

- 하드웨어 종속적
- 2의 거듭제곱 단위로 사용하는 이유는 가상 주소를 페이지 넘버와 오프셋으로 변경하기 용이하기 때문이다.
- 페이지와 프레임 사이즈는 같아야 한다.

**외부 단편화 해결**

- 남은 어떤 공간에도 할당할 수 있기 때문에 공간 낭비가 발생하지 않는다.
- 그러나 항상 프레임 크기의 정수배만큼 할당하므로 내부 단편화가 발생할 수 있다.
- 그렇다고 페이지 사이즈를 작게만들면 페이지 테이블 크기가 커져서 찾는데에 오래 걸릴 수 있다.
- 현재는 대부분 4 or 8KB인데, 종종 여러 페이지 사이즈를 가지는 경우도 있다.

**페이징 시스템에서 가능한 논리 주소 공간 크기와 실제 물리 메모리 크기의 독립성**

- 프로세스 가상 메모리 크기는 물리 메모리 크기보다 훨씬 클 수 있다.
- 결정 주체의 분리
    - **논리 주소 공간:** CPU의 비트 수에 의해 결정된다.
        - 32비트 CPU라면 2^{32} = 4GB가 최대
    - **물리 메모리 크기:** 메인보드에 꽂힌 **실제 RAM의 용량**에 의해 결정된다.
- 페이징을 통한 독립성 구현
    - 두 크기가 달라도 문제가 없는 이유는 페이지 테이블이 있기 때문
    - 지금 당장 실행에 필요한 일부 페이지만 물리 메모리의 빈 프레임에 올린다.
    - RAM보다 큰 프로그램도 실행 가능하다. 물리 메모리에 자리가 없으면 나머지 페이지는 백킹 스토어에 저장한다.
    - 논리 주소는 0번지부터 100GB까지 연속되어 보이지만, 실제 물리 주소는 불연속적이다.
- 독립성이 주는 이점
    - **프로그래밍의 단순화:** 개발자는 실제 RAM이 4GB인지 16GB인지 고민할 필요 없이 CPU가 허용하는 논리 주소 범위 내만 신경쓰면 된다.
    - **멀티태스킹 최적화:** 여러 프로그램이 각자 거대한 논리 주소 공간을 가져도, 운영체제가 실제 RAM에는 필요한 조각만 올리므로 수많은 앱을 동시에 띄울 수 있다.
    - **메모리 보호:** 각 프로세스는 자신만의 독립된 논리 주소 지도를 가지므로, 물리적으로는 같은 RAM을 써도 서로의 영역을 절대 침범할 수 없다.

**Frame Table**

- 운영체제는 물리 메모리에 접근해야하므로, 물리 메모리 내부 프레임에 대한 정보를 알아야 함
- 해당 정보를 담고있는 테이블이며 하나의 프레임마다 하나의 엔트리 가짐
- 할당됨 여부를 나타내고, 할당되었다면 어느 프로세스의 어느 페이지에 할당되었는지 저장

### 하드웨어 지원

**전용 고속 레지스터 방식 vs Page-table Base Register**

- 페이지 테이블은 각 프로세스마다 소유하고, 해당 테이블을 가리키는 포인터를 PCB에 저장할 수 있다.
- 전용 고속 레지스터 방식
    - CPU 안에 아주 빠른 레지스터들을 여러 개 두고, 여기에 페이지 번호와 프레임 번호 쌍을 하나씩 저장하는 방식
    - 메모리에 갈 필요 없이 CPU 내부에서 즉시 주소 변환이 일어나므로 매우 빠름
    - 프로세스가 바뀔 때마다 수천 개의 레지스터 값을 일일이 다 갈아끼워야 하므로, 전환 비용이 매우 크다.
- PTBR 방식
    - 페이지 테이블은 메인 메모리에 저장
    - **PCB에는 해당 테이블의 포인터를 저장**
    - 컨텍스트 스위칭 시 레지스터 수천 개를 건드릴 필요 없이, PTBR 값만 변경하면 됨

**TLB (Translation Look-aside Buffer)**

- 페이지 테이블 값을 조회하려면 느린 메인 메모리에 접근해야하므로, 속도 향상을 위해 도입한 하드웨어 캐시
- 각 엔트리는 key, value로 이루어지고, 작은 크기를 유지해야 함
- 페이지 테이블의 일부를 저장
- MMU는 가상 주소를 가지고 먼저 TLB를 확인
    - page number가 있으면 즉시 frame number로 변환 가능 (TLB hit)
    - 없으면 원래대로 주소 변환 과정을 거침 (TLB miss), 이후 해당 Page number 엔트리를 TLB에 추가함 (캐시의 지역성)
    - 만약 TLB가 가득 찼다면? 정책에 의해 하나의 엔트리를 제거함
        - LRU (Least Recently Used)
        - 특정 엔트리는 wired-down 상태일수도 있음 (고정)
- Address-space identifiers
    - 페이징 시스템에서 여러 프로세스가 동일한 논리 주소를 가질 수 있어서 문맥 교환시 발생할 수 있는 오류때문에 프로세스가 변경될때마다 TLB도 무효화 시켜야 했음 > 오버헤드 발생
    - 특정 TLB는 각 엔트리마다 `ASID` 값을 저장하는데, 이 값은 이 주소 변환 정보가 어느 프로세스의 것인지를 나타내는 고유 식별자 역할을 한다.
    - 따라서 TLB 전체를 비울 필요 없이, ASID 값을 체크하여 현재 프로세스 정보와 일치하지 않는다면 TLB miss로 간주한다. (동일 매커니즘)
    - 이를 통해 문맥교환 시 발생하는 오버헤드를 줄일 수 있고, 잠시 멈췄다 다시 실행되는 프로세스의 페이지 엔트리가 남아있을 경우 바로 주소 변환이 가능하다.
    - 그러나 캐시가 비워지지 않아 이전 프로세스 때문에 실제로는 유효하지 않은 엔트리가 남아있을 수 있다.
- hit ratio, effective memory-access time (유효 접근 시간)
    - hit ratio: TLB 접근 횟수 중 hit한 비율
    - effective memory-access time  =   hit ratio * (TLB + 실제 데이터) + (1-hit ratio) * (TLB + 실제 데이터 + 페이지 테이블)

### 메모리 보호

**protection bit**

- 페이지 테이블 내에 1비트 크기의 보호 비트를 설정하여, 해당 물리 메모리에 대한 접근 권한을 설정하고 확인할 수 있다.
- read-only 상태에 쓰기 요청이 오면 trap 발생

**valid-invalid bit**

- 해당 페이지가 프로세스의 논리 주소 공간 내에 위치하는 유효한 주소인지 검사
- invalid의 경우 마찬가지로 trap 발생

**PTLR (Page-table Length Register)**

- 대부분의 프로세스는 전체 주소 공간을 사용하지 않는다.
- 따라서 페이지 테이블의 엔트리 또한 그에 맞게 필요한만큼만 제한해 메모리 낭비를 줄이려면, PTLR에 그 값을 저장해서 페이지 테이블의 길이를 제한하는 것이다.
- 선형 페이지 테이블에선 크기를 제한하는 가장 효율적인 방법

### Shared pages

- C 표준 라이브러리처럼 여러 프로세스에서 공통적으로 사용될 수 있는 코드를 공유해 낭비를 줄일 수 있다.
- reentrant code
    - 공유될 수 있는 코드, 자기 수정 X
    - 해당 코드는 실행 중에 절대 변경되지 않는다. 따라서 여러 프로세스가 동시에 해당 코드를 실행할 수 있다.
- 물리 메모리에는 오직 한 개의 프레임만 존재하고, 각 프로세스의 페이지 테이블에서는 모두 같은 물리 주소로 매핑한다.
- 운영체제는 해당 코드를 읽기 전용으로 강제해야 한다.
