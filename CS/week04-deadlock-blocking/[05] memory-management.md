## 1. 핵심 개념

### 메모리 접근 범위

커널에서, 즉 운영체제만 접근 가능

- base register
    - 물리 메모리에서 프로세스의 시작 주소
- limit register
    - 논리 주소 공간에서 프로세스가 사용하는 주소 범위의 크기
- 프로세스의 주소 범위
    - `base`  ~ `base` + `limit`

---

### 주소 바인딩 흐름

소스 프로그램

- 심볼릭한 변수

컴파일

- 소스 파일의 심볼을 relocatable 주소(해당 파일 내에서의 상대 위치)로 바인딩

링커 or 로더

- relocatable 주소를 실제 접근 가능한 accessable 주소 바인딩
    - Relocation (재할당)
        - 프로그램의 주소를 실제 물리 메모리 위치에 맞게 변경하는 것
        - physical = logical + base, (logical < limit)

---

### 주소 바인딩 시점에 따른 차이점

- 컴파일 시점 (Compile Time Binding)
    - 프로그램이 컴파일될 때 실제 메모리 주소가 결정되는 것
    - 결과적으로 고정된 물리 주소를 생성해 CPU에서 바로 실행할 수 있는 형태인 절대 코드가 생성된다.
    - 메모리 내의 물리적 위치를 컴파일러가 미리 알고 있어야 하며, 시작 위치를 변경하고 싶다면 프로그램을 **처음부터 다시 컴파일**해야 함
    
- 로드 시점 (Load Time Binding)
    - 컴파일 시에는 주소를 확정하지 않고, 프로그램이 메모리에 실제로 올라갈 때(Loding) 주소를 결정하는 것
    - **결과적으로** Relocatable Code (재배치 가능 코드)가 생성된다.
    - 컴파일러는 기계어 코드를 생성할 때 0번지부터 시작하는 상대적인 주소를 부여하고,
    로더가 프로그램을 메모리에 올리면서 비어있는 실제 물리 주소를 더해준다. (재배치)

- 실행 시점 (Execution/Run Time Binding)
    - **설명:** 프로그램이 실행 중일 때 CPU가 메모리에 접근할 때마다 주소가 결정되는 방식으로, 현대의 일반적인 OS가 사용하는 방식이다.
    - 주소를 실시간으로 변환하기 위해 MMU라는 전용 하드웨어가 필요하다.
    - 프로그램이 실행 도중 메모리 내에서 다른 위치로 옮겨져도 중단 없이 돌아갈 수 있다.

---

### 주소 개념

**Physical address**

- memory-address register에 로드되는 물리적 주소

**Virtual(Logical) address**

- CPU가 생성하는 주소

**Address space**

- 프로그램에 의해 생성된 주소들의 집합을 주소 공간이라고 함
- 논리 주소 공간은 항상 연속적이다.

**주소 맵핑**

- 논리 주소 → 물리 주소로 변환하는 것
- MMU가 수행
    - CPU가 메모리에 접근하는 것을 관리하는 컴퓨터 하드웨어 부품.
    가상 메모리 주소를 실제 물리 메모리 주소로 변환하며, 메모리 보호, 캐시 관리, 버스 중재 등의 역할을 담당한다.

---

### 동적 로딩

- 프로세스가 실행되기 위해서 전체 프로그램과 데이터가 모두 물리 메모리에 올라와야 해서, 물리 메모리 사이즈에 제약을 받음.
이때 메모리 공간을 보다 효율적으로 사용하기 위해 나온 개념으로, 모든 부분을 메모리에 올리지 않고 필요한 코드만 실행 시점에 올리는 방식
    - 함수는 호출되기 전까지 로드되지 않음
    - A 함수가 B 함수를 호출할 경우, A는 먼저 B가 이미 메모리에 올라와있는지 확인
    - 있으면 바로 실행하고, 없다면 디스크에서 로드 후 실행한다. (제어는 B에게로)
- 루틴이 필요할 때만 호출되므로 효율적이라는 장점
- 운영체제의 특별한 지원 필요로 하지 않고, 개발자의 몫

**동적 링킹과 공유 라이브러리**

- 동적 링킹 vs 정적 링킹
    - 동적 링킹: 라이브러리 링킹이 실행 시점에 수행됨.
    - 정적 링킹: 시스템 라이브러리들은 로더에 의해 하나의 바이너리 프로그램 코드로 합쳐짐, 즉 실행 파일을 만들 때 미리 붙여짐
- DLLs(Dynamically Linked Libraries)
    - 프로그램이 실행될 때 사용자 프로그램과 연결된 시스템 라이브러리
    - 여러 프로세스에 의해 공유될 수 있음 → 공유 라이브러리, 메인 메모리에 한 개의 인스턴스만 존재
    - 로더가 필요한 경우 메모리에 DLL 올림 → 올라간 주소에 맞게 동적 라이브러리의 함수들을 참조하는 주소들을 재조정함
    - 실행 중에 라이브러리를 메모리에 로드해야하고, 재조정도 일어나므로 동적 로딩과 달리 운영체제의 지원을 필요로 함

### 연속 메모리 할당

- 메모리에는 운영체제 프로세스와 사용자 프로세스가 모두 존재하므로, 어떻게 할당할 것인지 결정해야 함
- 프로세스를 메모리의 연속된 하나의 영역에 할당하는 방식

**메모리 보호**

- base(relocation), limit 레지스터를 통해 프로세스 간 메모리 영역을 보호할 수 있다.
- relocation register: 프로세스가 접근할 수 있는 물리 주소의 최소값
- limit register: 논리 주소 공간의 범위(크기)
- CPU가 접근하려는 논리 주소가 limit 범위 안인지 확인하고, 
범위 안이라면 MMU는 실행 중에 두 레지스터 값을 더해서 실제 물리 주소를 생성한다.
범위 밖이면 트랩을 발생시킨다.

**메모리 할당**

- variable-partition
    - 프로세스 크기에 따라 가변적으로 할당하는 방식으로, 가장 단순한 방법
    - 운영체제는 메모리의 사용 가능 여부를 나타내는 테이블을 가짐
    - 프로세스가 시스템에 들어오면, 운영체제는 각 프로세스의 메모리 요구량과 가용한 메모리 공간의 크기를 고려하여 어떤 프로세스에 메모리를 할당할지 결정한다.
    - 만약 가용한 공간이 충분치 않다면?
        - 프로세스를 리젝하고 적절한 예외 메시지 제공. 대신 프로세스를 대기 큐에 넣을 수 있음
        - 추후 다른 프로세스가 메모리 사용이 끝나면, 대기 큐에서 기다리는 프로세스가 할당받을 수 있는지 확인

### 메모리 할당 문제

**Dynamic storage allocation problem (할당 오버헤드)**

- 빈 공간으로부터 어떻게 n바이트의 공간을 할당할 수 있는지에 대한 문제
- 아래 방식들은 각각 선택하는 기준만 다를뿐, 결국 할당하는 메모리 크기는 n바이트임.
- First fit
    - 충분히 큰 첫번째 빈 공간을 선택
    - 외부 단편화 문제 발생
- Best fit
    - n바이트 이상인 곳 중 가장 작은 공간 선택
    - hole들이 정렬되어 있지 않는 한, 전체 순회 필요하고 외부 단편화 문제 발생
- Worst fit
    - 가장 큰 공간 선택, 마찬가지로 전체 순회 필요하지만 best fit보다 유용할 수도 있음
        - 쓸모없는 작은 크기의 남은 공간을 덜 만들기 때문
- 일반적으로 자원 활용도와 시간 측면에서는 `First / Best > Worst`로 보여짐
- 속도 측면에서는 `First >> Best > Worst`

**Fragmentation**

- External fragmentation
    - 남은 공간의 총합은 충분하지만 연속적으로 사용할 수 있는 공간이 없는 경우
    - 50-percent rule: 할당된 메모리 공간의 절반은 외부 단편화로 인해 빈 공간이 됨
    - Compaction
        - 흩어진 빈 공간들을 하나로 모으기 위해 프로세스를 이동시키는 것
        - 재할당이 동적이고 실행 중에 수행되는 경우만 가능하며 비용이 매우 큼
    - Paging
        - 프로세스들의 논리 주소 공간(연속적임)이 물리 메모리에 불연속적으로 할당되는 것을 허용하는 방법
- Internal fragmentation
    - 고정 분할 방식에서 발생 가능 (가변 분할에는 해당 없음)
    - 할당된 공간보다 프로세스가 사용하는 공간이 적어서 할당된 메모리 공간 내부에 낭비되는 공간이 발생
    - 이 부분을 찾는게 빈 Hole 자체를 찾는 것보다 오버헤드 큼
    - 메모리를 고정된 블록 사이즈로 나누고, 블록 단위로 할당하는 것

## 3. 의문 / 논점

### 가상 주소 공간이라는 개념이 필요한 이유

- 메모리 재배치의 자유
    - 가상 주소 개념을 도입함으로써 프로그램 입장에서는 항상 프로그램 내의 독립적인 가상 주소만 바라보고, 운영체제가 그 주소를 실제 메모리 주소로 매핑하는 과정을 통해 이런 문제를 해소할 수 있다.
        - 그러면 가상 주소가 없어도 바로 바로 매핑하면 되는 것 아닌가?
        > 프로세스가 메모리를 할당받아야 할 때마다 사용 가능한 빈 공간은 달라지며 그 공간을 찾아 할당받아야 하는데 논리 주소가 없다면 매번 프로그램 상에서 해당 물리 주소에 직접 이동할 수 있어야 하는데, 이는 현실적으로 불가능하다.
- 메모리 공간 보호
    - 프로그램은 각자 독립적인 가상 주소 공간을 가진다.
    - CPU는 메모리 할당 요청이 올 때마다 가상 주소 공간의 유효성을 검증하여 프로세스 간에 메모리를 침범할 가능성을 차단한다.
- 메모리 효율성
    - 가상 주소 개념 덕분에 프로그램의 일부는 RAM에, 일부는 SSD(하드디스크)에 흩어져 있어도 사용자는 이를 **하나의 연속된 주소 공간**으로 인식하고 사용할 수 있다.
